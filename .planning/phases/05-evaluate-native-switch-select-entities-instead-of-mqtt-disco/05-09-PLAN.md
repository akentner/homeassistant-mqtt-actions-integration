## Phase Goal

Switch and select entities owned by the MQTT Actions config entry replace MQTT Discovery as the default, existing installations migrate automatically, and Discovery stays only as an optional export. This plan makes the documentation, the project record and the release version say exactly that, and defines the real-instance acceptance of what unit tests cannot prove.

<objective>
Update the README and the docs pages and pin them with tests, amend the project record (the Discovery constraint, the requirements, the decision), bump the manifest version for the release, run all test tiers, and write the UAT checklist for the two real instances (D-03, D-05, D-09, D-10, D-11, DEC-01).

Purpose: Phase 4 established that documentation is pinned to the code by tests; the same holds here, and a released one-way migration must tell users what it does, what it cannot undo and which instances lose their UI entities.

Output: updated `README.md`, `docs/operations.md`, `docs/troubleshooting.md`, `docs/broker-acl.md` and `tests/test_docs.py`, the amended `.planning/PROJECT.md` and `.planning/REQUIREMENTS.md`, the manifest version 0.2.0 and the UAT items.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions)

- **Wording follows the code, not the plan:** each documentation statement is checked against the behavior built in plans 05-02 to 05-08; where a limit exists (no rollback, stragglers, concurrent adoption on mixed versions, hub removal now removes the entities because they are this integration's) the page says it.
- **The ACL block stays:** the documented `acl` block is a superset that serves the legacy path and the export, and the broker test enforces it; only the explanation around it changes. The export prefix gets a topic-table row and a sentence that the owner needs write access to it when the export is on.
- **Release prep, not the release:** this plan bumps `manifest.json` to 0.2.0; the tag and the GitHub release are a human step after the merge and a green Validate run, as in Phase 4.
- **Planning-file amendments are part of the deliverable:** PROJECT.md changes on a phase transition by its own Evolution rules, and the requirements statuses follow the passing tests.
