## Phase Goal

**As a** Home Assistant user, **I want to** create a Switch device whose MQTT state changes run my configured actions, **so that** I need no YAML automation.

This plan's slice: what the device looks like in Home Assistant (the discovered switch) and how it behaves across the whole lifecycle: create, change, delete, unload, reload, reconnect.

<objective>
Finish the discovery contract against real core MQTT discovery and implement the lifecycle: reconcile change and remove, explicit-delete ordering, orphan cleanup, hub-removal cleanup, MQTT-not-ready retry, reconnect republish, and unload that never clears discovery.

Purpose: DSC-01 and DSC-02 decide whether the entity is trustworthy (no ghosts, no silent deletion) and FND-05 decides whether it survives real brokers and restarts. This is where the entity registry, retained topics and HA's lifecycle meet, so each rule is pinned by a test.

Output: complete `discovery.py`, gateway helpers, lifecycle in `manager.py` and `__init__.py`, and integration tests. Implements D-01, D-03, D-04, D-07, D-15, D-16.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MQTT broker retained topics | Any client with write access can replace or clear discovery, state and availability topics |
| Admin action to destructive cleanup | Removing the hub config entry triggers broker-side deletions |
| Integration lifecycle to entity registry | Unload, delete and removal decide which entities survive |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Tampering | retained discovery, state and availability topics on the broker | medium | accept | A client with broker write access can clear or replace them; the next reload or reconnect republishes discovery and availability idempotently; broker ACL guidance goes into the README (plan 01-06) and TRU-04 in Phase 3 |
| T-01-14 | Tampering | destructive cleanup on hub removal (D-15) | medium | mitigate | Runs only on explicit admin removal of the hub entry; scope is limited to ids this instance published (persisted published set plus current subentries); an MQTT failure is caught, logged and never blocks removal; Phase 3 replaces it with a confirmed multi-instance delete |
| T-01-15 | Repudiation | stale retained online availability after a crash | low | accept | The shared MQTT client offers no Last Will for this integration; documented limitation, heartbeat-based availability is the deferred requirement AVL-01 |
| T-01-SC | Tampering | package installs | low | accept | This plan installs nothing |
</threat_model>
