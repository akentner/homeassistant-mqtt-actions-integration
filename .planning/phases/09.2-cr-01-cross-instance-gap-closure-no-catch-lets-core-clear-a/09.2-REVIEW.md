## Hand verification of the timing logic

### WR-02: one pending timer, retry accounting, stop

**Arm sites.** Three places can arm a replay-catch timer:
- `_arm_replay_catch` (950-960) cancels any pending timer first. Its only caller is `async_start` (825), so the retry reset happens once per start.
- `on_discovery_emptied` (975-988) returns early while `_cancel_replay_catch is not None`.
- `_rearm_or_log_replay_catch` (1148-1154) cancels a pending handle before it stores a new one.

`_on_replay_catch_due` clears the handle only when its own timer fires (993). The handle therefore always refers to the only pending timer, so at most one timer can be pending.

**Counting.** Every counted arm checks the bound first:
- `on_discovery_emptied` checks it at 982.
- The `else` branch of `_rearm_or_log_replay_catch` is reached only when no timer is pending, so the `or` at 1146 reduces to `retries < REPLAY_CATCH_RETRIES`.

An uncounted arm always cancels a timer that had not fired yet. Each replacement leaves the number of live timers unchanged, so the number of catch runs per start is at most 1 + `REPLAY_CATCH_RETRIES`. I traced the overlap case:
1. Timer T2 fires while run A holds the lock, so task B queues on the lock.
2. A counts and arms T3.
3. B replaces T3 with T4 without counting.
4. T4 fires as a lone run C. C has no pending timer to replace, so C must count.

No chain re-arms without spending the bound. A replaced D-06 timer is never lost:
- With waits, it is replaced, and its run comes later.
- Without waits, it stays as it is.

**Stop.** `async_stop` takes the lock, sets `_running = False` and cancels the single handle (1571-1573). `_rearm_or_log_replay_catch` runs inside the catch's lock (1118). A catch task that is queued on the lock re-checks `_running` (1037). A task already in the lock arms its timer before the stop cancels it.

### WR-03: spacing, bound, D-06

**Spacing.** The first UNHEARD re-arm waits `31 - elapsed`. Every later one waits 31 s:
- The roster clock is `time.monotonic` (manager.py:522), the same clock as the loop timer.
- A re-run therefore computes `elapsed >= 31`.
- `restart_listening` on a reconnect resets this to a partial window, which is intended.

**Bound.** `REPLAY_CATCH_RETRIES` still caps the re-arms. The last check comes about 155 s after the start.

**D-06 on a follower.**
- While a catch timer is pending, `on_discovery_emptied` returns early. The pending run reads the EMPTY content fresh and removes the twins, so the cleanup still happens in this run.
- Once the shared bound is spent, D-06 no longer re-arms. The new troubleshooting section states this limit.

### WR-01: fresh verdict per migrate, and no await before a clear

**Migrate.** In `_async_publish_migrates`, the content read and the synchronous `_ids_that_may_empty_the_topic` check come right before `await _async_attempt(...publish_migrate)`, with no await in between. A raising gate excludes the device, which is the fail-safe direction.

**After the batch.** The re-read at 1053-1059 requires EMPTY content or `device_id in migrated`. A device that was skipped on LEGACY content keeps its twins. A device that was skipped because its content turned EMPTY is still removed on the EMPTY path, which is correct.

**Clear.** The clear loop runs `_may_clear`, then an awaited migrate, then `_may_clear` again (1073-1078). It then calls `async_clear_device` directly through `_async_attempt`. Neither wrapper awaits anything before the publish (manager.py:375-382, discovery.py:325-327).

**Callers.** `_async_publish_migrates` has a single caller, the replay catch at 1050. `_async_finish_takeover` is not affected.
