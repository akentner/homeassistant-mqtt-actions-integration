## Phase Goal

Existing installations migrate automatically on update with entity ids, history and registry customizations intact. This plan wires the registry takeover of plan 05-02 into the manager's start, in the fixed order, for owners and followers, and settles how adoption behaves between native and legacy devices.

<objective>
Run the takeover pass at manager start before the platform forward: the owner broadcast, the registry moves and the retained clear for pending owned devices, the registry moves for native mirrors, a safe fallback to the legacy path for a device that cannot be taken over yet, and the adoption rules (D-05, D-09, D-12, MIG-01, MIG-02).

Purpose: this is the task that makes the migration automatic, and with it the one-way door of D-05. Nothing sets a device to pending yet except adoption; plan 05-06 adds the decision that makes an instance native.

Output: `DiscoveryPublisher.async_publish_migrate`, the pass and the state around it in `manager.py`, the owner marker in published documents, and `tests/test_native_start.py`.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions)

- **The pass lives in `Manager.async_start`:** after `_async_reconcile_locked(startup=True)` and before `_async_publish_owned()`, under the held lock. That is before the platform forward (D-12, entities first, then device, then retained clear) and before any document is published, so the marker only ever follows the owner's own clear.
- **`pending` is the work list:** an owned device id in the persisted `pending` set still needs the takeover. The pass empties it for every device that finished (DONE or NOTHING) and keeps it for a deferred one. Until a device is finished, `is_native` is False for it, so no native entity is added next to a legacy one.
- **The migrate payload goes out unconditionally for a pending owned device**, even when the owner's own registry has no legacy device, because followers' core MQTT entities may be loaded and an empty clear without a migrate would delete their registry entries (spike scenario A of plan 05-01). It is published live, not retained.
- **Timeouts are read at call time:** the manager passes `takeover.TAKEOVER_UNLOAD_TIMEOUT` and `takeover.TAKEOVER_RETRY_INTERVAL` explicitly, so tests monkeypatch the module constants; the devices of one pass are taken over concurrently (`asyncio.gather`), so a pass waits at most one timeout in total.
- **Test harness:** core MQTT on `mqtt_mock` does not loop publishes back. The tests use a local helper that delivers every publish on a discovery topic back to core as a live message (`retain=False`) through `async_fire_mqtt_message`, the way a real broker would, and they reuse `setup_legacy_device` and `customize_mqtt_device` from `tests/test_takeover.py`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| This instance to the shared discovery topics | The pass publishes a migrate payload and an empty retained payload; the wrong topic would unload or delete another instance's entities |
| Persisted Store state to the pass | The pending list decides which topics are published for |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-5-02 | Tampering | A forged or wrong migrate payload or empty payload unloads or deletes entities of another instance | medium | mitigate | The pass publishes only for ids that are owned devices of this instance and pending (unknown and mirror ids are dropped before any publish); the retained clear follows the owner's own takeover; the broker stays cooperative as documented in docs/broker-acl.md, and this phase adds no broker authentication by the owner's decision, so a hostile broker client can still publish discovery topics exactly as before; `test_the_pass_never_publishes_for_an_id_that_is_not_owned` |
| T-5-12 | Tampering | Adoption between a native and a legacy instance creates duplicate entities or hands a migrated device back to legacy | medium | mitigate | An adopted native device stays native through the persisted `devices` set; a legacy device adopted by a native instance is queued as pending and is not native until its pass ran; a concurrent adoption by an old and a new instance is the existing owner conflict; the three adoption tests |
| T-5-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs nothing |
