<objective>
Close the one remaining gap of the Phase 11 re-verification (11-VERIFICATION.md `gaps[0]`, review WR-05) and both of its coincidental-reliance halves on the Store side.

Core's `Store._async_load_data` (installed Core 2026.9.4, `homeassistant/helpers/storage.py:430-460`) calls the migration hook for any version mismatch and then `async_save(stored)`, stamped with this release's `minor_version = 1`. `LocalActionsStore` lets that path run. So loading a newer minor file, the forward-compatibility case 11-20 and 11-21 designed for, rewrites and re-stamps it:
- on every start of a hub;
- when the user opens the removal settings of an unloaded hub (`async_local_action_device_count`);
- even for a shape-invalid newer minor payload that the integration then reports unreadable.

The verifier reproduced both cases with probes. Every regression test used minor 1 fixtures, so they passed by fixture only. The same review finding also covers WR-05 part 1: a row that parses but carries keys this release does not know loses those keys on the next save, including a broker-triggered label refresh.

Owner decisions of 2026-10-21 (locked, this run):
1. Keep unknown keys: such rows are parsed and applied as today, but their unknown keys are retained and written back unchanged on every save. The README bullet "Newer versions" is aligned with that.
2. WR-06 is fixed in plan 11-25, not here.

Purpose: a Store that this release only reads is never written, and no save of this release drops what a newer release stored.
Output: a read-only load path, unknown-key retention, minor 2 regression tests, a Core pin, README and CONTEXT text, and disposition row WR-05 = fixed.
</objective>

## Edge-probe and prohibition lift (spec-less fallback, gap scope only)

- MIR-06 and MIR-08 (unclassified and unresolved in 11-EDGE-PROBE.json) are lifted as truths 1 to 4:
  - Repeated loads: a second start and a reload keep the bytes.
  - Wrong shape at a newer minor: unreadable and byte-identical.
  - Unknown keys: kept through every save path.
  - An empty `extra`: the stored row is exactly the v1 row, so `test_round_trip_one_additive_record_through_a_separate_store` stays green.
- Flagged assumption: the user's explicit saves (an edit, a removal, a label refresh, an adoption discard or restore) keep stamping this release's minor version, as Home Assistant's own Stores do after a downgrade. Every row and key is kept, so the only consequence is that a later minor release runs its migration again; its migrations must be idempotent. The alternative, keeping a newer stamp on rows written here, would make a newer release read v1-shaped rows as already migrated, so it was not chosen. See the reversibility note of Task 2.
- Flagged assumption: a row with unknown keys is applied without their meaning, for example a newer `"enabled": false` still runs here. The owner decided this on 2026-10-21. The README says it, and the downgrade warning of D-09 already says that newer settings may not apply.
- Prohibition recall (§B): both kept prohibitions are in `must_haves.prohibitions`, flagged unverified.
