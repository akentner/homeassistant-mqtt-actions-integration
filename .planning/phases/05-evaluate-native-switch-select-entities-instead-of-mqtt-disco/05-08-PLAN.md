## Phase Goal

MQTT Discovery stays only as an optional export for external consumers, and the legacy-only machinery (healing, ghost handling, the test topic, two issues) no longer touches native devices. This plan builds the export, its options and the conditionals that keep both paths correct side by side.

<objective>
Add the optional Discovery export for native devices with its hub options, and make healing, the two discovery issues and the test-topic subscription conditional on the legacy path, with a clean delete lifecycle for native devices (D-03, D-04, D-11, ENT-03, MIG-03).

Purpose: D-02 criterion (c) keeps non-HA consumers where it is cheap; D-11 fixes the shape (best effort, disabled by default, configurable prefix, no healing, no test buttons). The conditionals are what make the native path quiet: a native owner must not heal, count removals or warn about discovery.

Output: `build_export` and the publisher methods in `discovery.py`, the hub option and prefix in `config_flow.py` with strings, the republish on option change and the conditionals in `manager.py` and `sync.py`, and two new test modules.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions)

- **Default export prefix `mqtt_actions_export`:** a prefix that Home Assistant does not listen to, so that enabling the export serves external consumers without any duplicate in HA. If the user sets the prefix to the one core MQTT listens to, HA creates disabled-by-default duplicates, which is exactly what `enabled_by_default: false` and the documented warning are for (D-03, D-11).
- **Options are stored as submitted:** the hub options flow stores the export keys only when they are submitted, so the existing options test that expects exactly the delete key keeps passing; reads use `.get` with the defaults off and `mqtt_actions_export`.
- **The export prefix is validated like a base topic:** `validate_base_topic` already rejects empty values, wildcards, empty levels and a leading `$`.
- **The export covers native devices only:** a legacy device publishes the legacy payload, which is a superset and serves the same consumers until the device is native.
- **Clearing is always safe:** an empty retained payload on a topic that holds nothing is a no-op, so the delete and hub-removal paths clear the legacy topic and, when configured, the export topic without asking which one the device used.

| User-chosen export prefix to the broker topic space | A prefix could collide with core MQTT's discovery prefix or with this integration's own topics |

| T-5-17 | Tampering | An export prefix equal to the core MQTT prefix creates duplicate entities, or one that overlaps the base topic collides with this integration's topics | low | mitigate | The prefix is validated by `validate_base_topic`; a duplicate on the core prefix is created disabled by default (`enabled_by_default` false, `test_the_export_on_the_core_prefix_creates_a_disabled_duplicate`); the default prefix is one Home Assistant does not listen to; the options text warns about the duplicate (D-03) |
