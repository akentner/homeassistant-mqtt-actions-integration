## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: presence. Every instance announces itself and knows who else is there; later plans show it in a sensor, use it for re-trigger acknowledgements, for adoption and for duplicate id detection.

<objective>
Add the heartbeat protocol and the roster to the `Manager`: publish a heartbeat every 30 seconds, track the heartbeats of peers with a 90 second timeout, answer "is this owner offline" conservatively, and extend the documented, broker-tested ACL for the new topic (D-05).

Purpose: OPS-03 (the roster; the sensor that shows it is plan 04-04). The heartbeat is the only liveness signal that survives a crash, because Home Assistant owns the MQTT connection and no Last Will is possible (Phase 3 D-19).

Output: `topics.py`, `const.py`, `presence.py`, `manager.py` wiring, the ACL document and tests in three tiers. Implements D-05 and prepares D-07 and D-09.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Roster across a reconnect:** rows are kept, only the "listening since" time restarts. A peer is offline by the 90 second rule, which is what D-05 says; clearing the roster on every reconnect would make the count flap for up to 30 seconds. The research pattern file suggested clearing; this plan deliberately does not (Claude's discretion).
- **A newly started instance learns its peers at their next heartbeat** (at most 30 seconds later), because a non-retained message is not replayed. There is no reply-on-new-peer protocol; D-05 asks for a periodic heartbeat only.
- **Peers known only by availability** (an instance that never sent a heartbeat, for example a Phase 3 build) are not roster rows. For adoption such an owner is "not known to be offline" while its availability says online, so adoption needs `force`.
- **Instance id shape:** an instance id on a heartbeat topic must pass `is_valid_device_id` (letters, digits, `_` and `-`, up to 64), the same shape rule that protects ids elsewhere; generated ids are uuid4 strings.
- **Session id:** a lower-case canonical uuid4 text generated once per `Manager` construction, so every start has a new one. Plan 04-12 uses it for duplicate id detection.
- **Constants** live in `const.py`: `HEARTBEAT_INTERVAL_SECONDS` (30), `HEARTBEAT_OFFLINE_SECONDS` (90), `MAX_BROKER_MESSAGE_BYTES` (1024, shared by the heartbeat, the re-trigger request and the acknowledgement), `MAX_HEARTBEAT_DEVICES` (10000), `SIGNAL_ROSTER_UPDATED` (a format string with the entry id).
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 2 and CONTEXT D-05.
