## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: the delivery path. A maintainer can push a tag and get a gated, reproducible release, and every change is tested in the three tiers the project promised (unit, real Mosquitto, multi-instance fake broker).

<objective>
Split the test suite into the three tiers with pytest markers, split CI into one job per tier, make the broker tier unable to pass vacuously, and add the tag-triggered release workflow that checks the manifest version and requires every tier (D-19, D-20).

Purpose: OPS-06 (test tiers closed in the phase where the multi-instance tier exists) and the release half of OPS-05. The release workflow is what HACS users see, so it is gated before any release exists.

Output: pytest marker registration, tagged test modules, a four-job `ci.yml`, a reusable `validate.yml`, a new `release.yml`, the broker require-switch and the executable repository checks that pin all of it. Implements D-19 and D-20.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Tier definition:** the unit tier is "no `broker` and no `multi_instance` marker" and includes the `mqtt_mock` single-instance integration tests, as in the research. Tier membership is by module (`pytestmark`), not by test.
- **Strict markers:** `--strict-markers` goes into the pytest `addopts` so a mistyped marker fails collection (the research said "consider"; this plan decides yes).
- **Release gate set:** besides the three test tiers the release also requires the existing hassfest and HACS validation, by turning `validate.yml` into a reusable workflow. D-19 only names the test jobs; the extra gate costs nothing and the validation already passes on every push.
- **Prerelease tags:** a tag with a hyphen suffix (for example `v0.2.0-rc1`) is created with `--prerelease`; a plain `vX.Y.Z` is a normal release (assumption A16 of the research, not verifiable offline).
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 10 and CONTEXT D-19 and D-20.
- **The first real tag cannot be exercised locally.** The end-of-phase human check below covers it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Git tag to release | Anyone who can push a tag triggers the release workflow |
| Workflow to third-party code | External actions run with the job's token |
| Tag name to shell | The reference name is attacker-influenced text that reaches a script |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | release workflow, tag versus manifest | medium | mitigate | `check-version` compares the tag with `manifest.json` and fails on a mismatch; the `release` job needs it (`test_release_needs_the_version_check_and_every_tier`) |
| T-04-02 | Tampering | third-party actions in the release path | high | mitigate | Every external `uses:` stays pinned by a 40-character SHA, the release uses the preinstalled `gh` CLI instead of a new action, and the repository test rejects an unpinned reference |
| T-04-03 | Elevation of privilege | shell injection through the tag or reference name | medium | mitigate | The script reads `GITHUB_REF_NAME` as a shell variable, validates it against a semantic version pattern and never interpolates it with an expression |
| T-04-04 | Elevation of privilege | token scope | medium | mitigate | Workflow permissions are `{}`; only the `release` job gets `contents: write`; checkout never persists credentials (`test_only_the_release_job_can_write`) |
| T-04-05 | Repudiation | broker tier silently skipped in CI | medium | mitigate | `MQTT_ACTIONS_REQUIRE_BROKER=1` turns a missing Mosquitto into a failure in the broker job only |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package; `apt-get install mosquitto` already exists in CI and moves to the broker job |
</threat_model>
