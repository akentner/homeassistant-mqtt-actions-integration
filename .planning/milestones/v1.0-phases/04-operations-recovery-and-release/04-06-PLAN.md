## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: visibility of the other instances' devices. A mirror shows up on this instance's integration page and can be observed or disabled like any owned device.

<objective>
Give every mirror a companion device under this integration's config entry with its own mode select, keep that device in line with the mirror's life cycle, and prove that doing so never touches the core MQTT registry entries of the discovery payload (D-13 revised, D-14, D-15).

Purpose: the user-visible half of D-13 for mirrors and SYN-09 for mirrored devices. The mode gate itself already covers mirrors; this plan adds their entity and device and the cleanup.

Output: select platform support for mirrors, signals and cleanup in `manager.py`, and `tests/test_companions.py`. Implements the mirror part of the revised D-13 and D-14 and D-15 for mirrors.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Mirror companion devices have no subentry:** `config_subentry_id` is None, so they appear as plain devices of the entry (research Pattern 3). The model is `Switch device (mirror)` or `Select device (mirror)`.
- **Two devices with one name:** the core MQTT discovery device and the companion carry the same display name; the companion is told apart by manufacturer `MQTT Actions` and its model text. This is accepted in the research (Open Question 1) and confirmed in the post-research decisions; real-frontend behavior is checked by the human check below (assumption A14, the frontend facts come from the `dev` branch).
- **Companion removal helper:** `Manager._remove_companion(device_id)` removes only the registry device whose identifiers contain `(mqtt_actions, device_id)`. Plan 04-11 (adoption) reuses it.
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 3 and Phase 3 pitfall 10.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker document to device registry | The name of a mirror becomes registry text on this instance |
| Our registry cleanup to core MQTT | A removal of the wrong registry entry makes core MQTT clear the discovery for every instance |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-24 | Tampering | broker-supplied mirror name as registry and UI text | low | mitigate | The name passed `parse_document` (printable, at most 64 characters, not blank) before a mirror exists; it is stored as plain registry text and never rendered as markdown here |
| T-04-25 | Tampering | companion cleanup removes a core MQTT registry entry or live entity, so core MQTT publishes an empty discovery that deletes the device everywhere | high | mitigate | `_remove_companion` looks up only the `mqtt_actions` identifier; `_clean_registry` is unchanged and still skips live entities; `test_removal_never_touches_the_mqtt_registry_device` |
| T-04-26 | Information disclosure | a stale mode or companion of a removed mirror lingers | low | mitigate | Removal drops the stored mode and the companion in the same step (`test_mirror_removal_removes_the_companion_and_its_mode`) |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs nothing |
</threat_model>
