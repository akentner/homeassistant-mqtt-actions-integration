## Warnings

### WR-01: The migrate batch publishes from verdicts read before earlier awaits (D-10, T-09.2-08)

**File:** `custom_components/mqtt_actions/manager.py:1032-1040`, `1157-1168`
**Issue:** `may_empty` is computed once for every native device. `_async_publish_migrates(to_migrate)` then awaits one QoS 1 publish per device in sequence. The verdict of device k was read before the publishes of devices 1..k-1 were awaited.

A peer heartbeat can arrive during those awaits and announce device k as KEPT. One case is a peer that comes back online and sends its first heartbeat. Another is a user who customizes a row. The migrate for device k still goes out. The re-read at 1043-1049 then correctly keeps the twin and the topic, but the migrate has already unloaded the peer's kept, enabled row. That row stays unavailable on the peer while the topic stays LEGACY, until the peer's next restart.

The docstring promises the opposite: "No migrate goes out while the gate keeps the device: it would unload the kept rows on every instance (T-09.2-08)". The single-device case has no such window, because no await sits between the read and the publish. With N devices the window grows with N publish round trips. The test `test_no_migrate_goes_out_while_the_gate_keeps_the_device` only covers a single device.

**Fix:** decide each migrate from a read taken right before its publish:
```python
async def _async_publish_migrates(self, device_ids: Iterable[str]) -> set[str]:
    migrated: set[str] = set()
    if self._publisher is None:
        return migrated
    for device_id in device_ids:
        # Fresh read per device: a peer heard during an earlier publish keeps this one (D-10, T-09.2-08)
        content_now = self.sync.discovery_content(device_id)
        if content_now is not DiscoveryContent.LEGACY or not self._topic_verdict(
            device_id, content_now, self.gateway.mqtt_entry_id()
        ).remove_disabled:
            continue
        if await _async_attempt(
            partial(self._publisher.async_publish_migrate, device_id),
            f"publish the migrate payload of device {device_id}",
        ):
            migrated.add(device_id)
    return migrated
```
Add a two-device test in which the peer announces device 2 during the publish of device 1's migrate. It should assert that no migrate goes out for device 2.

### WR-02: A second arm overwrites the replay-catch timer handle without cancelling it

**File:** `custom_components/mqtt_actions/manager.py:1133-1135` (overwrite), `967-980` (`on_discovery_emptied`), `985` (`_on_replay_catch_due`)
**Issue:** `_on_replay_catch_due` sets `_cancel_replay_catch = None` before the catch task runs. While the catch is running, `on_discovery_emptied` therefore passes its `self._cancel_replay_catch is not None` guard and arms a timer. This happens when a LEGACY->EMPTY message for another held device arrives during one of the catch's awaits (migrate, flush, clear).

Example: both instances restart together. Each one clears the device it owns, and each one follows the other's device. The catch then reaches `_rearm_or_log_replay_catch`. If it has any UNHEARD or unsettled-UNKNOWN device, it assigns a new timer to `self._cancel_replay_catch` and drops the first handle without cancelling it. This causes three problems:
- `async_stop` (1540-1542) cancels only one of the two timers.
- When the orphan timer fires, `_on_replay_catch_due` sets the handle to `None` while the other timer is still pending. That re-opens `on_discovery_emptied` for yet another arm.
- Two catch chains run and burn the shared `REPLAY_CATCH_RETRIES` budget twice as fast. That makes the D-06 "same run" cleanup less likely to fit in the bound.

The `_running` guard in `_on_replay_catch_due` keeps the problem from leaking past a stop. The docstring of `on_discovery_emptied` ("with no catch timer pending") still does not hold.

**Fix:** keep exactly one pending timer, for example in `_rearm_or_log_replay_catch`:
```python
if waits and self._replay_catch_retries < takeover.REPLAY_CATCH_RETRIES:
    if self._cancel_replay_catch is not None:
        # A re-arm (D-06) is already pending: one run covers both reasons
        self._cancel_replay_catch()
    self._replay_catch_retries += 1
    self._cancel_replay_catch = async_call_later(self._hass, max(waits), self._on_replay_catch_due)
```
An alternative is to let the earlier timer stand and skip this arm. Either way, add a test that fires an EMPTY for a followed device while the owner's catch awaits a migrate, with a second device UNHEARD. The test should assert one pending timer and the retry count.

### WR-03: The UNHEARD re-arm spends the shared retry budget within seconds, and a dead peer blocks cleanup on every start

**File:** `custom_components/mqtt_actions/manager.py:1124-1135`, `custom_components/mqtt_actions/presence.py:296-297`
**Issue:** The first UNHEARD re-arm waits `HEARTBEAT_INTERVAL_SECONDS + EXPIRY_MARGIN_SECONDS - listening_seconds()`, about 26 s. Every later one waits only the 1 s floor, because `listening_seconds()` already exceeds 31 s. The remaining 4 retries are therefore spent within about 4 s. The wait covers exactly one heartbeat interval. This has three consequences:
1. **One lost heartbeat defers cleanup.** If one QoS 0 heartbeat of an online peer is lost, the owner keeps everything until the next start, although the next heartbeat would arrive about 30 s later.
2. **The D-06 re-arm is starved.** The same counter gates the D-06 re-arm (`on_discovery_emptied`, 974). After the UNHEARD retries are spent, a later owner clear of a followed device no longer re-arms the follower's catch in this run. That contradicts `docs/troubleshooting.md:119-120` ("removes them in the same run once the owner has cleared them").
3. **A dead peer blocks forever.** No Last Will exists, so an instance that crashed or was decommissioned keeps a retained `online` availability. `peer_keep_state` returns UNHEARD for it on every start, unlike `blocking_peers`, which drops silent ids after `HEARTBEAT_OFFLINE_SECONDS`. Every owner then keeps its legacy topic and twins indefinitely. The only signal is an INFO count line, and README/troubleshooting do not mention this case. The README only lists "older than 1.0.1" and "owner offline".

**Fix:**
- Space the UNHEARD retries one heartbeat interval apart. For example:
  ```python
  heard_by = HEARTBEAT_INTERVAL_SECONDS + EXPIRY_MARGIN_SECONDS
  elapsed = self.presence.listening_seconds()
  wait = heard_by - elapsed if elapsed < heard_by else HEARTBEAT_INTERVAL_SECONDS
  ```
  An alternative is a separate small UNHEARD budget, so the D-06 budget is not consumed.
- Document the stale-`online` case in README limitations and troubleshooting, including how to clear the dead instance's retained availability topic. A Repairs hint is optional.

## Info

### IN-01: The troubleshooting text implies the peer gate covers every owner clear

**File:** `docs/troubleshooting.md:115-121`
**Issue:** The text says the owner clears the old messages "unless a renamed or otherwise customized MQTT entity of that device is still enabled on this or on any other instance that is online". That is true for the replay catch only. `_async_finish_takeover` (manager.py:1419-1446) clears with migrate but without the gate, on purpose (research Q5). It runs at the cutover start and also from `_async_retry_unconfirmed_clears` on every reconnect and resync. There, kept rows survive only as unloaded registry rows.
**Fix:** Add one sentence saying that the one-time cutover clear (and its retry) is not gated by kept entities, and that kept entities then remain in the registry without a state until their instance takes them over. Mirror the sentence in the release notes (D-19).

### IN-02: A failing kept-list build logs a WARNING on every heartbeat

**File:** `custom_components/mqtt_actions/manager.py:868-872`
**Issue:** `kept_legacy_ids` logs a WARNING each time it fails. `async_publish_heartbeat` calls it every 30 s, so a persistent registry problem produces about 120 warnings per hour. The overflow case logs once per start (`_kept_overflow_logged`).
**Fix:** Gate the warning with a once-per-start flag, like `_kept_overflow_logged`, and keep the DEBUG line for each failure.
