## Phase Goal

The ten human-verification items of Phases 1 to 3 deferred from Phase 7 each have a recorded pass or fail on the final build, so the archived reports can be refreshed (ROADMAP Phase 8 success criterion 6). This plan runs three of them on ha-a: P1-3, P1-4 and P3-2. Plan 08-07 runs P2-1 and P2-2, plan 08-08 runs P1-2 and P3-1, plan 08-09 runs P1-1 and P1-6.

<objective>
Prepare each frontend check (fixtures through the documented import service, steps through the browser MCP where it works, screenshots into the evidence), let the owner judge the rendering, then record three results and remove every throwaway device.

Purpose: these are checks no automated tier performs. Claude drives everything that needs no eyes (D-04); the owner reviews what only eyes can judge (rendering and wording). The earlier owner passes (01-UAT tests 3 and 5, 03-UAT test 2) predate later changes to `config_flow.py` and the translations, so they are not evidence for the final code. The frontend items are split over three plans because each screenshot costs context; three items per plan keeps every plan inside its budget (a context constraint, not a difficulty judgement).

Output: three ledger blocks (7, 8, 14) recorded, screenshots under `08-evidence/{p1-3,p1-4,p3-2}/`, a clean ha-a.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-01:** ha-a and `mosq` only; production untouched. The browser is pointed at `http://localhost:8123` (and `8124` in plan 08-08) and nowhere else.
- **D-03:** each task starts from `check-preflight.sh --quick`; the build identity of every result is the pinned SHA.
- **D-04:** fixtures, flow steps, screenshots, retained-topic checks and cleanup are Claude's, through the chrome-devtools browser MCP and `ha-test-guard`. The owner judges rendering and wording only.
- **D-07:** all three items are in scope; none is waived by default. An override of a failed item is possible only under the owner's own name (plan 08-10).
- **D-08:** a rejected item is `result: issue` with a Gaps entry; the remaining items continue.
- **Planner decisions (documented):** (1) the owner may review the screenshots or look live in their own browser at `http://localhost:8123`; the fixtures stay in place until the task after the checkpoint; (2) if the browser MCP is not available in the executing session (research A1), the prep task still creates the fixtures and writes `browser.txt` saying so, and the owner performs the click path listed in the checkpoint; (3) the hostile names of P3-2 are inert inputs (backticks and an HTML bold tag as text), the actions are `system_log.write` only (T-08-16).

## Fixture facts (verified 2026-10-04; re-read before relying)

- ha-a: `http://localhost:8123`, hub config entry domain `mqtt_actions`, instance name "Test HA One". The integration page is Settings > Devices & services > MQTT Actions; **Add switch device** and **Add select device** are on it; a device's three-dot menu offers reconfigure and delete.
- The action editor (ActionSelector) can be switched to YAML mode. A literal `device_id` in an action target makes the flow warn once and save on the second submit; entity, area and label targets do not warn (`tests/test_config_flow.py` twins).
- Deep validation does not check that a service exists, so an unknown service name saves and then fails at run time and raises the Repairs failure issue (STATE decision).
- `mqtt_actions.import_devices` creates owned devices from a `data` document (used for the P3-2 hostile-named devices); the integration's own delete step and the generic core dialog both end in the same tombstone sequence.
- The profile language is set per user at Settings > profile (the general page, never the security page).
