## Phase Goal

A mixed fleet keeps working throughout the migration: running followers must follow the owner into native entities without a manual step, and the whole path must be proven with real Home Assistant instances, not only with one instance and mocks.

<objective>
Make a running follower flip a legacy mirror to native when the owner's marker first appears, reload automatically so the takeover runs before the platform forward, and extend the multi-instance harness to run the real setup so the cutover is proven across two instances (D-09, D-12, MIG-02, ENT-02).

Purpose: plan 05-05 migrates what is cached at start, plan 05-06 decides when an owner switches. The follower side of the live path is the remaining piece, and the research flagged both it (assumption A5) and the harness (Pitfall 8) as unproven.

Output: the flip handling in `sync.py` and `manager.py`, the `real_setup` option of the fake-broker harness, helpers for v0.1.0-shaped peers and `tests/test_cutover_instances.py`.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions)

- **Reload, not live takeover, for followers (D-12):** the flip is saved and the entry reloads; the takeover then runs at setup, before the platform forward, when no entity of ours for that device is loaded. The research's open live-takeover question (A5) is avoided by construction rather than answered.
- **Reload scheduling is guarded:** `Manager` keeps a flag so that several flips before the stop schedule one reload; the flag is per manager instance, so the new manager after the reload starts clean.
- **Harness shape:** `InstanceFactory.__call__` gains `real_setup: bool = False`. With it the factory patches `custom_components.mqtt_actions.MqttGateway` and `custom_components.mqtt_actions.manager.MqttGateway` with a function that returns the one cached `FakeGateway` of the instance's hass, then runs `hass.config_entries.async_setup`, so reloads create a manager on the same gateway. The default stays the bare manager, so no existing multi-instance test changes. The fake gateway returns no MQTT entry id, so the registry part of the pass is a no-op in this tier; the broker order of migrate then clear is still asserted from `FakeGateway.published`.
- **If the secondary hass cannot set the integration up** because of the manifest dependency on `mqtt`, mark `mqtt` and whatever it pulls in as already set up in `hass.config.components` before the setup; do not weaken the real setup into a manual platform forward, because reloads need the real `async_setup_entry`.
