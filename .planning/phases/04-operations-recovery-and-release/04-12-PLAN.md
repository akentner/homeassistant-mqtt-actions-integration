## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: the two recoveries that need the user's decision. A cloned or restored instance is told apart from the original and repaired without hurting it, and an old owner that returns after its device was adopted gets a safe way to follow.

<objective>
Detect a duplicate instance id (D-07), repair it with a fix flow that forgets the copy's devices locally and gives it a new id without touching anything the original owns (D-08), and give an old owner that returns after an adoption a fixable release flow instead of a fight (D-09 refined). Both flows share one local-release primitive and one Repairs dispatcher.

Purpose: SYN-10 and the safe half of SYN-07. Phase 3's teardown paths publish tombstones; reused here they would delete the original's devices for everyone, so this plan introduces a separate primitive with a fixed order and proves with byte-identical broker state that nothing of the original changes.

Output: detection in `presence.py`, the release primitive and the id rotation in `manager.py`, the recognition in `sync.py`, two flows and a dispatcher in `repairs.py`, translations and tests. Implements D-07, D-08 and the returning-owner part of the revised D-09.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Debounce (assumption A12):** a duplicate is confirmed after two heartbeats with the own instance id and a session other than this instance's own, within `HEARTBEAT_OFFLINE_SECONDS`; observations are bounded in number. The issue is deleted when no foreign session was heard for `HEARTBEAT_OFFLINE_SECONDS`. Constants `DUPLICATE_ID_CONFIRMATIONS` (2) and `MAX_DUPLICATE_OBSERVATIONS` (8) in `const.py`.
- **Guard against re-adding:** the manager keeps an in-memory set of device ids that are being released. `_async_reconcile_locked` ignores subentries of those ids, because each subentry removal runs the update listener, which would otherwise add a popped device again and republish it. The set is cleared when all subentries are removed.
- **One-shot offline suppression:** after the local release `Manager.async_stop` skips publishing the retained `offline` availability of the old instance id, because that topic belongs to the original too. The suppression applies to that one stop (the reload).
- **ACL note:** the new instance id is not in a per-instance ACL. The flow text says so; the troubleshooting page (plan 04-13) explains how to add it. This is documentation, not a code path.
- **Transferred-away state is in memory** (assumption A15, narrower than persisting it): after a restart the old owner's first publish can briefly overwrite the adopter's document, the adopter heals within one throttle window and the old owner recognizes the marker again. The release flow ends it. The adopter raises a claim issue during that overlap; that is expected.
- **Claimant payload:** the recognized adopter document is kept in memory (one per device, only for owned ids) so the flow can create the mirror from it without waiting for another publish; the payload passed `parse_document` before it was kept.
- **Release of a single device keeps its baseline and its mode** so the mirror that follows starts with them; only the duplicate flow and the transferred flow call the primitive.
- **Repairs dispatch:** `async_create_fix_flow` returns the duplicate id flow for the issue id `duplicate_instance_id`, the transferred flow for ids with the prefix `transferred_`, and the approval flow otherwise (the existing behavior). `repairs.py` keeps its own `_loaded_manager`.
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 7 and Pitfalls 1 and 5 and CONTEXT D-07, D-08 and the post-research D-09 refinement.
