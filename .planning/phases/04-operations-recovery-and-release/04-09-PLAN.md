## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: recovery by import. After data loss, a clone or a fresh install, an administrator restores devices from the JSON or the file of an export.

<objective>
Add the `import_devices` service: strict, all-or-nothing validation of every item through the broker document parser and the deep action validation, new uuids and this instance as owner, bounded size and device count, and private file reading (D-11).

Purpose: the import half of SYN-08. An import turns text into owned, unrestricted, published devices, so it is the most security-relevant path of the phase after the broker itself and reuses the strictest validation the project has.

Output: the import part of `portability.py`, the handler in `services.py`, the service definition and translations, and tests. Implements D-11 (import).
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Static denylist applies to imports (assumption A11):** an item whose actions call a service of the fixed denylist is rejected, although owned actions are otherwise unrestricted, so a hostile file cannot smuggle what mirrors would block. A legitimate item that calls a denied service has to be created in the UI.
- **Deep validation:** like the UI flows, an item whose actions do not validate on this instance (unknown service, unresolved device action) is rejected with the reason `invalid_actions`.
- **Not partial:** all items are validated before the first subentry is created. Creating the subentries afterwards is not transactional (a failure halfway leaves the earlier ones); that is rare and documented.
- **Caps (constants in `const.py`):** `MAX_IMPORT_DEVICES = 100` (like `MAX_MIRRORS`) and `MAX_IMPORT_BYTES = 4 * 1024 * 1024` for the whole JSON; the existing `MAX_DOCUMENT_BYTES` still caps each item.
- **Response and error shape (Claude's discretion):** `{"imported": [{"index": 1, "uuid": "<new uuid>", "name": "<name>"}, ...]}` with 1-based positions; a rejection raises `ServiceValidationError` with the key `import_rejected` and the placeholders `index` (the 1-based position, or a dash for an envelope problem) and `reason` (one of `bad_format`, `too_new`, `too_many`, `too_large`, `not_json`, `invalid_device`, `invalid_actions`, `denied_service`); file problems use the keys `bad_file_name` and `file_unreadable`; a call with both or neither source raises `import_needs_exactly_one_source`.
- **Reading the file:** by bare name from `<config dir>/mqtt_actions/`, opened with no-follow semantics, regular files only, size checked before reading, UTF-8 strict.
- **Shared helper:** `subentry_payload(content, device_id)` turns the shared content into subentry data (drops `kind` and `name`, adds the device id); plan 04-11 (adoption) reuses it.
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 8 and CONTEXT D-11.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Import file or object to device creation | Text from a file, a backup or a paste becomes owned, unrestricted, published actions |
| File name to filesystem | The import file name is user input that reaches a path |
| Import to peers | Imported devices are published to every instance |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-36 | Tampering | hostile import file with forged ids, oversized or deeply nested content, or denied services | high | mitigate | Every item runs through `parse_document` (size, depth, fields), the structure check, the static denylist and deep validation; forged bookkeeping keys lose to this instance's values; nothing is created before all items pass (`test_forged_bookkeeping_keys_are_ignored`, `test_denied_services_are_rejected`, `test_import_is_all_or_nothing`) |
| T-04-37 | Tampering | path traversal or symlink through the import file name | high | mitigate | Bare name with a full-match pattern, fixed directory, no-follow open, regular files only (`test_read_import_rules`) |
| T-04-38 | Denial of service | a huge or many-device import | medium | mitigate | `MAX_IMPORT_DEVICES`, `MAX_IMPORT_BYTES`, the per-item `MAX_DOCUMENT_BYTES`, size check before reading a file |
| T-04-39 | Elevation of privilege | imported actions run unrestricted as owned devices and are published to peers, where they still need approval | medium | mitigate | Admin only, deep and static validation including the denylist; the residual risk is that an administrator imports content they did not read, documented in the operations page |
| T-04-40 | Elevation of privilege | a non-admin user imports | high | mitigate | `async_register_admin_service`; `test_import_is_admin_only` |
| T-04-41 | Information disclosure | error texts or logs echo action content | low | mitigate | Fixed reason codes and a position only (`test_import_errors_never_echo_content`) |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs nothing |
</threat_model>
