## Phase Goal

**As a** user with several HA instances, **I want** devices created on one instance to appear on the others once I approve them, **so that** every instance runs the actions locally.

This plan's slice: the trust gate. A mirror starts running only when the user approved exactly the actions in front of them on this instance.

<objective>
Implement the approval gate (D-01, D-02): per-device approvals bound to the actions hash in the Store, a restricted Script build for mirrors with a guarded service-name hook (D-03, D-05), the Repairs fix flow with its issue lifecycle, and the blocked state.

Purpose: TRU-01, TRU-02 and TRU-03 (execution-time half), plus the end of STA-03: approved state changes run on every instance. This is the security-critical plan of the phase.

Output: `trust.py`, `repairs.py`, changes in `runner.py`, `manager.py`, `const.py`, en/de issue and flow texts and the tests named in the tasks. Implements D-01 to D-05 and the execution half of D-06.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **A1 / Open Question 2 default (denylist policy, flagged for user confirmation):** the fixed list of plan 03-01 stands: whole domains `shell_command`, `python_script`, `rest_command`, `command_line`, `hassio`, `backup`; exact `homeassistant.restart`, `homeassistant.stop`, `homeassistant.reload_all`, `homeassistant.reload_core_config`, `homeassistant.reload_config_entry`, `homeassistant.set_location`, `homeassistant.save_persistent_states`, `mqtt.publish`, `mqtt.dump`, `recorder.purge`, `recorder.purge_entities`; `notify`, `script` and `automation.trigger` stay allowed and visible in the approval YAML. `mqtt.publish` is denied because a mirror that can publish MQTT could forge other devices' config, discovery or state.
- **Open Question 3 default (D-06 reading):** deep validation (`async_validate_actions_config`) does not drop or block a mirror. It runs when the approval view is built (the view names the trigger labels that do not validate on this instance) and again when the Script is built, where a failure is the existing per-trigger setup error.
- **Open Question 4 default:** a mirror subscribes to the test topic and runs a test press only when approved, so the test button works on every approving instance; pressing Test on one instance therefore runs the actions on every instance that approved. The ACL document names the test topic as a second trigger source.
- **Open Question 6 default:** there is no hub-level opt-in switch; per-device approval is the opt-in of D-01. `.claude/CLAUDE.md` says "local opt-in flag"; the README trust section (plan 03-07) states the reconciliation and the planning return flags it to the user.
- **A5:** `run_on_startup` is part of the approved hash; run mode, breaker limits and names are not.
- **A6:** a statically denied mirror is blocked (visible, never approvable) rather than silently dropped.
- **A9:** a mirror whose triggers all have empty action lists needs no approval and gets no issue.
- **A14 residual risk (documented, not solved):** actions that call local scripts or automations, scenes, device actions or events are outside the denylist by design. Approval is the primary control; the denylist is defense in depth. The approval view lists these step kinds.
- **A3 (manual):** whether the Home Assistant frontend renders fix-flow descriptions as markdown, so the fenced YAML displays as a code block, is checked in the manual UAT at the end of the phase.
- **A10:** approvals are dropped with the mirror on a tombstone or prune (plan 03-05); no retention is built.
- **Kept approval entries:** an approval whose hash no longer matches stays in the Store (approvals are separate from mirror records); if the owner reverts to exactly the approved actions the approval applies again, which is what the user approved.
- **A2 tunables:** `APPROVAL_YAML_MAX_CHARS = 20000`, `APPROVAL_TEMPLATED_MAX_LINES = 20`, `APPROVAL_HASH_PREFIX_LENGTH = 12`.
- **hassfest and the repairs platform:** `repairs.py` imports `homeassistant.components.repairs` exactly like core's own `components/mqtt/repairs.py`, which declares no `repairs` dependency. If the hassfest job of the validate workflow objects after the push, the fix is to add `repairs` to `after_dependencies` in `manifest.json` in a separate fix commit; the local suite cannot run hassfest.
- **Self-derived edge cases (no SPEC.md exists, the spec-less probe was not run):** the prohibitions above and the behavior edge cases were authored by the planner from RESEARCH and CONTEXT.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker document to local execution | Approved actions run with the full privileges of this Home Assistant instance |
| Owner edit to approved state | The approved content can change after approval |
| Broker-supplied text to the approval dialog | Names, owner names and YAML are attacker-controlled and rendered as markdown |
| Store to Script build | Approval entries and mirror records are read back at start |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-24 | Elevation of privilege | remote actions run without the user's consent | critical | mitigate | No Script exists for a mirror until the stored approval equals its actions hash; unapproved, changed and blocked mirrors run nothing for state, test button and run-on-startup (`test_unapproved_mirror_runs_nothing`) |
| T-03-25 | Elevation of privilege | an approved document is later changed to malicious actions | critical | mitigate | Approval is bound to the canonical actions hash; a change unloads the Script, stops running and queued runs and raises a new request; delete-then-create resets dismissal (`test_changed_actions_lapse_the_approval`, `test_dismissed_issue_does_not_hide_a_changed_request`) |
| T-03-26 | Elevation of privilege | a templated service name resolving to a denied service, or `continue_on_error` swallowing the denial | high | mitigate | `GuardedTemplate` on every service-name template of mirror Scripts raises a plain Exception; static denied services block the mirror; a regression test pins the core hook (`test_denied_call_aborts_the_run_even_with_continue_on_error`) |
| T-03-27 | Tampering | a mirror using `mqtt.publish` to forge other devices' config, discovery or state | high | mitigate | `mqtt.publish` and `mqtt.dump` are in the fixed denylist (D-03); the list is not user-editable |
| T-03-28 | Tampering | markdown injection or an unreadable approval view | high | mitigate | `escape_markdown` on names, fence neutralization, control characters removed, hard cap with refusal instead of truncated display; frontend rendering verified in the manual UAT (A3) |

| T-03-30 | Repudiation | a dismissed issue hides a changed approval request | medium | mitigate | The old issue is deleted before the new one is created, so the dismissal state resets |
| T-03-31 | Elevation of privilege | residual step kinds outside the denylist: local scripts and automations, scenes, device actions, events | medium | accept | Approval is the primary control and the denylist is defense in depth; the approval view lists these step kinds; documented in the README (plan 03-07) |
