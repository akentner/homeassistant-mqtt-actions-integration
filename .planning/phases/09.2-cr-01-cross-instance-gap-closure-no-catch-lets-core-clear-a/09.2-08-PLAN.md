## Fixed expectations of the CR-01 gate

These lines go verbatim into `G/expectations.txt` before any variant runs.

Common setup of every variant, in order: (a) bench gate: `check-uat02.sh clean` PASS (suffix unset), nothing retained on `homeassistant/device/#`, retained availability `online` for exactly the instance ids of ha-a and ha-b on `mqtt_actions/v1/instances/+/availability`, ha-c not running, else ABORT; (b) pre-variant copy of `core.entity_registry` and `core.device_registry` of ha-a and ha-b with both stopped to `<9.2 backup base>/cr01-<variant>-pre-<UTC stamp>/{a,b}/` (0700), both started, 90 s, `check-preflight.sh --quick` PASS; (c) the legacy payload of ID built as `build_payloads` of `check-uat02.sh` does, with the A7 unique-id check (mismatch: ABORT); (d) live publish of that payload retained at QoS 1 on TOPIC while both run, read back retained and equal, 20 s wait; (e) shape check on each instance: the platform-mqtt row with unique id ID has `disabled_by` integration and at least one platform-mqtt button row of ID is enabled, else ABORT. After every start of a variant: a "postponed" line of this start on either instance is an ABORT (research Pitfall 8), never a verdict.

Variant 3, positive control (nobody keeps anything): no rename; restart ha-a and ha-b together (graceful); wait 90 s; record. ha-a holds when: no platform-mqtt row with unique id ID or `ID_test_*` exists, no device with identifier `["mqtt", "mqtt_actions_ID"]` exists, and TOPIC holds no retained payload. ha-b holds when the same three facts hold on ha-b. Both after one start, without a second restart (the follower cleaned up in the same run).

Variant 2, reverse case (only the follower keeps): rename on ha-b only the enabled replayed button with the lowest unique id to NAME; wait 40 s, recording the heartbeats for 35 s of that wait; restart ha-a only (graceful) while ha-b keeps running; wait 90 s; record. ha-a holds when: the platform-mqtt row with unique id ID still exists with `disabled_by` integration and every platform-mqtt row of ID that was integration-disabled before the start (by registry id) still exists, TOPIC holds a retained, non-empty payload whose JSON equals the published one, and at least one log line of this start contains "another instance keeps". ha-b holds when: a platform-mqtt row named NAME with `disabled_by` null exists and its state (WebSocket `get_states`) exists and is not `unavailable`, and the platform-mqtt row with unique id ID still exists with `disabled_by` integration.

Variant 1, bench case repeated (both keep; ha-b's start moves its row, WR-04): rename on each instance the enabled replayed button with the lowest unique id to NAME; wait 40 s, recording the heartbeats for 35 s of that wait; restart ha-a and ha-b together; wait 90 s; record. ha-a holds when: a platform-mqtt row named NAME with `disabled_by` null exists, the platform-mqtt row with unique id ID exists with `disabled_by` integration, and TOPIC holds a retained, non-empty payload whose JSON equals the published one. ha-b holds when: a row named NAME with `disabled_by` null exists on platform `mqtt_actions` or `mqtt`, every platform-mqtt row of ID that was integration-disabled before the start (by registry id) still exists with `disabled_by` integration (so the switch twin with unique id ID is still present), and TOPIC holds the same retained payload. A "Removed N duplicate entities" line on ha-b is allowed (enabled replay twins, D-05).

Verdicts: per instance `holds` when every fact of its expectation holds, else `contradicts`; per variant `holds` when both instances hold, else `contradicts`; overall `holds` when all three variants hold, else `contradicts`. `outcome.txt` per variant: line 1 the variant verdict; `ha-a: <verdict>; <facts>`; `ha-b: <verdict>; <facts>`; `release gate (D-15); expectations fixed in 09.2-08-PLAN.md and cr01-gate/expectations.txt before the run`; `build: <FIX>`.
