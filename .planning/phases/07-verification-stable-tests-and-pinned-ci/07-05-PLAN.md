## Phase Goal

Phases 1 to 4 have a current verification of the final code, and the tooling no longer reads them as stale (QLT-01, success criterion 1). This is the last plan on purpose: the digests cover `ci.yml`, `validate.yml`, `release.yml`, `manifest.json`, the test and source files that plans 07-01 to 07-04 edited, so any re-verification before the last edit would read stale again (research pitfall 1).

A report that lists archived paths and carries a digest from `verification.fingerprint` reads `passed` (reproduced in research: passed, stale after a one-line edit of a covered file, passed after the restore).

Output: four regenerated reports, the ledger section "QLT-01 re-verification (plan 07-05)", and four `passed` readings.

## Decisions this plan implements (visible, not silent)

- **D-01:** each of Phases 1 to 4 is re-verified by running the `gsd-verifier` agent against the current code; the report and its digest are regenerated; no hand-edited frontmatter. The digest comes only from `gsd_run query verification.fingerprint`.
- **D-02:** the new reports overwrite the existing `*-VERIFICATION.md` in `.planning/milestones/v1.0-phases/PHASE_DIR` (history stays in Git). No phase directory is revived under `.planning/phases/`, no side-by-side files.
- **D-03:** a gap caused by intended later behavior (for example Phase 5 native entities replacing MQTT Discovery as the default) is recorded in the report as "superseded by Phase 5". A real regression becomes a fix plan inside this phase.
- **D-04:** the human-verification items of the old reports are covered by the automated tiers (real Mosquitto, multi-instance); the verifier may cite those tests. Real-instance checks stay in Phase 8.
- **Acceptance (planner decision on research open question 1):** success criterion 1 is met when `verification status` on the four archived directories prints `passed`; `init.manager` is recorded too, but it never listed these phases, so it cannot be the gate.
- **Who runs the verifier (planner decision on research open question 2, assumption A5):** the orchestrator spawns `gsd-verifier` four times with an explicit `PHASE_DIR` and output-path override (Task 2, written as an orchestrator-run checkpoint). An executor that has an agent-spawning tool may do it itself; one that has not stops at Task 2 and the orchestrator resumes it at Task 3.
- **Last plan (planner decision):** re-verification follows the pin, the guard test, the test fix, the stress and three-run proofs, the CI proofs and the rc cleanup (research recommendation).
