## Phase Goal

The release workflow runs on the same pinned runner and passes end to end, shown by a prerelease tag run (QLT-03, success criterion 4). Only a real tag push exercises `check-version`, the reusable CI and Validate workflows and `gh release create`, so this plan pushes one prerelease tag, watches the run and removes every trace afterwards.

<objective>
Bump the manifest to `1.0.1-rc1` on the phase branch, tag `v1.0.1-rc1`, push after explicit approval, watch `release.yml` pass on `ubuntu-24.04`, then delete the prerelease and the tag and reset the manifest byte-identically (D-12, D-13). The real 1.0.1 release belongs to the end of the milestone and is not touched here.

Purpose: the pin of plan 07-01 changed `runs-on` in `release.yml`. The CI and Validate dispatch runs of plan 07-03 prove those two workflows; this run proves the release workflow, including the version check that compares the tag with the manifest and the job that creates the GitHub release with `contents: write`.

Output: a green `release.yml` run for `v1.0.1-rc1` recorded in the proof ledger with its eight job results, then a clean repository state: no tag, no prerelease, manifest at 1.0.0.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-12:** the release proof is a prerelease tag run: manifest version `1.0.1-rc1` on the phase branch, tag `v1.0.1-rc1`; `check-version`, CI, Validate and release must all pass on the pinned runner. `release.yml` marks a hyphenated tag as a prerelease. `1.0.1-rc1` is a valid manifest version (hassfest accepts SemVer and the project's own `SEMVER` test accepts the suffix; `AwesomeVersion` reads it as SemVer) and the `check-version` regular expression and the `v*.*.*` tag glob accept `v1.0.1-rc1`. CI and Validate skip tag pushes through `tags-ignore`, so they run once, through `release.yml`.
- **D-13:** pushing the tag creates a public GitHub release in the HACS repository, so Task 1 stops for explicit approval before the push, with `gate="blocking-human"` so no auto mode can approve it. After the run the prerelease and the tag are deleted and the manifest is reset. The run URL and the per-job result are recorded in the ledger, which the phase VERIFICATION cites.
- **Cleanup always runs (planner decision):** Task 3 deletes the release and the tag and resets the manifest whether the run was green or red. A red run is recorded and returned as a gap; a second tag attempt (`rc2`) needs a new approval, never an automatic retry.
- **The bump commit stays on the phase branch (D-12 literal):** the reset is a second commit that restores the file from the commit before the bump, so the net change of the manifest is zero and the covered-file digest of Phase 1 and Phase 4 in plan 07-05 sees identical bytes.
- **REMOTE_BRANCH:** the remote branch of plan 07-03 (`gsd/phase-06-native-entity-residual-fixes` unless the owner chose another name there). Pushes use `HEAD:refs/heads/REMOTE_BRANCH`, so no command depends on the local branch or worktree the executor runs in; the verify command reads `REMOTE_BRANCH` from the environment and defaults to the phase branch name.
- **Assumptions to check, not to trust (research):** a prerelease cannot take over the Latest marker from v1.0.0 (A1; Task 2 records `gh release list` while the prerelease exists), and deleting a tag does not start `release.yml` (A2; Task 3 records `gh run list`).
