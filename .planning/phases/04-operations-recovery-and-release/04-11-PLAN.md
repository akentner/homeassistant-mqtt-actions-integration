## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: recovery of an orphan. When the instance that owned a device is gone for good, another instance takes the device over without re-creating it and without losing its entities.

<objective>
Implement SYN-07 as adoption of orphaned devices (D-09 as refined after research, D-10): the additive `transferred_from` marker in the config document, the adoption on the manager with its preconditions, the follower pin rule that honors the marker only for an offline pinned owner, and the `adopt_device` service.

Purpose: SYN-07. The exception to Phase 3's "first owner wins" is deliberately narrow: only a marker that names the pinned owner, only while the roster says that owner is offline, only after an explicit administrator action on an approved mirror.

Output: the document marker, the Manager adoption and its persisted transfers, the changed pin rule in `sync.py`, the service with translations and tests in two tiers. Implements D-09 (adoption part) and D-10. The returning old owner is plan 04-12.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Planner-added precondition (safety, needs your confirmation):** the adopting instance must have approved the mirror's actions (or the mirror has no actions), and a mirror that is blocked by the static denylist is refused even with `force`. Without this, adoption would turn actions that were never reviewed here into owned, unrestricted, running actions, which contradicts TRU-01. `force` only overrides the owner-online check. Say so if you want it relaxed.
- **Marker encoding (post-research decision):** an optional top-level list `transferred_from`, newest last, at most 8 entries (`MAX_TRANSFER_HISTORY`), each an id of the same shape as any instance or device id; absent means no transfer and the document is byte-identical to a Phase 3 document. A malformed marker rejects the whole document with the new reason `bad_transfer`. No `SCHEMA_VERSION` bump.
- **Adopter steps (under the manager lock, in this order):** preconditions, build the subentry data from the mirror's shared content, persist the transfer record, seed the revision record with a hash that cannot match (so the first publish is revision + 1), keep the baseline, remove the mirror without touching its discovery or the core MQTT registry (its Script, subscriptions, approval, issues and companion device go; its stored mode stays), save, then release the lock, add the subentry and run a reconcile (the update listener would reconcile too and then finds nothing to do). If the subentry cannot be added, the mirror is restored by feeding its saved payload through the normal ingest path.
- **Persisted transfers:** additive Store key `transfers` (device id to list of ids), parsed defensively, pruned to owned ids at start, removed with the device.
- **Offline rule (D-09, assumption A10):** `PresenceManager.owner_offline` of plan 04-03; an owner that announced `online` and never sent a heartbeat is not treated as offline.
- **The returning old owner** (its start-up publish can overwrite the adopter's document; the adopter heals; the old owner then recognizes the marker) is handled in plan 04-12 by a fixable Repairs flow. Until then the old owner behaves as in Phase 3 (claim issue and heal).
- **Service errors (Claude's discretion):** keys `adopt_owner_not_offline` (names the owner and says to use `force: true`), `adopt_not_approved`, `adopt_not_a_mirror`; the response is `{"uuid": ..., "adopted": true, "previous_owner": <name>}`.
- **Reversibility:** the marker is rated one-way in CONTEXT and confirmed in the Post-Research Decisions, so no checkpoint is inserted; the rating is kept on the task for the record.
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 4 and CONTEXT D-09 and D-10.
