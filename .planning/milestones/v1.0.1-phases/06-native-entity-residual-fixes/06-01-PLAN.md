## Phase Goal

A native mirror stays native after a restart even when its config document is near the size limit, and a retained legacy Discovery replay during startup never leaves a duplicate entity behind the takeover (the accepted 1.0 review residuals IN-02 and IN-03). This plan is the IN-02 half (MIG-04); plan 06-02 is the IN-03 half and the README.

<!-- planner-discipline-allow: with_native_marker -->

<objective>
Persist the native flag of a mirror as a set of device ids in the native Store dict instead of inside the stored payload, keep 1.0.0 Stores native, make the flag sticky until the mirror ends, and retire the payload marker writer (D-01, D-02, D-03).

Purpose: with the flag in the payload the 20-byte marker no longer fits once a document is within 20 bytes of MAX_DOCUMENT_BYTES, so the stored copy of a native mirror loses its only persistent native flag and a restart rebuilds it as a legacy mirror: legacy entities, a test-topic subscription and a reload when the next marked document arrives. The flag has to live where no document size can touch it.

Output: `NativeState.mirrors` with parse, save, restore and lifecycle handling in `manager.py`, the marker writer removed from `document.py`, an updated persistence assertion in `tests/test_native_entities.py`, the new tests in `tests/test_native_start.py`, and D-03 in `06-CONTEXT.md` aligned with the sticky decision.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-01:** the flag is a set of mirror device ids in the native Store dict (`NativeState`, next to `pending` and `devices`), parsed with `_parse_native` and `is_valid_device_id`; additive key, no Store version bump. Headroom in the size cap is rejected.
- **D-02:** a mirror is native when its id is in the set or its stored payload carries the old marker, so 1.0.0 Stores stay native; only the set is written from now on and the first save moves marker-only mirrors into it; the marker writer is removed.
- **D-03 (amended by the planning session, user decision 1):** the flag is sticky. An id leaves the set only when the mirror ends: device deleted (tombstone or prune), adoption (it becomes owned and `NativeState.devices` applies) or release. A document without the marker never resets it, whether it comes from the same owner or from a re-pinned owner. The last sentence of D-03 in CONTEXT.md (a re-pin keeps the flag only if the new owner's document carries the marker) is superseded; Task 2 rewrites it. The current re-pin and update branches already keep the flag and are not changed.
- **D-07:** each fix starts with a failing-test commit (`test(06-01): ...`) that is red on the 1.0.0 production code, followed by the fix commit. The project already prefixes a bug fix commit with `fix`, so the fix commits are `fix(06-01): ...`. The plan type is `execute` with `tdd="true"` tasks (the convention of earlier phases), so the task-level RED gate applies to every code task.
- **Commit-type note for the end-of-phase review:** the generic TDD review gate of the workflow only inspects plans whose frontmatter says `type: tdd` and looks for a `feat` commit as the GREEN commit; this plan is `type: execute`, so that gate does not fire, and the per-task gate (a `test(06-01)` commit with intentional red evidence before the fix) still does.
