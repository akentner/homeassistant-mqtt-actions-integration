## Phase Goal

While a legacy Discovery message is retained, a customized, enabled MQTT entity of a device that any instance keeps survives on every instance: only the owner lets the shared legacy topic go empty, and only when no online instance announces a kept row. The new fix SHA then passes CI, the full bench re-run and the CR-01 release gate, and plans 09-04 and 09-05 are re-pointed to it (REL-01).

<objective>
Close the cross-instance CR-01 gap on the receiving side, test first: the catch decides every action that can empty the shared legacy topic with one pure gate fed by the role, the topic content, the local keep and what the online peers announce in a new heartbeat field. A follower never removes an integration-disabled twin on LEGACY content.

Purpose: the 09.1 bench proved that the keep is decided per instance while core's clear lands on a topic every instance shares (09.1-VERIFICATION truth #7). This plan is the tracer of the fix: the two red cross-instance tests of D-12 drive the gate through every product layer (presence parse, peer state, gate, registry removal, catch, clear).

Output: the gate in `takeover.py`, the field parse and peer state in `presence.py`, the gate application in `manager.py`, the D-12 and D-05 tests, the D-13 matrix and the receiver contract tests.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-12:** red first, one `hass`, core's empty payload looped back with `_loop_back_discovery`, a simulated peer heartbeat that lists the kept device. Two tests: the bench case on the follower side and the reverse case on the owner side (research Q6).
- **D-01 (receiving half), D-02, D-03:** the heartbeat key is `kept_legacy` (Claude's discretion, research A2), a JSON list of device ids, capped at 16 (`MAX_HEARTBEAT_KEPT_DEVICES`), read leniently. Offline peers do not block; an online peer not heard since this start is UNHEARD, a peer without a valid field is UNKNOWN; both keep. The sending half is plan 09.2-02.
- **D-05:** a follower never removes an integration-disabled twin on LEGACY content. On the takeover path the catch passes no content and no may-empty id, so nothing changes there (pinned in plan 09.2-02 Task 3). Enabled replay twins keep going (disable-then-remove publishes nothing).
- **D-08, D-10 (first half):** the explicit clear after the flush re-reads the content and the peer signal and needs the gate's `may_clear`. The re-check after a migrate await follows in plan 09.2-02 with the migrate itself (D-09).
- **D-04 (first half):** in this plan an UNHEARD peer keeps, like UNKNOWN; the gate already returns `rearm`, and plan 09.2-03 makes the catch use it.
- **D-13:** the pure gate is table-tested over the full matrix; the receiver parse and peer state have their own unit tests.
- **Orchestrator resolution 2:** `may_empty_topic` defaults to False (fail-safe, like the UNKNOWN content default); the one direct test helper `_remove_replay_twins_of` passes True, so the existing tests of `remove_replay_twins` stay unchanged.
- **Planner decisions:** (1) the gate lives in `takeover.py` next to `remove_replay_twins`, which keeps the "no MQTT import" rule and keeps the registry decision in one module; (2) the tracer test helper `_announce_peer` builds the peer heartbeat from `tests.documents.heartbeat_payload` plus the literal key, so the RED commit imports nothing that does not exist yet; (3) `Roster.peer_keep_state` takes the announced-online ids as an argument so it is unit-testable with the existing `_roster()` helper.
