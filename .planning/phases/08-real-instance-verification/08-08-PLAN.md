## Phase Goal

Phase 1's strings check (P1-2) and Phase 3's approval-rendering check (P3-1) run in the real frontend on the final build (ROADMAP Phase 8 success criterion 6).

</objective>

## Fixture facts (verified 2026-10-04; re-read before relying)

- Hub flow fields: instance name (default the location name) and base topic (default `mqtt_actions`, immutable after creation); the instance name is rejected only if unprintable or longer than 64 characters (`invalid_name`). `single_config_entry` is true, so the hub exists once per instance.
- Hub removal keeps every device retained by default (option `delete_devices_on_remove` false); the Store and issues are removed.
- A newly added hub on a fleet with no online legacy instance becomes native; with an online legacy instance it shows `native_cutover_waiting` (README, Upgrading from 0.1.x). ha-c is stopped and its availability is offline (plan 08-05).
- The `ha_two` ACL block carries a per-instance line `topic write mqtt_actions/v1/instances/{id}/availability`; ha-b's current id is `a09499e4-5674-48d5-b3d6-4860d5226fcb` until the re-add. Without a line for the new id, ha-b's availability publish is dropped silently.
- The approval request is a Repairs fix flow whose dialog shows device name, owner name, the YAML in one code block, a short hash, the startup sentence and lists of templated and residual parts; markdown characters in names are escaped (`escape_markdown`, T-03-05).
