**As a** user running several HA instances, **I want to** re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

(Phase 4 goal, taken verbatim from ROADMAP.md. This gap plan closes the one verified blocker of its success criterion 5: the release gate is red.)

<objective>
Close the single gap of 04-VERIFICATION.md (status gaps_found, score 4/5): the Validate workflow fails in the hassfest job, `release.yml` requires `validate` before it creates the release, so a first `v*.*.*` tag would never produce a GitHub release (ROADMAP success criterion 5, OPS-05, D-19, D-20).

Root cause: three fixable Repairs issues (`approval_required` from Phase 3, `duplicate_instance_id` and `transferred` from plan 04-12) carry an issue-level `description` and a `fix_flow` side by side. hassfest puts both keys in the exclusion group `fixable`; a fixable issue shows its text in `fix_flow.step.<step>.description`. No local test modeled the rule, which is why 1228 tests were green while CI was red.

Purpose: make the translations valid, keep every explanation the user had (the text moves, it does not shrink), and put a guard in the suite so the rule is checked locally for every issue and language.

Output: en.json and de.json with the issue-level description removed from the three issues and the missing explanation merged into their confirm steps; `tests/test_translations.py` with the guard, its self-test and wording pins. Nothing else changes.

Verified at planning time (exact state of the repository at commit 19ae5d6):
- The hassfest container that CI uses (`ghcr.io/home-assistant/hassfest`, run through the same command Phases 1 and 2 used) reproduces the failure locally: exit 1 and exactly three errors, `issues.approval_required.fixable`, `issues.duplicate_instance_id.fixable` and `issues.transferred.fixable`. GitHub run 36958292292 shows the same error and that the HACS job is green, so hassfest translations is the only red job.
- On a scratch copy of the integration with only those three issue-level descriptions deleted (outside the repository), the container exits 0 and reports `Invalid integrations: 0`. The approach is accepted by the real validator, not just by reasoning.
- Which text is lost without a merge: `approval_required`: nothing, its confirm description already names the device, the owner, the hash and says nothing runs before the submit. `duplicate_instance_id`: the cause (backup restored on a second machine or a clone started) and that both instances write the same topics. `transferred`: that the other instance adopted the device and published itself as owner, that this instance stopped publishing it to avoid overwrites, and that it still owns and runs the device locally until released. The sentences "Open this repair ..." and "Nothing changes until you confirm" are dropped on purpose: the user already opened the repair, and each confirm step ends with its own "nothing happens until you submit".
- Code paths that depend on the removed keys: `repairs.py` references no translation key (the flows use the step id `confirm` and abort reasons only, which stay). `manager.py` (approval and duplicate id) and `sync.py` (`_raise_once`, transferred) still pass `translation_placeholders` for the removed descriptions; they are harmless, `tests/test_repairs_flow.py` asserts them, and removing them would widen the scope. `tests/test_docs.py::test_troubleshooting_covers_every_issue_key` iterates the issue keys only, and the docs cite keys and titles, not descriptions: both unaffected. The tests that read a removed key are all in `tests/test_translations.py`: `NEW_ISSUES` (used by `REQUIRED_KEYS` and `test_issue_texts_exist_in_both_languages`), `ESCAPED_FLOW_PLACEHOLDERS` (two keys), `test_issue_strings_use_expected_variables` (the approval line), `test_required_duplicate_keys_exist_in_both_languages` and `test_required_transferred_keys_exist_in_both_languages` (one assertion each).
- Home Assistant shows only the title for a fixable issue in the Repairs list and the confirm step when the user opens it; this is the standard pattern of core integrations and the reason hassfest has the rule.
- The review item WR-02 (04-REVIEW-DISPOSITION.md, open) concerns what the confirm dialogs claim about deleting local configuration. It is a separate hardening item; this plan moves text and does not change what a dialog promises.

## Assumptions and defaults (visible, not silent)

- **hassfest runs locally in a container.** The command is the one Phases 1 and 2 used (`docker run --rm -v "$PWD":/github/workspace:Z ghcr.io/home-assistant/hassfest`). On this machine `docker` is podman's emulation and the image is already present; its notice on stderr is harmless. The container exits 1 for an invalid integration and 0 for a valid one (both observed at planning time).
- **No one-way or costly decision.** The plan moves translation text between keys; reverting it is a git revert, and no stored data, topic or wire contract depends on it.
- **No push.** The phase branch is not on origin yet. Pushing, the pull request and the first tag belong to the user and to the ship step; the plan only states what to check afterwards.
- **Wording is reused, not rewritten.** The German merged paragraphs use the sentences that already exist in the removed German descriptions.
