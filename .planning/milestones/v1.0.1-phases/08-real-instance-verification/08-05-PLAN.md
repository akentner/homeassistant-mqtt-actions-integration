## Phase Goal

With a v0.1.0 instance running next to a native instance, the v0.1.0 instance keeps running its actions for the migrated devices, shows no entities for them and raises no error (ROADMAP Phase 8 success criterion 1; Phase 5 UAT test 4).

<objective>
Fix the UAT-01 pass wording with the owner, set up the third instance `ha-c` with the v0.1.0 component next to the native ha-a and ha-b, run UAT-01, record block 1, and stop `ha-c` cleanly.

Purpose: this is the one check that needs a real mixed fleet; Phase 5 accepted it without a reproduction. The v0.1.0 follower still creates a mode select per mirror, so "shows no entities for migrated devices" is ambiguous until the owner words it (Pitfall 6). Doing the decision first prevents rationalizing after the observation.

Output: `uat-01` evidence, block 1 recorded, `ha-c` stopped, its availability offline, the owner's wording in the ledger.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-01:** `ha-c` runs in `~/ha-test`; the v0.1.0 component from `~/ha-test/v010` is the straggler.
- **D-03:** each task starts from `check-preflight.sh --quick`; the native fleet under test is unchanged by ha-c's arrival.
- **D-04:** container start, onboarding, MQTT entry, hub, ACL and approval are scripted; the owner is asked only for the wording decision (and for onboarding only if the scripted route fails, fallback rule).
- **D-08:** a FAIL is `result: issue` with a Gaps entry; v0.1.0 behavior and the product code are not changed in Phase 8.
- **Planner decision (supply chain, T-08-SC):** a fresh `default_config` first start installs integration requirements from the network; to avoid a fresh dependency resolution the `deps` folder of ha-b is copied first, and the HA image tag stays `2026.9` (never `latest` or `stable`).
- **Documented assumptions:** the onboarding API (`/api/onboarding/users`, `/auth/token`) and the config-entries flow API work as in standard Home Assistant (research A3, A5); each has the fallback rule behind it. A clone of the pre-Phase-5 backup is the fallback only if the fresh start fails for lack of network.

## Fixture facts (verified 2026-10-04; re-read before relying)

- Straggler component: `~/ha-test/v010/custom_components/mqtt_actions`, manifest version 0.1.0, identical to the tag for every `.py` file; it ignores unknown document keys and never hashes them, and it creates one mode select per owned or mirrored device on a companion device (`v010/select.py` module docstring).

- ACL pattern (docs and the existing blocks): per instance user, `topic readwrite` on the devices state, config, retrigger and test topics, the instances acks and heartbeat topics, `topic read` on all availability, and `topic write` on that instance's own availability topic only.
- Marker device (plan 08-03): uuid in `08-evidence/uat-03/fixture.txt`; approved on ha-b; actions `system_log.write` with `UAT03-MARKER on` and `UAT03-MARKER off`.
- A freshly added 1.0.x hub would wait for a legacy peer that is online (`native_cutover_waiting`); `ha-c` is therefore stopped at the end (Pitfall 10).
