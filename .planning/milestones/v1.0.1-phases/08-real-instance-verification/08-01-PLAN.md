## Phase Goal

The Phase 5 UAT debt is closed on real instances against the v1.0.1 build, and the ten deferred human-verification items of Phases 1 to 3 each have a recorded pass or fail with evidence; a failure becomes a gap, never an accepted skip (ROADMAP Phase 8, success criteria 1 to 6). No product code changes (CONTEXT domain).

<objective>
Build the verification bench once and prove it end to end: pin the build under test, back up the test instances, add two throw-away broker users, restart ha-a and ha-b at HEAD, prove the container runs the pinned files, prove the broker round trip with a second client, and create the one ledger (`08-UAT.md`) every later plan writes into. Then get the owner's decision on API access.

Purpose: every later check is only as honest as the bench under it. Both containers started before Phase 6 and run old code until restarted (Pitfall 1); the export prefix and the ha-c user are missing in the ACL (Pitfall 2); and a mistaken API call could reach production (Pitfall 9, corrected here). This plan removes those failure modes and gives later waves a single `check-preflight.sh --quick` gate.

Output: `~/ha-test/bin/` helpers (outside the repo, per the research recommendation), `00-preflight` evidence, `08-UAT.md` skeleton, a recorded owner decision.
</objective>

## Execution rules for the whole phase (every plan repeats them by reference)

- **Run in the main checkout, not in an isolated worktree.** The containers bind-mount `custom_components/mqtt_actions` of the main checkout of this repository read-only; the bench is one shared mutable thing. Do not switch branches, check out, rebase or reset between the preflight and the final stale-anchor check of plan 08-09 (D-03). The plans are strictly sequential (waves 1 to 10) because they share the bench and `08-UAT.md`; there is no parallelism to gain.
- **A failed check is a recorded result, not a stop.** A check script ends in PASS, FAIL or ABORT. FAIL is a result: record `result: issue` with a Gaps entry and continue with the next check (D-08). ABORT means the bench was wrong; fix the bench and re-run, never record it.
- **Fallback rule for every token-based or `[ASSUMED]` API step:** if no token file exists (decision option ui-only) or an endpoint does not behave as the plan says, do the same step in the frontend through the chrome-devtools browser MCP; if that is unavailable too, return a `checkpoint:human-action` that names the exact click path. Never read `.storage/auth`, and never dump `core.config_entries` (it holds broker passwords); read single non-secret fields with `jq` only.
- **Evidence is committed to a public repository.** No tokens, passwords, `.storage/auth`, `core.config_entries` content or screenshots of the profile security page. Every evidence task ends with `check-evidence-clean.sh` over its folder (T-08-02).
- **User-facing chat is German; files, commits and comments are English.** Commit evidence per plan as `docs(08-NN): ...` with `gsd_run query commit`.

## Decisions this plan implements (visible, not silent)

- **D-01:** all checks run in `~/ha-test` on ha-a, ha-b and `mosq`; the production broker and hosts are not touched by this plan.
- **D-03:** the SHA of the mounted checkout is recorded and each container is restarted at it; later plans re-assert it with `check-preflight.sh --quick`.
- **D-04:** Claude automates everything that needs no eyes or hands; this plan automates the whole bench; the only owner step is the token decision.
- **D-05:** `08-UAT.md` is created here with one block per check (14) plus the results table; evidence lives in `08-evidence/`.
- **Documented assumptions (not owner decisions):** (1) helper scripts live in `~/ha-test/bin/` outside the repo, because they carry local ports and paths (research open question 5; a scrubbed copy is added to the evidence in plan 08-10); (2) the bench gets its own broker users `uat_probe` and `uat_bridge` with random passwords in `~/ha-test/.mqtt-uat.env` instead of reading the passwords stored in the instances' MQTT entries, which would mean reading `core.config_entries`; (3) an INFO `logger` block for `custom_components.mqtt_actions` is added to the two test configurations so the replay-catch log line can be captured (research assumption A6); if `logger` rejects it the registry stays the proof.
