## Phase Goal

The v1.0.1 build is verifiably sound: Phases 1 to 4 have a current verification of the final code, the test suite is deterministic, and CI and release no longer drift with the floating `ubuntu-latest` image. This plan is the QLT-03 pin and its guard; plan 07-02 fixes the flake, plans 07-03 and 07-04 prove CI and Release on the pin, plan 07-05 re-verifies Phases 1 to 4 last.

<objective>
Pin every job of `ci.yml`, `validate.yml` and `release.yml` to `ubuntu-24.04` and keep it pinned with a guard test that reads the whole workflow directory (D-10, D-11). TDD order: the guard is committed red first (eight floating jobs at HEAD), then the pin turns it green, then negative tests pin down what the guard must reject.

Purpose: `ubuntu-latest` starts moving to Ubuntu 26.04 gradually between 2026-10-19 and 2026-11-19 (GitHub changelog of 2026-09-17), so CI, Validate and Release would change their environment without a commit. The v1.0.0 release run resolved the label to image `ubuntu-24.04`, version `20260927.320.1`, with Mosquitto 2.0.18 from the Ubuntu archive, so D-10's assumption holds and `ubuntu-24.04` is a supported label today. Pinned means one OS label; GitHub still rolls the hosted image weekly, so this is not a byte-identical environment (research pitfall 6). The guard states that in its docstring and the proof runs of plan 07-03 record the image version.

Output: eight `runs-on: ubuntu-24.04` entries, `workflow_runners` and `pinned_runner_problems` in `tests/test_repo_structure.py`, one real-files guard test and nine negative test cases.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-10:** pin `ubuntu-24.04` for every job in `ci.yml` (4 jobs), `validate.yml` (2) and `release.yml` (2). Mosquitto stays installed through `apt` in the broker job as today. The research verified that `ubuntu-latest` resolves to `ubuntu-24.04` today and that `ubuntu-24.04` is a supported label.
- **D-11:** a test in the suite reads `.github/workflows` and fails on any `*-latest` runner or on more than one distinct runner version. It follows the pattern of `tests/test_docs.py` and of the existing workflow guards in `tests/test_repo_structure.py` (pin a repository artifact to a rule).
- **D-07 (TDD order):** the guard is committed red first (`test(07-01)`), then the pin (`feat(07-01)`). The negative tests of Task 2 pass at once because the helper exists, so their red evidence is a mutation check (planner decision, Claude's discretion).
- **Planner decisions (Claude's discretion):** the guard lives in `tests/test_repo_structure.py` next to the other workflow guards; it uses a directory glob over `*.yml` and `*.yaml` instead of the fixed `WORKFLOW_FILES` tuple so a new workflow file cannot escape; the helper is split into `workflow_runners` (data) and `pinned_runner_problems` (rules) so the negative tests need no files for most cases.
- **Not planned:** a runner version variable, a matrix, a container image, or any change to Dependabot or Renovate (the guard catches a partial bump of a runner label, research assumption A4).
