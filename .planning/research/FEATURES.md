# Feature Research

**Domain:** Home Assistant custom integration (HACS) - MQTT state changes -> locally executed HA action sequences; Switch/Select devices; MQTT Discovery; central retained config shared across HA instances; per-device owner; re-trigger service
**Researched:** 2026-09-28
**Confidence:** MEDIUM (HA MQTT entity semantics verified against official docs = HIGH; there is no direct competitor, so "comparable product" analysis is by analogy = MEDIUM; frontend behaviour of ActionSelector inside config/options flows is from training knowledge and must be spiked = LOW)

## Landscape Summary

No product does exactly this. The idea sits at the intersection of four families, each of which contributes expectations:

| Family | Examples | What users expect from it that carries over |
|--------|----------|---------------------------------------------|
| HA UI Helpers / Template helpers | `input_boolean`, `input_select`, Template Switch/Select, "Add MQTT device" (MQTT subentries, HA 2025.7+) | Create/edit/delete in UI, entities appear in registry with device, rename/area/icon work, survive restart |
| MQTT Discovery publishers | HA MQTT switch/select, `ha-mqtt-discoverable`, Zigbee2MQTT, ESPHome-MQTT | Stable `unique_id`, device registry info, availability, retained discovery config, clean removal via empty retained payload |
| Multi-instance sync tools | `remote_homeassistant`, `mqtt-share-remote` (abandoned Feb 2021), AppDaemon `ad_sync_entities`, `mqtt_statestream` | Survive reconnects, no ghost entities, filtering, prefixing, clear direction of truth. Failure modes: stale states, duplicate entities, loops, abandoned maintenance |
| Blueprints / automations reacting to state | Blueprint "on change to X do Y" | Native action sequences, familiar editor, traces/debuggability |

The product's real competitor is "write an MQTT switch in YAML on each instance plus an automation on each instance". The value is removing that duplicated boilerplate and keeping it in sync. Every feature is judged against: does it make this less work or more reliable than that?

## Feature Landscape

### Table Stakes (Users Expect These)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Config Flow setup (broker via existing HA MQTT integration, no YAML) | HA quality scale Bronze: "can be easily set up through the UI"; sibling projects follow it | LOW | Depend on built-in `mqtt` integration (`dependencies`/`after_dependencies`), do not open own broker connection |
| Device creation UI: pick domain (Switch/Select), name, topics, actions | Core promise; parity with "Add MQTT device" subentries and Helpers UI | MEDIUM | Model devices as config subentries (HA >= 2025.3 pattern) OR store in own storage synced from MQTT; decide in architecture phase |
| Edit and delete device from UI (owner only) | Any helper is editable | MEDIUM | Non-owner sees read-only device with clear "owned by <instance>" message |
| Switch: `onChangeToOn` / `onChangeToOff` action sequences | Stated core requirement | MEDIUM | Reuse `homeassistant.helpers.script.Script`; do not hand-roll an action executor |
| Select: options each with StateValue, StateFriendlyName, Actions | Stated core requirement | MEDIUM-HIGH | MQTT select only has a plain `options` list (verified). Friendly names need `value_template` / `command_template` mapping (state value <-> label) generated by the integration, or the label is the option and StateValue is the wire payload. Must be designed carefully; test with special characters and duplicate labels |
| Native UI action selector (service, target, data) | Familiar editor, stated requirement | MEDIUM | `ActionSelector` in flow schemas. Frontend rendering inside config/options flows must be verified early (spike) |
| State from both paths: HA UI command topic and external MQTT state topic drive same behaviour | Stated requirement; matches how MQTT switch/select work (command_topic / state_topic) | MEDIUM | Integration should be the single writer of state: receive command, publish state (retained), and fire actions from the state-change path so UI and external sources cannot diverge |
| Loop and echo protection | Classic MQTT failure: command -> state -> action -> service -> command | MEDIUM | Trigger only on actual value change; ignore same-value republish; debounce; guard against actions that write back to the same device |
| Retained state and startup semantics | Users expect state to persist across HA restarts and not to fire actions unexpectedly | MEDIUM | Explicit decision needed: does a retained message received at startup/subscribe run actions? Recommend: no by default (record state only), per-device optional "run on startup" flag; the re-trigger service covers explicit replays |
| MQTT Discovery for every entity, with `unique_id`, device info, `origin`, availability | Requirement; unique_id is mandatory for registry (rename, area, history) | MEDIUM | Prefer device-based discovery (single `cmps` payload) for cleanliness; check availability of `default_entity_id` and retention rules against the minimum supported HA version |
| Stable identifiers across instances | Same device on N instances must not create duplicates or lose registry customisations after re-sync | MEDIUM | Device ID generated once by owner (UUID), never derived from name; renames do not change ID |
| Clean removal (empty retained payload for discovery and central config) | Users hate ghost entities (a top complaint with sync tools) | MEDIUM | Ordering: unpublish discovery, then config, in a defined order; followers must handle removal while offline via retained state on reconnect |
| Central retained config in MQTT with schema version | Requirement; versioning prevents old instances from mis-parsing | MEDIUM | Include `schema_version`; followers reject/ignore unknown higher versions with a repair issue instead of crashing |
| Per-device owner; non-owners follow read-only | Requirement | MEDIUM | Owner = instance ID stored in device config; instance ID persistent (generated on first setup, stored in config entry), human-readable instance name shown in UI |
| Delete warning: affects all connected instances | Requirement | LOW | Confirmation step in flow; consider showing number of known instances if instance presence is tracked |
| Trust model and opt-in for remotely provided actions | Actions arrive from the broker and run with full local service access; a public HACS integration without this is a security incident waiting to happen | MEDIUM | Follower instances must explicitly enable "accept devices from broker" (default off or first-time confirm); optionally allow-list of owner instance IDs; document broker ACL requirements (write access to config topic = remote code execution on all instances) |
| Re-trigger service (`mqtt_actions.retrigger`) on all connected instances | Requirement | MEDIUM | Service publishes a non-retained command message on a control topic; every instance executes locally. Accept optional target device(s). Must not be retained (replay on reconnect would re-fire) |
| Availability handling | Sync tools without it show stale states as valid | MEDIUM | MQTT LWT per instance; entity availability = broker connected and config valid |
| Robust action execution: errors logged, one failing action does not wedge the device | Users expect failures visible, not silent | MEDIUM | Use script runner run modes (queued/single), timeouts; log to HA logbook/trace; surface last error as attribute |
| Reload/unload cleanly; survive broker reconnect and HA restart | Bronze/Silver expectation | MEDIUM | Resubscribe on MQTT reconnect; re-read retained config; no duplicate subscriptions |
| Diagnostics download and translations (en, de) | Silver/Gold quality scale items; user is German | LOW | Redact broker topics/action data in diagnostics as needed; German translation is cheap and matches the user's needs |
| HACS structure: `hacs.json`, `manifest.json` (version, documentation, issue_tracker, codeowners), brand assets, GitHub releases, CI with hassfest and `hacs/action` | Requirement; HACS default-repo inclusion requires these | LOW-MEDIUM | Do in the first phase; retrofitting CI later is annoying |
| README with setup, trust model, topic layout, limitations | Bronze doc requirement; security transparency | LOW | Include an "Architecture and MQTT topics" section (others will write automations against it) |
| Automated tests (config flow, discovery payloads, action execution) | Bronze "automated tests" | MEDIUM | `pytest-homeassistant-custom-component`, uv, ruff |

### Differentiators (Competitive Advantage)

Aligned with Core Value: "a state change on one device reliably triggers configured actions on every connected instance, each executing locally". Differentiate on reliability, safety and multi-instance ergonomics, not on breadth of domains.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Zero-YAML multi-instance provisioning (define once, appears everywhere) | The headline; removes duplicate MQTT YAML + automations on every instance | HIGH (whole system) | This is the product itself; no maintained competitor (mqtt-share-remote abandoned 2021; remote_homeassistant needs websocket links between every pair and installation on both sides) |
| Broker-only coupling (no instance-to-instance connectivity) | Works across Tailscale/NAT/segmented networks; a single shared component | MEDIUM | Compared to `remote_homeassistant`: no tokens, no websockets, no ghost states on disconnect |
| Local execution of remote-triggered actions with per-instance entity mapping | Same action sequence, local entity IDs; instance can substitute | HIGH | Only worth it if entity IDs differ across instances; likely later. Defer, but design the config schema so a per-instance override layer can be added |
| Per-instance participation control (run / observe-only / disabled per device) | Multiple instances (prod vs test bed) should not all fire everything | MEDIUM | Local, stored per instance, not in central config. High value once someone has 3+ instances |
| Instance presence and roster (which instances are connected, last seen, config version applied) | Makes "reliably triggers on every instance" verifiable; supports meaningful delete warning and re-trigger feedback | MEDIUM | Retained per-instance presence topic with LWT; expose as diagnostic sensor / device attributes. Strong for debugging |
| Re-trigger with per-device targeting and acknowledgement/report | Turns a fire-and-forget service into an observable operation | MEDIUM-HIGH | Ack topic lets caller see which instances executed. Start without ack (P2) |
| Execution history / last run result per device (attributes or event entity) | Debuggability of actions running remotely; standard automation trace is not available for these | MEDIUM | Fire HA events `mqtt_actions_executed` with device, instance, result; optionally an `event` entity |
| Dry-run / "test actions" button in the device edit UI | Fast iteration; comparable to blueprint "run actions" in automation editor | LOW-MEDIUM | Runs locally only, does not publish state |
| Import/export of a device definition (YAML/JSON) | Sharing and backup, Git-managed configs | LOW | Simple serialisation of the same schema; also enables ownership transfer without broker access |
| Ownership transfer / "take over" for orphaned devices (owner instance retired) | Ownership model is fragile if the owner is decommissioned | MEDIUM | Explicit, confirmed action; writes new owner ID. Needed eventually; not launch |
| Repairs integration for problems (unknown schema version, untrusted owner, missing referenced entities) | Native HA UX for surfacing issues, Gold-ish quality | MEDIUM | Use `issue_registry` |
| Config validation on receive (referenced services/entities exist locally) | Actions from elsewhere may reference entities that do not exist here; avoid silent failure | MEDIUM | Warn via Repairs, do not block; run attempt logged |
| Bulk operations: republish discovery, resync from broker | Recovery when broker was wiped or retained messages were lost | MEDIUM | Service `republish`; also handles broker migration |
| Signed/HMAC-verified central config | Protects against arbitrary broker writers injecting actions | HIGH | Strongest security story but adds key distribution burden; consider as v2. Trust opt-in + ACL documentation is the v1 answer |

### Anti-Features (Commonly Requested, Often Problematic)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Peer-to-peer multi-writer editing | "Any instance should edit any device" | Needs conflict resolution (CRDT/vector clocks, last-writer-wins races); already ruled out in PROJECT.md | Per-device owner + explicit ownership transfer |
| Referencing local scripts by name | Reuse existing scripts | Scripts differ per instance; the device silently breaks elsewhere; already ruled out | Inline action sequence; optionally call `script.turn_on` inside the sequence knowing it is instance-specific |
| Execute actions on the owner and forward results | Central control | Contradicts "each instance executes locally"; single point of failure; timing coupling | Every instance executes locally from the same state change |
| Many domains at launch (Number, Button, Light, Cover, Sensor...) | Feature completeness | Each domain has its own state and command model; multiplies test matrix before Switch and Select are validated | Ship Switch + Select; design the device schema and discovery generator as a per-domain plugin so domains are added in v1.x |
| Retained re-trigger commands | "Make sure every instance gets it" | Every reconnect and restart replays actions (e.g. turning things on again) | Non-retained control message + roster/ack to observe delivery |
| Auto-running actions on every retained message at startup (as default) | "Restore state" | Reboot storms; garage door opens after HA restart | Off by default; opt-in per device |
| Auto-accept and auto-execute config from any broker writer | Convenience | Remote code execution across all instances for anyone with broker write access | Opt-in per instance, owner allow-list, documented ACLs |
| Building a custom action editor / templating DSL | Simpler UI or custom syntax | Reimplements HA's script engine and will lag it | Native `ActionSelector` and the `Script` helper |
| Bidirectional mirror of arbitrary existing HA entities (statestream/remote_homeassistant clone) | "While we're at it, sync sensors" | Different problem with well-known trap (loops, ghost entities); dilutes focus | Recommend `remote_homeassistant` or `mqtt_statestream` for that use case |
| Own MQTT client/broker connection settings | "Support a second broker" | Duplicates HA's MQTT config, credentials handling, reconnection, TLS | Use the built-in MQTT integration's connection only |
| Cloud/relay, web UI outside HA, or a companion add-on | "Manage all instances centrally" | Big scope, new attack surface | Every instance has the UI; owner instance is the editor |
| Sequence execution guarantees (exactly-once, persistence across restarts) | "Reliably" in the core value | Exactly-once across N independent HA processes is not achievable over MQTT QoS 0/1 without a shared log | Define reliability as at-least-once state delivery (retained state + QoS 1) and idempotent-friendly actions; document it |

## Feature Dependencies

```
Config Flow / MQTT integration dependency
    └──requires──> Device model & schema (versioned, stable IDs, owner)
                       ├──requires──> MQTT Discovery generator (Switch, Select)
                       │                  └──requires──> Select label mapping (value_template / command_template)
                       ├──requires──> Action execution (Script helper + ActionSelector)
                       │                  ├──requires──> State-change detection + loop protection
                       │                  └──requires──> Startup / retained semantics decision
                       └──requires──> Central config publish (retained)
                                          ├──requires──> Follower: subscribe, validate, create devices
                                          │                  └──requires──> Trust opt-in (before execution!)
                                          ├──requires──> Owner enforcement (edit/delete gating)
                                          │                  └──requires──> Clean delete (unpublish discovery + config, warning)
                                          └──requires──> Instance identity (persistent ID + name)

Re-trigger service ──requires──> Instance identity + control topic (non-retained) + Action execution
Instance presence/roster ──enhances──> Delete warning, Re-trigger ack, Availability
Per-instance participation control ──enhances──> Trust opt-in
Ownership transfer ──requires──> Owner enforcement + Instance roster
Signed config ──enhances──> Trust opt-in (v2)
HACS/CI structure ──independent──> everything (do first)

Retained re-trigger ──conflicts──> Startup semantics (replay storms)
Peer-to-peer editing ──conflicts──> Per-device owner
```

### Dependency Notes

- **Trust opt-in requires to precede follower execution:** the follower path (receive config -> create device -> run actions) must not exist in a release without the trust gate; build the gate together with the first version of follower sync, not as hardening later.
- **Select label mapping precedes Select discovery:** MQTT select has no native value/label split, so the mapping shapes the discovery payload, the state parser and the command topic contract. Decide it before writing the Select data model.
- **Startup semantics precede action execution:** it determines the first-message behaviour in the subscriber and cannot be bolted on afterwards without changing behaviour for existing users.
- **Instance identity underlies owner, presence, re-trigger ack, LWT:** generate and persist it in the first phase that touches MQTT.
- **State-change detection is shared by UI and external paths:** both must go through one code path or "both drive the same behaviour" will diverge.
- **Central config schema version is required before the first public release**, otherwise the first schema change breaks every existing installation.

## MVP Definition

### Launch With (v1)

- [ ] HACS/CI scaffolding (hacs.json, manifest, hassfest + HACS validation, uv + ruff + pytest) - gate for public distribution
- [ ] Config Flow + dependency on built-in MQTT; persistent instance ID/name
- [ ] Switch device: create/edit/delete, on/off action sequences via ActionSelector, MQTT Discovery, availability
- [ ] Single-path state handling (UI command and external state topic converge), loop protection, defined startup semantics
- [ ] Select device: options with StateValue/StateFriendlyName/Actions, discovery with label mapping
- [ ] Central retained config with schema version; follower creates devices; owner enforcement; clean delete with warning
- [ ] Trust model: follower opt-in for remote devices, documented ACL requirements
- [ ] Re-trigger service (non-retained, all instances, optional device filter)
- [ ] Error handling: action failures logged and surfaced; reconnect/reload safe
- [ ] README (trust model, topic layout, limitations), translations en/de, diagnostics

### Add After Validation (v1.x)

- [ ] Instance presence/roster (LWT + retained presence) - once users run 3+ instances or ask "did it reach everyone"
- [ ] Re-trigger acknowledgement report
- [ ] Repairs for schema/trust/missing-entity problems
- [ ] Per-instance participation control (observe-only/disabled)
- [ ] "Test actions" button and last-run/history events
- [ ] Import/export of device definitions; republish/resync service
- [ ] Ownership transfer for orphaned devices
- [ ] Additional domains (Button first: trivial state model; then Number)

### Future Consideration (v2+)

- [ ] Signed/HMAC config messages - needs key distribution design
- [ ] Per-instance entity mapping/overrides layer for actions
- [ ] Add-on/YAML-based (headless) provisioning
- [ ] Domains with richer state (Light, Cover, Climate)

## Competitor Feature Analysis

| Feature | remote_homeassistant | mqtt-share-remote / AppDaemon sync (abandoned) | HA "Add MQTT device" (subentries, 2025.7+) / Helpers | Our Approach |
|---------|----------------------|-----------------------------------------------|-------------------------------------------------------|--------------|
| Transport | Websocket per instance pair, tokens | MQTT broker, statestream-style | Local only | MQTT broker only |
| Sync unit | Existing entity states, service calls forwarded | Existing entity states, `call_service` events | None (single instance) | Purpose-built Switch/Select devices plus their actions |
| Config location | Per-instance YAML/UI | Per-instance YAML | Per-instance config entry | Central retained MQTT config, followers auto-create |
| Direction of truth | Remote is source | Bidirectional (loop risk) | n/a | Owner writes config; state is shared, actions run everywhere locally |
| Executes actions | Forwards service to remote instance | Forwards call_service | No (entities only) | Runs the action sequence locally on each instance |
| Ghost entity handling | Removes states on disconnect | Retained states (stale risk) | n/a | Availability topic + clean unpublish |
| Filtering/prefixing | Yes | Include/exclude | n/a | Not needed at launch (own device namespace); per-instance participation later |
| Trust/security | Access tokens, TLS | Broker only, no docs | Local | Explicit opt-in + ACL guidance; signing later |
| Maintenance | Active | Ended Feb 2021 | Core | Public HACS repo with CI; maintainer is the user |
