### WR-01: The migrate batch publishes from verdicts read before earlier awaits

**Files modified:** `custom_components/mqtt_actions/manager.py`, `tests/test_native_replay.py`
**Commits:** e138bae (red test), 9e8dff4 (fix)
**Applied fix:** `_async_publish_migrates` now reads the content and the gate fresh for each device, right before that
device's publish. It goes through `_ids_that_may_empty_the_topic`, which keeps the existing fail-safe if the gate
raises. A device whose content is no longer LEGACY, or whose gate now keeps it, gets no migrate and keeps its twins.
The re-read after the batch and the `device_id in migrated` filter are unchanged. Docstrings are updated.
**Test:** `test_no_migrate_goes_out_for_a_device_a_peer_announced_during_an_earlier_migrate`. Two owned native
devices have disabled twins on LEGACY content. During the first device's migrate publish, a peer announces KEPT for
the second device. The test asserts that the second device gets no migrate and no falsy publish, that its twin is
kept, and that the first device is cleaned up. It adds a reusable two-device harness,
`_an_owner_of_two_devices_with_disabled_twins_on_legacy_content`.
**Status:** fixed (logic change; the red/green test covers the race the review described)

### WR-02: A second arm overwrites the replay-catch timer handle without cancelling it

**Files modified:** `custom_components/mqtt_actions/manager.py`, `tests/test_native_replay.py`
**Commits:** 385061c (red test), 14c8476 (fix)
**Applied fix:** If a timer is already pending in `_rearm_or_log_replay_catch`, the function now replaces it instead
of overwriting the handle. The pending timer was armed by `on_discovery_emptied` while the catch awaited, and it has
already been counted against `REPLAY_CATCH_RETRIES`. So the function cancels it and arms one timer with the catch's
own wait, `max(waits)`, without counting a second retry. One run covers both reasons. As a result, exactly one catch
timer can be pending at a time: `async_stop` cancels it, and two catch chains can never spend the bound twice.
Without a pending timer, the behavior is unchanged: the retry is counted and the bound is checked. The docstrings of
`on_discovery_emptied` and `_rearm_or_log_replay_catch` are updated.
**Design note:** The review offered two options: cancel and re-arm, or keep the earlier timer and skip. This fix
takes the cancel-and-replace route but does not charge a second retry. That saves budget for D-06 (see WR-03). The
trade-off: the D-06 cleanup of that device moves from about 1 s to the catch's own wait (up to one heartbeat
interval). It still happens in the same run.
**Test:** `test_a_catch_that_rearms_while_an_emptied_topic_already_armed_it_keeps_one_timer`. While the start-up
catch awaits the first device's migrate, the second device's topic turns LEGACY->EMPTY (this arms D-06), and a new
instance is announced `online` without a heartbeat (UNHEARD, so the catch re-arms at its end). The test tracks the
catch timers through a wrapper around `async_call_later`. It asserts exactly one pending timer and
`_replay_catch_retries == 1`, that the first device's twin is kept, and that the second device is cleaned up (D-06).
Before the fix, two timers were pending.
**Status:** fixed: requires human verification (timer/retry-accounting logic)

### WR-03: The UNHEARD re-arm spends the shared retry budget within seconds, and a dead peer blocks cleanup

**Files modified:** `custom_components/mqtt_actions/manager.py`, `README.md`, `docs/troubleshooting.md`,
`tests/test_native_replay.py`, `tests/test_docs.py`
**Commits:** f187335 (red tests), 4e23c14 (fix)
**Applied fix:**
- **Spacing:** The first UNHEARD re-arm still waits `HEARTBEAT_INTERVAL_SECONDS + EXPIRY_MARGIN_SECONDS - listening`.
  Once that point has passed, each re-arm waits one full `HEARTBEAT_INTERVAL_SECONDS + EXPIRY_MARGIN_SECONDS` (31 s)
  instead of the 1 s floor. With 5 retries, an unheard peer now gets about 2.5 minutes, not about 30 s. A single lost
  QoS 0 heartbeat no longer defers the cleanup to the next start.
- **Docs:** The README Limitations section has a new bullet, and `docs/troubleshooting.md` has a new section, "Old
  Discovery messages stay after an instance crashed or was removed". Both describe the stale retained `online`
  availability of a crashed or removed instance. The troubleshooting section also gives the steps:
  - list the instances with `mosquitto_sub`;
  - compare them with the roster;
  - publish an empty retained payload on `mqtt_actions/v1/instances/<instance id>/availability`, using
    `mosquitto_pub -r -n` or `mqtt.publish` with `retain: true`.
  It also covers the effects: every instance forgets the dead instance, its mirrors turn unavailable, and adoption is
  the way to keep them. The behavior was checked in code: an empty availability payload pops the instance, and a
  mirror is available only while its owner's status is `online`.

**Design choice (D-04/D-06):** The fix uses the most conservative option:
- It only spaces the retries. It adds no separate UNHEARD budget and no new constant, because D-04 says the wait
  uses the existing `REPLAY_CATCH_RETRIES` bound with "no separate peer timeout constant".
- The bound keeps its meaning: at most 5 re-armed runs per start, shared by every reason.
- The cost is a longer wait. A peer that is truly dead keeps the owner checking for about 2.5 minutes, then the owner
  logs the existing INFO count line.

**Remaining limit:** Consequence 2 of the review (D-06 starvation) is reduced but not removed. In the common case the
peer is heard within one or two retries. But if an instance stays unheard for the whole bound, a later owner clear
of a followed device no longer re-arms in this run. The new troubleshooting section states this. A separate budget
for D-06 would remove the limit, but it would change D-04/T-09.2-12 ("the retry bound that every re-arm of this
start shares"), so it is left to the owner.
**Tests:**
- `test_the_owner_checks_an_unheard_peer_again_once_per_heartbeat_interval`: the peer's first heartbeat is lost and
  its second one arrives at 60 s. The clock advances by each pending timer's requested delay. The test asserts that
  every re-arm delay is at least 30 s, and that the owner cleans up and clears once in the same run. Before the fix,
  the delays were `[31, 1, 1, 1, 1]` and the bound ran out before 60 s.
- `test_docs_explain_a_crashed_instance_that_keeps_the_legacy_discovery`: the README limitation and the
  troubleshooting text must be present.

**Status:** fixed: requires human verification (timing logic, and the owner may want to revisit the separate-budget
option)
