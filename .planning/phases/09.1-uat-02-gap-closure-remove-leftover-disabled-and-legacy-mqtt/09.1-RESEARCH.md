### Locked Decisions

#### Fix strategy vs. CR-01
- **D-01:** CR-01 stays a hard invariant. The product never clears another instance's retained export topic, including
  indirectly through core MQTT's clear-on-removal hook.
- **D-02:** The start-up replay catch may now remove a **disabled** legacy replay twin, but only when the retained discovery on
  that row's topic is a **legacy payload** (multi-component with test buttons, as opposed to the single-component export from
  `discovery.build_export`, `discovery.py:140`) or the topic is empty. Core clearing a stale legacy topic is acceptable and even
  wanted. With an export payload on the topic, the row stays and CR-01 holds.
- **D-03:** If the catch cannot determine the topic content reliably (payload not readable, not delivered yet, or of an unknown
  shape), the row stays. This is a fail-safe in favor of CR-01, and the next start tries again. The log line carries a count
  only, never broker content.
- **D-04:** Only rows with `disabled_by: integration` are candidates. Rows with `disabled_by: user` always stay, because that is
  a user decision. The existing customization rule (`_is_customized`, WR-03) and the twin and identity rules of
  `remove_replay_twins` stay unchanged.
- **D-05:** Test first. A test that starts from integration tombstones reproduces E1 to E3 (red) before the fix and goes green

## Summary

The leftover rows do not come from the integration tombstones. They come from the duplicate guard. When the legacy replay
re-creates the `switch` or `select` row, it comes back **enabled** in both tombstone states. With a null tombstone, the registry
restores `disabled_by: None`. With an integration tombstone, core MQTT re-enables it on purpose (`reenable_condition`,
`components/mqtt/entity.py:1489-1524`). The guard then disables the row on its `create` event, about 5 s before the
quiet-period catch. The catch skips every disabled row because of CR-01 (`takeover.py:231-233`), so the switch or select row
and its legacy device stay. The test buttons are never guarded, so the catch removes them, which explains the
"Removed 2 duplicate entities" line in each round. A probe against the current code reproduces exactly that outcome from
**both** tombstone states (see Root cause). Phase 8 passed for a different reason: its build `b8232252` predates the CR-01 fix
`ea258df`, so its catch still removed disabled rows. The CONTEXT hypothesis is therefore **partly refuted**: the CR-01 skip is the
cause, the "second lead" (the guard) is the actual mechanism, and the null start (D-10 b) would fail on `7baec98` as well.

The fix extends only the disabled branch of `remove_replay_twins` under D-02 to D-04. It needs a reliable answer to "what is
retained on `<core prefix>/device/<id>/config` right now": LEGACY, EXPORT, EMPTY or UNKNOWN. The integration already holds a
long-lived subscription to exactly that wildcard (`sync.py:190-193`, `discovery_wildcard(prefix)` = `<prefix>/device/+/config`),
which receives the retained replay at subscribe time and every live change afterwards. Recommended: record a per-device
classification there (bounded to held ids), mark the subscription "settled" through the public
`mqtt.async_on_subscribe_done`, and let the catch read that state synchronously right before the registry step. EMPTY is
needed, not optional: the heal start (D-09, topics already empty) and the follower after the owner's clear both depend on it.

The owner/follower split for the D-06 clear already exists. Only owned devices are published for (`device_id in self.devices`,
plus not in `self.sync.transferred_away`). Mirrors publish nothing (`manager.py:1117-1131`, `_async_finish_takeover`). Removing a
disabled row that core rediscovered while disabled makes **that instance's core** publish `(None, qos 0, retain True)` on the
legacy topic (probe-confirmed). On a follower that is core's own publish, which D-02 accepts for LEGACY or EMPTY topics.

**Primary recommendation:** Classify the core-prefix discovery content per held device in `SyncManager._on_discovery_message`
(LEGACY / EXPORT / EMPTY / UNKNOWN, EMPTY only after the wildcard subscription is confirmed). Pass that verdict into
`remove_replay_twins` as a keyword argument that defaults to UNKNOWN, so CR-01 behavior is unchanged everywhere else. Remove
`disabled_by: integration` twins only for LEGACY or EMPTY. Then flush, and have the owner (not transferred away, legacy device
gone) clear LEGACY topics with `DiscoveryPublisher.async_clear_device` through `_async_attempt`.

### Pattern 1: Content source = the existing sync wildcard subscription (research focus 3)

**What:** `SyncManager.async_start` subscribes `discovery_wildcard(self._discovery_prefix)` and today only acts on empty
payloads (owner heal) [VERIFIED: sync.py:183-193, 706-726]. Extend `_on_discovery_message` before its `if msg.payload: return`.
Parse the device id with `parse_discovery_topic` (already done there). If the id is held (in `manager.devices` or
`manager.mirrors`, which bounds the map by owned ids plus `MAX_MIRRORS` (100, `const.py:69`)), store `classify_discovery(id, payload)`.
Never store the payload itself.

**Why this over the alternatives:**

| Option | Verdict | Reason |
|--------|---------|--------|
| A. Existing sync wildcard subscription + settled flag | **Recommended** | Public API, no new subscription or broker traffic, already modeled by `FakeGateway` with real retained semantics (`fake_broker.py:72-76` replays on subscribe). Live updates mean a follower sees the owner's clear right away. The state is read synchronously, so the decision sits in the same step as the registry change |
| B. Short-lived exact-topic subscribe per device at catch time | Fallback | Also public API, but it adds subscribe/unsubscribe churn. Under MQTT 3.1.1 (HA's default protocol) a fresh SUBSCRIBE makes the broker resend the retained message, and HA routes it to **every** matching subscription not yet marked in `_retained_topics` (`client.py:1347-1354`). That can include core discovery and re-trigger discovery processing. EMPTY still needs a SUBACK wait |
| C. Core MQTT private state (`hass.data["mqtt"]`, `discovery_already_discovered`, debug info) | Rejected | Private, breaks the gateway rule, and holds no reliable "current retained payload" |

**Settled (EMPTY vs. not delivered, D-02 vs. D-03):** An absent message is only EMPTY when the broker has acknowledged the
subscription. Use `mqtt.async_on_subscribe_done(hass, wildcard, 1, cb)` through a new gateway method. Register it right after
`gateway.async_subscribe` in `SyncManager.async_start`. HA dispatches `MQTT_PROCESSED_SUBSCRIPTIONS` with `[(topic, max_qos)]`
for each wildcard after the SUBACK (`client.py:1095-1122`). If the topic is already active and not pending, the callback runs at
once (`client.py:238-243`). Core's discovery subscription on the same string uses `discovery_qos` (default 0,
`discovery.py:605`), so max qos is the gateway's 1. If a user configured discovery qos 2, the callback never matches. Settled
then stays false, and EMPTY is never inferred: the rows stay, which is the safe D-03 direction. Clear the flag (and the map) on
disconnect and in `on_reconnect`. HA resubscribes and replays retained after a reconnect (`_retained_topics.clear()` at
`client.py:1268`).

**Content verdict at catch time:**
- A message was seen for the id → its classification. The latest message wins, and a live empty message → EMPTY.
- No message and settled → EMPTY.
- No message and not settled → UNKNOWN.
- A payload that parses to `{"migrate_discovery": true}` → ignore it (it is live and non-retained and does not change the retained content, `discovery.py:202-213`).

### Pattern 2: Legacy vs. export classification (exact shapes)

Shapes as built by the repo [VERIFIED: discovery.py:88-90, 100-110, 113-137, 140-159; const.py:112]:
- Legacy (`build_discovery`): `components` holds `"switch"` or `"select"` (with `"unique_id": <device_id>` and **no** `enabled_by_default`). It also holds one key per trigger, `BUTTON_KEY_PREFIX + key` with `BUTTON_KEY_PREFIX: Final = "test_"`, value `{"platform": "button", "unique_id": f"{device_id}_test_{trigger.key}", ...}`. Retired keys hold the tombstone `{"platform": "button"}`. `"device": {"identifiers": [f"{DOMAIN}_{spec.device_id}"], ...}`.
- Export (`build_export`): `components` holds exactly one key, `"switch"` or `"select"`, and `component["enabled_by_default"] = False`. No buttons, same device block.

Recommended `classify_discovery(device_id, payload) -> DiscoveryContent` (proposed name):
1. `payload == ""` → EMPTY.
2. Oversized (more bytes than `MAX_DOCUMENT_BYTES`, 256 KiB, `const.py:64`) or not a JSON object → UNKNOWN.
3. `device.identifiers` is not exactly `[f"mqtt_actions_{device_id}"]`, or `components` is missing or not a dict (this includes abbreviated keys such as `cmps`) → UNKNOWN.
4. Exactly one component, key `switch` or `select`, `unique_id == device_id`, `enabled_by_default is False` → EXPORT.
5. One main component (`switch`/`select`, `unique_id == device_id`, no `enabled_by_default: false`), every other key starts with `test_` and is a button (`platform == "button"`, with `unique_id == f"{device_id}_{key}"` or the bare tombstone), and at least one such key → LEGACY. This is D-02's literal "multi-component with test buttons".
6. Anything else → UNKNOWN (fail-safe keep).

A device without triggers would give a buttonless payload with no `enabled_by_default` key. That is UNKNOWN under rule 5, so
the row stays (D-03). The planner may relax rule 5 to "main component without `enabled_by_default: false`" if triggers can be
empty [ASSUMED: model rules on minimum triggers not checked].

### Pattern 4: D-06 owner-only clear (research focus 4)

The existing rule, verbatim [VERIFIED: manager.py:1033-1037 docstring, 1117-1131]: "Only ids that are owned devices are ever
published for (T-5-02). A follower publishes nothing." and in `_async_finish_takeover`: `if device_id not in owned: return True`
followed by `_async_attempt(partial(self._publisher.async_clear_device, device_id), f"clear the discovery of device {device_id}")`.
The heal path also refuses to publish for an adopted device: "Another instance adopted it: publishing would only start the fight
again (T-04-60)" (`sync.py:775`). `sync.transferred_away` is the set of owned ids another instance adopted (`sync.py:366-369`).

Recommended clear condition per id, all must hold:
- `content == LEGACY` (D-06: never EMPTY, EXPORT or UNKNOWN).
- `device_id in self.devices` and `device_id not in self.sync.transferred_away` (owner rule).
- `takeover.legacy_device(self._hass, mqtt_entry_id, device_id) is None` after the catch. This means no legacy row is left on this instance. An empty retained payload makes core delete a **loaded** legacy row (`test_plain_clear_on_a_loaded_entity_deletes_the_registry_entry`, `tests/test_takeover.py:274`), so a customized enabled row that the catch kept on purpose (WR-02, WR-03, D-08) must not be destroyed by the owner's own clear.
- Order: after `async_flush_registries`, as in the takeover path (move, catch, flush, then clear).

Native owned devices are never healed (`heals_discovery` is False for native, `manager.py:657-669`), so the owner's own empty
payload does not start a republish loop.

### Pattern 5: Tombstones after the clear (research focus 5)

- A replay is still possible after the clear only if someone republishes the legacy payload. The deleted record stays with `disabled_by: integration`. At the next replay core re-enables it (Pattern above), the guard disables it, and the catch removes it again (LEGACY) while the owner clears again. That is self-healing on every start. The bench's round 2 exercises exactly this.
- Core has no public API to purge one deleted record. The only purge is for orphaned records (`async_purge_expired_orphaned_entities`, `entity_registry.py:2464-2478`, requires `orphaned_timestamp`). Mutating `deleted_entities` directly is private state.
- The bench **requires** the records to exist: `reseed-tombstones.sh` ABORTs with "a missing record is never fabricated" when the switch or select record is missing (`reseed-tombstones.sh:112-118`). A purge would block D-10 b and D-12.
- **Recommendation: do not touch `deleted_entities`.** [VERIFIED: source read]

### Pattern 6: Guard and catch interaction (research focus 6)

- The guard disables with `RegistryEntryDisabler.INTEGRATION` (`takeover.py:286`). So every row it disabled in this run is a candidate under D-04, and it goes only with LEGACY or EMPTY content (D-02). With an EXPORT on the topic (UAT-04 clause 2, a foreign core-prefix export), it stays (CR-01).
- The guard's own rule does not change (CONTEXT). Its docstring (`takeover.py:266-269`) and `_arm_duplicate_guard`'s (`manager.py:907-908`) claim "the replay catch never removes it". They must state the refined rule.
- The guard keeps running for the whole run. A live replay after the catch is WR03-LIVE-REPLAY (D-07, out of scope).

### Anti-Patterns to Avoid
- **Awaiting between the content read and the registry removal.** Read the map, then remove synchronously. An await would let a live export arrive between decision and removal.
- **Treating "no message" as EMPTY without the settled signal.** That violates D-03 ("not delivered yet").
- **Clearing on EMPTY or UNKNOWN, or from a mirror.** Violates D-06 and T-5-02.
- **Changing `async_take_over`'s disabled branch** (`takeover.py:165-170`). Not in scope (D-04). The quiet-period catch handles leftovers on followers.
- **Changing the catch log text** that the bench greps.
- **Calling `async_update_entity(disabled_by=...)` on an already disabled row before removal.** It is unnecessary, and it fires an extra update event that the entity platform reacts to.

## Common Pitfalls

### Pitfall 1: The PHACC mock never replays retained messages on subscribe
**What goes wrong:** After `_restart`, the sync subscription sees nothing for the id. Depending on the settled state, a test
silently becomes EMPTY or UNKNOWN. The two existing CR-01 export tests (`tests/test_export_guard_receiver.py:442`, `:480`) can
flip for the wrong reason.
**Why:** `mqtt_client_mock` loops publishes back but keeps no retained store. The repo states it in `fake_broker.py:4-6`.
**How to avoid:** After every `_restart` in these tests, re-fire the retained topic content with `async_fire_mqtt_message(hass,
topic, payload, retain=True)`. Core discovery skips it, because its subscription already saw a retained message for that topic
(`client.py:1349-1354`), while the new sync subscription receives it. Stub the settled seam explicitly per test (monkeypatch or
fixture) rather than relying on debouncer timing.
**Warning signs:** A CR-01 test passes, but `_falsy_publishes` was never checked against a known-settled state.

### Pitfall 2: Subscribe debouncer timing in PHACC
**What goes wrong:** `async_on_subscribe_done` fires only after HA's subscribe debouncer runs. It uses `loop.call_at`
(`components/mqtt/util.py:110-116`), and `async_block_till_done` does not advance it.
**How to avoid:** `async_fire_time_changed` runs due loop timers (`pytest_homeassistant_custom_component/common.py:539-564`), so
`_quiet_period_passes` (+10 s) fires the debouncer **and** the 5 s catch in one pass, in unspecified relative order. Do not depend
on that order: set the settled state explicitly in catch tests, and test the gateway wrapper alone.

### Pitfall 3: G6 test contradicts the refined rule (expected change, not a regression)
**What goes wrong:** `test_the_export_off_cycle_leaves_the_disabled_row_in_place_across_the_restart`
(`tests/test_export_guard_receiver.py:442-477`) asserts the export row stays after "export off + restart". With D-02's EMPTY
clause, a settled empty topic makes that row a candidate, and it goes at the next start.
**Why it is correct to change:** README.md:104-105 and docs/troubleshooting.md:113-114 already promise: "When the export is
switched off again, the disabled duplicates stay in the entity list until Home Assistant is restarted, and the next start removes
them." The current code contradicts the shipped docs. The planner must rewrite this test's restart step to the refined rule,
noting the docs alignment. It is not a null-tombstone test, so D-05 does not freeze it.
**Residual risk to state in the release notes or PROJECT.md:** the EMPTY clause has a narrow race. A foreign export can be
republished after this instance's decision but before its core's hook clear reaches the broker (for example right after a broker
restart without persistence). The export would then be wiped until its owner republishes. That needs a broker restart and an
HA start in the same seconds window. Low risk, inherent to the locked D-02.

### Pitfall 4: The follower's core publishes the clear
**What goes wrong:** A reviewer reads "a follower publishes nothing" and flags a `(None, retain=True)` publish from a mirror instance.
**Why:** Removing a row that core rediscovered while disabled triggers core's hook on any instance (probe: `[(None, 0, True)]`).
**How to avoid:** Assert the product rule with `_discovery_clears` (payload `""`, the product's clear) and allow core's `None`
(`_falsy_publishes` sees both, `tests/test_takeover.py:153-160`). Document in the docstrings that core's hook publish on LEGACY or
EMPTY is accepted by D-02.

### Pitfall 5: The tag SHA and merge commits / worktrees
**What goes wrong:** The executor merges a worktree branch with a merge commit, or `main` gets a test or doc change after the fix.
Then the tag SHA (the fix commit) no longer equals the bench HEAD tree, or `check-stale-anchor.sh` fails. It diffs
`custom_components tests .github` between build.txt's sha and HEAD (`check-stale-anchor.sh:4,15`).
**How to avoid:**
- Fast-forward only. Phase 9 used `git fetch . gsd/phase-...:main` then `git switch main` (09-01-PLAN.md:156).
- Every test, docstring and product change goes in or before the fix commit. Only `.planning/` after it.
- The checkout is currently on `gsd/phase-09.1-...`, which is main plus 2 `.planning` commits. The bench bind-mounts **this checkout's working tree** read-only (`podman inspect ha-a`: `/home/akentner/Projects/homeassistant-mqtt-actions-integration/custom_components/mqtt_actions -> /config/custom_components/mqtt_actions (false)`), so whatever is checked out is live at the next container start.

### Pitfall 6: CI on the fix SHA needs origin/main == fix SHA at dispatch time
**What goes wrong:** Local main has `.planning` commits after the fix. A plain `git push origin main` puts a docs commit at the
head. `workflow_dispatch` runs on the branch head, so `headSha` != fix SHA.
**How to avoid:** The owner pushes `git push origin <fix-sha>:refs/heads/main` and dispatches CI and Validate while origin/main ==
fix SHA. Later `.planning` commits follow afterwards (precedent: `09-evidence/release/push-main.txt`, `push-readiness.txt` `why_refspec`).

### Pitfall 7: Bench scripts hard-code folder names
**What goes wrong:** D-16 names `preflight/` and `uat-02-integration/`. The unchanged scripts read and write
`$(evidence_root)/00-preflight/` (`preflight.sh:12`, `check-preflight.sh:15`, `check-stale-anchor.sh:15`, `check-uat02.sh:72,279`).
`check-uat02.sh clean` reads `$(evidence_root)/uat-02${PHASE8_EV_SUFFIX}/baseline-*.json` (`check-uat02.sh:34,397`), and both
`reseed-tombstones.sh` (`unset PHASE8_EV_SUFFIX`, lines 20-21, then `check-uat02.sh clean` at line 173) and `check-uat04.sh`
(`env -u PHASE8_EV_SUFFIX ... check-uat02.sh clean`, line 66) force the suffix off. So a plain `uat-02/` folder with baselines

**How to avoid:** Use the Phase 9 precedent (09-01-PLAN.md:122: "D-12's `preflight/` folder is realized as `00-preflight/`"). See
Open Question 1 for the `uat-02` folder.

### Pitfall 8: A deferred mirror takeover hides an id from the catch
**What goes wrong:** On a follower, if core processed the retained replay **before** the integration started, a legacy device
exists at start. `_async_native_takeover` then tries the mirror takeover and waits up to `TAKEOVER_UNLOAD_TIMEOUT` (10 s) for
loaded legacy entities. If they stay loaded, the device is deferred: legacy for this run, not native, so excluded from
`_native_device_ids()` and from the catch.
**Status:** Pre-existing behavior, seen as "keeps its MQTT device" (DONE, not deferred) in Phase 9 round 2. Not caused by the
fix. Grep the round logs for "Takeover of device %r postponed" (`takeover.py:144`) and record it as an observation if it shows up.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Wiping another instance's export via core's clear-on-removal hook (CR-01) | Tampering / DoS | Remove a disabled twin only for LEGACY or EMPTY content. EXPORT or UNKNOWN keep it. Decision and removal in one synchronous step |
| Hostile payload on `<prefix>/device/<id>/config` crafted to look legacy, to make an instance delete rows | Tampering | Only affects `integration`-disabled twins of held native ids that pass `is_legacy_entity`, are not customized and have an identity-carrying native twin. The worst case is a duplicate removal plus a clear of a topic that held the attacker's own payload. Accepted under the cooperative-broker decision |
| Broker content in logs | Information disclosure | Counts only (D-03) |
| Unbounded memory from the discovery wildcard | DoS | Store a classification only for held ids (≤ owned + `MAX_MIRRORS`), never payloads |
| Follower publishing for a device it does not own | Tampering / Repudiation | Product clear gated on owned and not transferred away. Core's own hook publish on LEGACY/EMPTY accepted by D-02 |
