## Phase Goal

**As a** Home Assistant user, **I want to** create a Switch device whose MQTT state changes run my configured actions, **so that** I need no YAML automation.

This plan's slice: the tracer. One Switch, created through the UI flows, published through MQTT Discovery, triggered by one live MQTT message, runs its action locally. It is production-quality code that later plans widen; it is not a prototype.

<objective>
Freeze the one-way identifiers, prove the whole architecture with one end-to-end Switch path (hub flow, switch subentry flow, gateway, discovery, decision function, action runner), then run the D-13 spike gate on the real frontend before the authoring plans build on the subentry model.

Purpose: the identifiers (domain, topic layout, UUID unique_id) become permanent once code creates them, and the subentry-plus-ActionSelector model is the one thing the research could not see in a browser. Proving the path end-to-end now means an architectural dead end costs one commit, not five plans.

Output: a loadable, hassfest-clean custom integration `mqtt_actions` with one tested vertical slice and a recorded D-13 verdict. Implements D-01, D-03, D-04, D-05, D-11, D-12, D-13, D-14 (thin form); widened by plans 01-03 to 01-05.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MQTT broker to integration | Anyone with write access to a state topic can publish payloads the integration parses (untrusted) |
| HA admin UI to stored config | Actions are authored by an admin in the flow and stored raw in subentry data |
| Integration to HA service registry | Configured actions run with full local service access |
| Developer machine to live HA host (D-13 gate) | A pre-release build is copied to a production instance by the developer |
