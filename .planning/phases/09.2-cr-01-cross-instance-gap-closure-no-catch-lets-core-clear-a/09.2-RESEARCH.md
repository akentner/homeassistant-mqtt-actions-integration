#### Cross-instance mechanism
- **D-01:** Peers announce kept legacy rows in the existing presence heartbeat (`presence.py`). Each instance adds a new
  field: the list of device ids for which it holds a kept, **enabled, loaded** legacy (platform `mqtt`) row (the rows
  `remove_replay_twins` keeps: no native twin under this entry, customized, or carrying the identity). Device ids only,
  never names, entity ids or registry content; capped and strictly validated like the other heartbeat fields
  (T-04-09 to T-04-12); no field value in any log line (T-04-14). The ids already appear in broker topics, so nothing new
  leaks. The value must be correct in the first heartbeat after start (the registry already holds the customized row
  before the replay arrives). — **Reversibility:** costly — the heartbeat field becomes a wire contract between versions;
  removing or renaming it later makes newer peers read older ones as UNKNOWN.
- **D-02:** The gate: the shared legacy topic may go empty for device X only when (a) this instance keeps no enabled legacy
  row of X (existing local rule) **and** (b) every **online** peer (presence roster) has sent a heartbeat since this
  start that carries the new field and does not list X. Offline peers do not block: they have nothing loaded, so core's
  empty payload deletes nothing there.
- **D-03:** A peer that is online but not yet heard since start, or that sends no field (older version, e.g. v1.0.0),
  counts as UNKNOWN: keep, no removal, no clear (fail-safe in the spirit of 09.1 D-03). In a mixed-version fleet the
  disabled twins stay until every online instance runs 1.0.1. README/troubleshooting and the release notes say so.
- **D-04:** Waiting for peer heartbeats uses the existing catch re-arm (`REPLAY_CATCH_RETRIES`,
  `takeover.py:46`): a device blocked only because a peer is not heard yet is treated like UNKNOWN content and the catch
  arms itself again within the existing bound; after that it keeps, and the next start tries again. No separate peer
  timeout constant.

#### Who lets the topic go empty
- **D-05:** **Only the owner** of a device ever lets its shared legacy topic go empty: by removing an integration-disabled
  twin that core discovered in this run (core's clear-on-remove hook) or by an explicit retained clear. A follower
  (mirror) never removes an integration-disabled twin on LEGACY content. This extends T-5-02 ("a follower publishes
  nothing") to core's hook. It applies at **both** call sites of `_remove_replay_twins`: the start-up takeover path
  (`manager.py:1152`) and the later replay catch (`manager.py:913`). Enabled replay twins (disable-then-remove, which
  publishes nothing) are unaffected.
- **D-06:** A follower removes its integration-disabled twins once the content of that device is EMPTY. When the content
  of a device with a waiting twin changes from LEGACY to EMPTY (the owner cleared), the follower's catch re-arms in the
  same run, bounded like the existing retries, so UAT-02 meets E1 to E3 on both instances after one start without any
  change to expectations or procedure.
- **D-07:** If the owner is offline, the legacy topic stays retained and the followers' twins stay disabled. That is
  harmless and documented.

## Summary

The 09.1 bench proved that the CR-01 keep is decided per instance while the clear it guards against lands on a topic
every instance shares. Core MQTT 2026.9.4 deletes the registry row of every **loaded** entity of a device when an empty
device payload arrives, unless that entity was first put into "migration" by a `migrate_discovery` payload. This session
traced that in core source and re-confirmed it with three throwaway probe tests against the installed core 2026.9.4:
migrate followed by the empty payload (even back to back, and even when the empty payload is core's own clear-on-remove
hook) **unloads** the peer's kept row but **keeps** its registry row with the user's name; the hook clear without migrate
**deletes** it. Two contract tests that pin exactly this already exist in `tests/test_takeover.py`. So D-09 is confirmed:
add the migrate payload before every owner action that can empty the topic.

The fix therefore has three layers: (1) a follower never removes an integration-disabled twin on LEGACY content
(D-05) and re-arms its catch when its view of the topic turns EMPTY (D-06); (2) the owner empties the topic only when
the new gate passes: no local kept row and every online peer has announced, since this start, a heartbeat field that
does not list the device (D-02/D-03), with a timed re-arm for peers not heard yet (D-04), whose wait must be derived from
the heartbeat interval because the current re-arm never fires once the discovery settle is done; (3) a migrate payload
right before the twin removal and before every explicit clear (D-09), with a re-check of content and peer signal right
before each of them (D-10).

The bench must change in one non-obvious way: in the reverse case (D-16 variant 2) a follower only holds a customized
legacy row **mid-run**, because every follower start moves its customized legacy rows to native (WR-04 or a plain move)
before the replay arrives. Variant 2 therefore restarts only the owner. Two existing tests are contracts that the locked
decisions change on purpose and must be updated: `test_a_follower_removes_its_disabled_twin_and_publishes_nothing`
(contradicts D-05) and `test_heartbeat_is_published_non_retained_with_qos_0` (pins the heartbeat key set).

**Primary recommendation:** Put the decision into one pure, table-tested gate function; feed it from a new lenient
heartbeat field (`kept_legacy`, list of device ids, omitted on overflow) and a shared keep predicate in `takeover.py`;
publish `migrate` before any owner action that can empty the topic; and turn the CR-01 observation script into a
three-variant pass/fail gate with the reverse case run as an owner-only restart.

## Research Question Answers

### Q1 (D-09): Does core MQTT 2026.9.4 keep other instances' registry rows when migrate precedes the empty clear?

**Status: CONFIRMED** for loaded rows, by source trace and by probe. [VERIFIED: core source at
`.venv/.../homeassistant/components/mqtt/` 2026.9.4, `uv run python -c 'import homeassistant.const as c; print(c.__version__)'`
printed `2026.9.4`]

Trace (device-based discovery topic `homeassistant/device/<id>/config`):

1. A migrate payload on a device topic is parsed by `_parse_device_payload`; `_async_process_discovery_migration`
   recognises it and the code returns `_generate_device_config(hass, object_id, node_id, migrate_discovery=True)`
   [VERIFIED: discovery.py:302]. That function builds one empty component config per hash in
   `mqtt_data.discovery_already_discovered` of that device [VERIFIED: discovery.py:245, :261 `for platform, discover_id in
   mqtt_data.discovery_already_discovered:`], each carrying `migrate_discovery = True`.
2. Each **loaded** entity receives it in `_async_discovery_callback`, sets `self._migrate_discovery`, and because the
   payload is empty schedules `_async_process_discovery_update_and_remove`, which calls `_cleanup_discovery_on_remove()`
   (drops the hash from `discovery_already_discovered`) and then branches [VERIFIED: entity.py:1077-1082]:
   ```
   if self._migrate_discovery is None:
       # Unload and cleanup registry
       await self._async_remove_state_and_registry_entry()
   else:
       # Only unload the entity
       await self.async_remove(force_remove=True)
   ```
3. The following empty device payload (owner's explicit clear or core's hook clear) runs `_generate_device_config` again;
   the hashes are gone, so it returns an empty payload and core logs `"No device components to cleanup for %s, node_id
   '%s'"` [VERIFIED: discovery.py:291] and returns. Nothing is deleted. (The 09.1 bench logs show the same line on both
   instances after the rows were already gone [VERIFIED: 09.1-evidence/fix2/cr01-observation/findings.txt].)
4. Back-to-back delivery (no event-loop turn between the two messages) also keeps the row: the hash is still pending,
   the empty component payload is queued, and when it is processed the hash is no longer "already discovered" and not in
   `discovery_discovered_and_disabled`, so nothing happens.

Disabled rows are not touched by either message: a row core discovers while disabled aborts its add; `add_to_platform_abort`
registers the clear-on-remove hook and calls `stop_discovery_updates`, so its hash is never "already discovered"
[VERIFIED: entity.py:1234-1247, :1239 `self._registry_hooks[discovery_hash] = (`]. The hook publishes the empty retained
payload when the row leaves the registry [VERIFIED: entity.py:770-778, :778 `await async_remove_discovery_payload(hass,
discovery_data)`].

Probe results this session (throwaway tests, run inside `tests/` and deleted again; `git status --short tests/` clean
afterwards) [VERIFIED: pytest run, 3 passed]:

| Probe | Result |
|-------|--------|
| Renamed, loaded legacy button; migrate and empty fired back to back | registry row kept with name `Kept`; state `None` (unloaded) |
| Same, then the legacy payload delivered live again | the row is loaded again (state present) |
| Renamed loaded button + integration-disabled switch rediscovered in this run (hook held); migrate, then remove the switch (hook publishes, looped back) | 1 falsy publish by the hook; renamed row kept with its name |
| Same without migrate (negative control) | renamed row deleted (the CR-01 mechanism in one `hass`) |

Existing pinned contract tests: `test_plain_clear_on_a_loaded_entity_deletes_the_registry_entry` and
`test_migrate_then_clear_keeps_the_registry_entry` in `tests/test_takeover.py` (both pass on 2026.9.4) [VERIFIED: pytest
run, 3 passed with `test_user_disabled_entity_survives_the_migrate`]. They are the version guard: a PHACC/HA bump that
changes the behavior turns them red.

**Side effects of the migrate on peers (answer to the second half of Q1):**
- Every **loaded** legacy entity of that device on every connected instance is **unloaded** (`async_remove(force_remove=True)`):
  it disappears from the state machine for the rest of that instance's run; the registry row with all customizations stays.
  It is loaded again only when a non-empty discovery payload for the topic arrives (probe 2). After a clear that never
  happens in the same run; at the peer's next start a 1.0.1 native mirror's takeover moves such a row to native, a
  legacy-path instance shows it as not provided.
- Core logs one INFO line per entity ("Rollback to MQTT platform discovery schema started ...", device discovery case).
- Disabled rows and their hooks are untouched (probe 3: the hook was still registered after the migrate).
- The migrate is non-retained, so instances that are offline never see it, and a later subscriber never replays it
  [VERIFIED: discovery.py (integration) :312-323 docstring and `retain=False`].
- Consequence for the design: **never publish migrate while the gate blocks** — it would unload the kept rows (the local
  ones too: `test_the_catch_keeps_an_enabled_customized_button_next_to_a_disabled_twin_on_legacy_content` asserts the kept
  button keeps its state).

Ordering on the wire: MQTT 3.1.1 requires a server to deliver PUBLISH packets of one client "for the same Topic and QoS
in the order that they were received" [CITED: docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html §4.6,
MQTT-4.6.0-6]. The integration publishes migrate and its explicit clear at QoS 1 (`mqtt_gateway.async_publish(..., qos: int
= 1)`) [VERIFIED: mqtt_gateway.py:98], and core's `async_publish` awaits the broker acknowledgement
(`_async_wait_for_mid_or_raise`) [VERIFIED: client.py:1484] before the integration continues. Core's own hook clear is
QoS 0, so the spec guarantee does not formally cover migrate (QoS 1) followed by the hook clear (QoS 0); in practice the
migrate was acknowledged (received and routed) before the hook clear is even sent. [ASSUMED: mosquitto routes a message
to subscriber queues before it sends the PUBACK, so the order holds across QoS levels]

### Q2: Heartbeat field — build, publish, parse, roster, and the kept set

**Current code** [VERIFIED: presence.py read this session]:
- Payload built in `async_publish_heartbeat` (presence.py:340-359), keys `instance_id`, `name`, `version`, `devices`,
  `session`, and `NATIVE_KEY: NATIVE_VALUE`; published `retain=False`, `qos=HEARTBEAT_QOS` (`HEARTBEAT_QOS = 0`,
  presence.py:54). `NATIVE_KEY: Final = "entities"`, `NATIVE_VALUE: Final = "native"` [VERIFIED: document.py:87-88].
- Published at start right after the online availability (`await self.presence.async_publish_heartbeat()`, manager.py:815),
  every tick under the manager lock (`_async_tick`, presence.py:370-375; `HEARTBEAT_INTERVAL_SECONDS: Final = 30.0`,
  const.py:161), and in `_async_republish` (manager.py:1379).
- Parse: `_heartbeat_object` checks `within_size_cap` (`MAX_BROKER_MESSAGE_BYTES: Final = 1024`, const.py:170, characters
  and UTF-8 bytes), topic id == payload id, valid device-id shape; `parse_heartbeat` requires valid `name`, `version`,
  `devices`, `session` and reads `native=data.get(NATIVE_KEY) == NATIVE_VALUE` leniently (presence.py:120-139).
- Roster: one `Roster` per `PresenceManager`, which is created per `Manager` (manager.py:523), which is created per entry
  setup (`__init__.py:40`). Every roster row is therefore "heard since this start"; a reconnect keeps rows and restarts the
  listening time (presence.py:320-329). Online = fresh (`<= HEARTBEAT_OFFLINE_SECONDS`, `90.0`, const.py:162) and the
  retained availability is not `offline` (presence.py:176-180). `saturated()` covers a dropped peer at
  `MAX_TRACKED_INSTANCES: Final = 256` (const.py:157). `blocking_peers()` shows the established pattern for "announced
  online via retained availability but no heartbeat row" (presence.py:505-524).

**Recommended field design (Claude's discretion):**

| Aspect | Recommendation | Why |
|--------|----------------|-----|
| Key | `"kept_legacy"` [ASSUMED name] | Short, says what it is; not a document key, so define it in `presence.py` (or `const.py`), not `document.py` |
| Value | JSON list of device ids, sorted, unique; `[]` when nothing is kept | `[]` must mean "known, nothing kept", distinct from a missing field (UNKNOWN) |
| Cap | `MAX_HEARTBEAT_KEPT_DEVICES` (16) [ASSUMED value] for receiver validation **plus** a size check of the whole payload on the sender | A fixed count cannot guarantee the 1024-byte cap: with a 64-character emoji instance name the existing payload is already 946 bytes (room for one UUID); with an ASCII name 16 UUIDs give 899 bytes, 12 ids of 64 characters give 1075 bytes [VERIFIED: computed this session with `json.dumps` default `ensure_ascii=True` and `invalid_name`] |
| Overflow | Omit the key entirely (identical to a v1.0.0 heartbeat, peers read UNKNOWN and keep everything) and log one count-only warning per start | Fail-safe and one code path; never drop the heartbeat itself |
| Receiver validation | Field present and a list, length `<= cap`, every item a `str` passing `is_valid_device_id` (`_DEVICE_ID = re.compile(r"[A-Za-z0-9_-]{1,64}")`, topics.py:11), no duplicates → `frozenset`; anything else → `None` (UNKNOWN) **while the heartbeat itself stays valid** | If a bad field invalidated the whole heartbeat, a previously heard peer would go stale after 90 s and count as **offline**, which does **not** block — the unsafe direction. This mirrors the lenient `native` read |
| Dataclass | `Heartbeat.kept_legacy: frozenset[str] \| None = None` | Default keeps `test_parse_heartbeat_accepts_a_valid_message` (equality without the field) green |
| Logs | No field value, ever; counts only | T-04-14 |
| Diagnostics/sensor rows | Do not add the list to `Roster.rows()` / sensor attributes | Avoids churn in hub-entity and diagnostics tests; not needed by the gate |

**The kept set (sender side).** Compute it at every publish from the entity registry, over the held ids
(`{*self.devices, *self.mirrors}`), with one shared predicate so it can never drift from `remove_replay_twins`:

- Extract the keep test of `remove_replay_twins` (takeover.py:250-257) into a helper used by both:
  ```
  twin is None
  or twin.config_entry_id != entry_id
  or _is_customized(legacy)
  or _carries_the_identity(legacy, twin)
  ```
  and add `takeover.keeps_enabled_legacy_row(hass, entry_id, device_id, *, mqtt_entry_id) -> bool` = "some legacy entry
  of the core MQTT device of the id passes the keep test and has `disabled_by is None`" (exactly `keeps_an_enabled_row`).
- **Also list every held id that is not native this run and has a legacy device** (`not self.is_native(device_id)`, which
  covers a legacy-path instance, a legacy mirror and a device in `_legacy_this_run` after a deferred takeover). For a
  deferred native mirror the legacy rows have native twins and would fail the keep test, yet they are the live entities of
  this run. [VERIFIED: manager.py `_async_defer_takeover` adds the id to `_legacy_this_run`; `_native_device_ids` excludes
  deferred devices]
- Use the registry's **enabled** state, not `entity_sources` (loaded). That is a superset of "enabled, loaded" (D-01),
  which is the safe direction, and it is what makes the **first** heartbeat (manager.py:815, after the takeover and before
  core's replay loads anything) correct: the customized row is in the registry from the previous run.
- `gateway.mqtt_entry_id()` None → no MQTT entry → no legacy rows → `[]`.

| `KEPT` | an online roster peer's `kept_legacy` contains X | keep, no re-arm |
| `UNKNOWN` | an online roster peer has `kept_legacy is None` (older version, overflow, invalid), or `roster.saturated()` | keep, no re-arm |
| `UNHEARD` | an id in `sync.online_instance_ids()` (retained availability `online`) has no roster row | keep **and** re-arm (D-04) |
| `CLEAR` | none of the above (offline and stale rows are ignored; no online peer is CLEAR too) | may empty |

Precedence `KEPT > UNKNOWN > UNHEARD > CLEAR`, so a re-arm happens only when "not heard yet" is the only blocker (D-04).
Unlike `blocking_peers()`, do **not** drop UNHEARD peers after 90 s of listening: the catch ends long before that, and a
peer whose heartbeats are malformed must never turn into "offline" through silence.

### Q3 (D-04): Does the existing re-arm cover one heartbeat interval?

**No.** [VERIFIED: manager.py:943-953, takeover.py:43-47, sync.py:95, sync.py:404-417]
- `REPLAY_QUIET_SECONDS = 5.0`, `REPLAY_CATCH_RETRIES = 5`, `REPLAY_RETRY_MIN_SECONDS = 1.0` (takeover.py:43, :46, :47).
- The re-arm needs `(wait := self.sync.discovery_settles_in()) is not None` and waits `max(wait,
  takeover.REPLAY_RETRY_MIN_SECONDS)`. `discovery_settles_in()` returns at most `DISCOVERY_SETTLE_GRACE_SECONDS = 2.0`
  and returns `None` once the settle plus grace has passed. The catch first runs 5 s after start, normally after that point,
  so it re-arms zero times; the theoretical horizon is 5 x 2 s = 10 s, far short of 30 s.

**Minimal change (keeps the bound's meaning, adds no timeout constant):** give the re-arm a second reason. When at least
one owned LEGACY device is blocked only by `UNHEARD`, re-arm with
`max(HEARTBEAT_INTERVAL_SECONDS + EXPIRY_MARGIN_SECONDS - presence.listening_seconds(), REPLAY_RETRY_MIN_SECONDS)`
(`EXPIRY_MARGIN_SECONDS = 1.0`, presence.py:56; expose `listening_seconds()` on `PresenceManager`), sharing the same
`_replay_catch_retries` counter and `REPLAY_CATCH_RETRIES` bound. Combined wait when both reasons apply: the larger one.
Timeline: catch at about 5 s, one re-arm to about 31 s of listening (every 30 s-ticking peer must have been heard by then
unless a QoS 0 heartbeat was lost), at most four 1 s retries after that, then keep with a count-only INFO line. This ends
about 35 s after the presence start, inside the 90 s `SETTLE_SECONDS` of `check-uat02.sh` [VERIFIED:
~/ha-test/bin/check-uat02.sh:31].

Optional, not required: an early trigger from `on_roster_changed` when a heartbeat of an awaited peer arrives (faster
common case). Keep it out unless the plan has room; the time-based path is deterministic and easy to test.

### Q4 (D-05/D-06): Both call sites, role and peer gate, the follower's LEGACY to EMPTY re-arm

**Role.** Owner = `device_id in self.devices and device_id not in self.sync.transferred_away` (the guard already used at
manager.py:923-924). Everything else (a mirror, or an owned id another instance adopted) is a follower.

**Call site 1, the catch (`_async_replay_catch`, manager.py:889; removal at :913).** Pass a per-device permission, not the

**Call site 2, the takeover path (`_async_native_takeover`, removal at manager.py:1152).** It already passes no content, so

**Follower LEGACY to EMPTY (D-06), recommended: a sync-side callback.**

### Q5: Does the takeover-path clear (`_async_finish_takeover`, manager.py:1194-1211) need the peer gate?

**Recommendation: no peer gate; add a fresh migrate immediately before the clear instead.**
- On that path the migrate goes out for every pending owned device before the registry takeover (manager.py:1135-1142),
  so the empty payload that follows unloads, not deletes, peer rows (Q1). The D-02 invariant ("no kept row is deleted on
  any instance") holds through the migrate. Gating it would block the owner's cutover clear whenever a peer is still on
  the legacy path (that peer lists X by definition), which changes the Phase 5 migration protocol and its tests.
- Gap found: the migrate is sent once, before `async_take_over`, which can wait up to `TAKEOVER_UNLOAD_TIMEOUT = 10.0`
  (takeover.py:39) plus the registry flush. A peer that (re)starts in that window loads its rows again and the later clear
  deletes them. And `_async_retry_unconfirmed_clears` (manager.py:1381-1396, run by `_async_republish`, e.g. after a
  reconnect) calls `_async_finish_takeover` with no migrate at all in that run. Publishing the migrate inside
  `_async_finish_takeover` right before `async_clear_device` closes both windows at the cost of one non-retained message.
- Out of scope by design: the device-deletion clear (`_async_clear_discovery_topics`, manager.py:404-415). Deleting a
  device is meant to remove it on every instance (D-16 of an earlier phase: the empty config payload is the tombstone).

### Pattern 1: Pure gate, impure inputs
**What:** All decisions in one function without `hass`; inputs are gathered by the manager, outputs applied by it.
**When:** Every place that can make the shared topic go empty (catch removal, catch clear).
**Example (skeleton, names are recommendations):**
```python
# Source: derived from manager.py:889-960 and takeover.py:209-286 (this repo)
class PeerKeep(StrEnum):
    CLEAR = "clear"
    UNHEARD = "unheard"
    UNKNOWN = "unknown"
    KEPT = "kept"


@dataclass(frozen=True, slots=True)
class TopicVerdict:
    remove_disabled: bool  # an integration-disabled twin may go (core's hook may clear the topic)
    may_clear: bool  # the owner may publish the explicit clear (still needs: no local legacy device left)
    rearm: bool  # blocked only because a peer was not heard yet (D-04)


def shared_topic_verdict(*, owner: bool, content: DiscoveryContent, local_keeps: bool, peers: PeerKeep) -> TopicVerdict:
    if content is DiscoveryContent.EMPTY:
        return TopicVerdict(remove_disabled=True, may_clear=False, rearm=False)
    if content is not DiscoveryContent.LEGACY or not owner or local_keeps:
        return TopicVerdict(remove_disabled=False, may_clear=False, rearm=False)
    if peers is PeerKeep.CLEAR:
        return TopicVerdict(remove_disabled=True, may_clear=True, rearm=False)
    return TopicVerdict(remove_disabled=False, may_clear=False, rearm=peers is PeerKeep.UNHEARD)
```

### Pattern 2: Lenient optional wire field
**What:** A new heartbeat key that never invalidates the heartbeat; anything not exactly valid reads as UNKNOWN.
```python
# Source: modeled on presence.py:120-139 (native flag read)
def _kept_legacy(value: object) -> frozenset[str] | None:
    if not isinstance(value, list) or len(value) > MAX_HEARTBEAT_KEPT_DEVICES:
        return None
    if not all(isinstance(item, str) and is_valid_device_id(item) for item in value):
        return None
    kept = frozenset(value)
    return kept if len(kept) == len(value) else None
```
Sender: build the payload with the sorted list; if the list is over the cap or `not within_size_cap(payload)`, rebuild
without the key and warn once per start with a count only.

### Anti-Patterns to Avoid
- **Migrate while the gate blocks:** unloads the kept rows on every instance, the local one included.
- **Rejecting the whole heartbeat for a bad field:** the peer ages into "offline" after 90 s and stops blocking.
- **Gating on `entity_sources` (loaded) for the kept set:** the first heartbeat runs before core's replay; the row is not
  loaded yet and would be missed.
- **Re-arming on UNKNOWN peers (older version):** wastes the bound on something that cannot change in this run.
- **Comparing `_listening_since` across a swapped test clock** (see Q6).
- **Logging the field or the device ids from the broker** (T-04-14).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Keep peers' rows when the topic empties | A custom "unload" broadcast or deleting/restoring registry rows | Core's `migrate_discovery` payload (`DiscoveryPublisher.async_publish_migrate`) | Core already unloads and keeps the registry; pinned by existing contract tests |
| Peer liveness | A new timeout or roster | `Roster` freshness + `sync.instance_status` | Same semantics as cutover and owner-offline logic |
| The keep rule for the heartbeat | A second copy of the twin/identity rules | One predicate shared with `remove_replay_twins` | Drift between announce and act re-opens CR-01 |
| Waiting for peers | A new timer subsystem | The existing catch re-arm and its retry counter | D-04 |
| Test peers | A two-`hass` harness | `heartbeat_payload` + `async_fire_mqtt_message` + `_loop_back_discovery` | D-12 |

**Key insight:** every row deletion on a peer happens in core MQTT on that peer; the only levers are what the peer
announces and the order of messages on the shared topic.

## Common Pitfalls

### Pitfall 1: A peer that is still starting
**What goes wrong:** At a simultaneous restart, a peer's core MQTT loads legacy rows from the retained payload before its
integration publishes availability `online`; its retained availability still says `offline`, so the gate ignores it.
**Why:** D-02 treats offline peers as having nothing loaded; that is false for the seconds between core's subscribe and the
integration's start.
**How to avoid:** the migrate before every emptying action (D-09) turns any deletion into an unload with the registry
kept. Do not try to gate on it.
**Warning signs:** "Rollback to MQTT platform discovery schema" INFO lines on the peer, and on its next start a takeover
that moves rows ("keeps its MQTT device" lines). Record peer availability timing in the bench evidence.

### Pitfall 2: A deferred mirror's live legacy rows not announced
**What goes wrong:** A takeover deferred because rows stay loaded (`_legacy_this_run`) runs on legacy entities that have
native twins; the keep predicate alone does not list them.
**How to avoid:** list every held id that is not native this run and has a legacy device (Q2).

### Pitfall 3: Heartbeat size
**What goes wrong:** A long non-ASCII instance name plus a list overflows 1024 bytes; peers drop the whole heartbeat.
**How to avoid:** size check on the sender, omit the key on overflow; test with an emoji name.

### Pitfall 4: The bench timing budget
**What goes wrong:** The owner's clear can wait until about 31 s of listening; the follower's EMPTY re-arm adds about 1 s.
`check-uat02.sh` waits `SETTLE_SECONDS=90` after both ports answer, so it fits, but a slower peer wait would not.
**How to avoid:** keep the peer re-arm target at one heartbeat interval plus margin; never add waits that exceed ~60 s.

### Pitfall 5: Integration reload is not an HA restart
**What goes wrong:** Tests use `_restart` (entry unload/setup); core MQTT's `discovery_already_discovered`,
`discovery_registry_hooks` and the "saw a retained message on this topic" state survive it. Tests must reproduce hooks
explicitly (rediscover the disabled row live) and hand retained payloads to the new subscriptions themselves.

### Pitfall 6: Phase branch vs `main`
**What goes wrong:** The work runs on `gsd/phase-09.2-...` (2 `.planning` commits ahead of `main`, `main` is an ancestor).
FIX is defined on `main` (`git log -1 main -- . ':(exclude).planning'`, today `dc6513c0b4ac54d68fbf5207161508c18cc2a5b6`),
and the 09.1 bench plans required `git symbolic-ref --short HEAD` = `main`.
**How to avoid:** the plan must fast-forward `main` to the fix (or execute on `main` as 09.1 did) before preflight; CI on
`main` push or `workflow_dispatch` with `headSha == FIX`.

### Pitfall 7: A missed heartbeat
**What goes wrong:** Heartbeats are QoS 0; one lost message leaves a peer UNHEARD until the bound ends; the owner keeps
for this start (fail-safe), and UAT-02 then fails E1 on ha-b.
**How to avoid:** accept (fail-safe); if a UAT-02 run fails this way, the logs show the new count-only "not heard" line,
which distinguishes it from a product defect. Consider the optional early trigger (Q3) if it happens.
