## Phase Goal

**As a** Home Assistant user, **I want to** create Select devices whose options each run their own actions, **so that** multi-state MQTT devices drive my setup predictably.

This plan's slice: predictable execution. The execution engine moves from one Script per trigger plus a lock to one Script per device with a run mode, which makes rapid changes queue or restart the way the user configured.

<objective>
Replace the per-trigger Scripts and the per-device lock of the runner with one Script per device (mode `queued` for serial, `restart` for restart), dispatching on the trigger key, with a fixed queue bound and correct handling of dropped, cancelled and superseded runs.

Purpose: DEV-06 needs restart to cancel across triggers and serial to order across triggers. Per-trigger Scripts cannot do either (each Script owns its own queue and run list), and hand-rolled cancellation re-implements HA's race handling. One combined Script gets the native, tested semantics. The manager and its callers stay untouched because plan 02-01 already fixed the runner API.

Output: reworked `runner.py`, the `SERIAL_QUEUE_LIMIT` constant, `tests/test_runner_modes.py`. Implements D-10, D-11, D-12.
</objective>

## Assumptions carried from RESEARCH.md (visible, not silent)

- **A5** A change to a trigger without actions does not cancel a running `restart` run, because nothing is enqueued for it. Users who expect "latest state wins" to cancel anyway do not get that; a test pins the behavior so a later change is a deliberate decision.
- **A10** A small per-device enqueue generation counter keeps a superseded run that returns normally between steps from clearing the failure issue. Risk if wrong: rare false clear or false keep in restart mode.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| State topic to runner | A party with broker write access can produce rapid changes that enqueue runs |
| User-authored actions to the combined Script | Action text is executed with full local service access; only the dispatch condition is generated |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Denial of service | unbounded serial queue from rapid state changes | medium | mitigate | Script mode queued with `max_runs=SERIAL_QUEUE_LIMIT` (10) and `max_exceeded="WARNING"`: runs beyond the bound are dropped and logged; the per-device circuit breaker (plan 02-04) stops sustained loops |
| T-02-06 | Repudiation | a dropped, cancelled or superseded run clears or fakes the failure state | low | mitigate | The issue is cleared only by a run that returned a result and is the latest enqueue; a cancelled run is never treated as success or failure; covered by three tests in Task 2 |
| T-02-07 | Tampering | user text inside the generated choose conditions | medium | mitigate | Conditions compare the run variable with the sha256-derived hex key only; option names and StateValues never enter a template of the Script; action lists are validated per trigger before assembly |
| T-02-SC | Tampering | package installs | low | accept | This plan installs nothing; no dependency is added |
</threat_model>
