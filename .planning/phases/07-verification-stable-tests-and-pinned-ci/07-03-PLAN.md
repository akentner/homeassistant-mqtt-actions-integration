## Phase Goal

The v1.0.1 build is verifiably sound: the full suite passes three consecutive runs, and CI and Validate are green on a pinned runner (QLT-02, QLT-03). Plans 07-01 and 07-02 changed the code; this plan proves it on the combined head, locally first and then on GitHub.

<objective>
Run the full suite three times in a row locally, publish the branch after an explicit owner decision, and run CI three times and Validate once through `workflow_dispatch` on the pushed head (D-09). Record every result in the proof ledger `07-PROOF.md`.

Purpose: the three-run proof only means something on the head that contains both the pin and the test fix, and the CI proof only means something when the runs name the same commit and the pinned image. Local Mosquitto is 2.1.2 and CI installs 2.0.18 from the Ubuntu 24.04 archive, so a green local broker tier does not prove the CI one; both are shown.

Output: the ledger sections "Local three-run proof" and "CI proof on ubuntu-24.04", the pushed branch, three green dispatch runs of CI and one of Validate.
</objective>

## Decisions this plan implements (visible, not silent)

- **D-09:** three consecutive full-suite runs, shown locally (three runs with Mosquitto) and in CI (three consecutive green runs on the pinned runner through `workflow_dispatch`; the push of the branch also starts push-event runs, which are recorded but not counted).
- **Local runs match CI's serial behavior:** one pytest invocation over all three tiers without xdist, with `MQTT_ACTIONS_REQUIRE_BROKER=1` so a missing broker fails instead of skipping (research pitfall 5; the CI broker job sets the same variable). The expected shape is no skipped and no failed tests; the count is read from the run, not assumed (plan 07-01 adds tests, so the research baseline of 1480 no longer applies).
- **Merge order and push (planner decision on research open question 3):** the Phase 6 branch is local only and 29 commits ahead of `origin/main`; `workflow_dispatch` and the later tag run need the commits on origin; `branching_strategy` is `phase` and Phase 7 work already sits on the Phase 6 branch (the executor never switches branches). Task 2 is an explicit `checkpoint:decision`, not an assumption. The earlier phases were pushed as `gsd/phase-NN-*` branches and merged through a pull request, which is the recommended option. Merging into `main` is not part of this plan; it happens at ship time.
- **Dispatch needs the workflow on the default branch (research pitfall 8):** `ci.yml` and `validate.yml` already exist on `main`, so `gh workflow run ... --ref REMOTE_BRANCH` works once the branch is on origin.
- **REMOTE_BRANCH:** it is `gsd/phase-06-native-entity-residual-fixes` unless the decision of Task 2 names another remote branch. Pushes use `HEAD:refs/heads/REMOTE_BRANCH`, so no command depends on which local branch or worktree the executor runs in (the executor never switches branches). Verify commands read `REMOTE_BRANCH` from the environment and default to the phase branch name.
- **No retry to get three greens (D-05):** one failed run stops the plan; the cause is diagnosed first and the count restarts after the fix.
