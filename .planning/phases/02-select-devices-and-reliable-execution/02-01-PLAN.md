## Phase Goal

**As a** Home Assistant user, **I want to** create Select devices whose options each run their own actions, **so that** multi-state MQTT devices drive my setup predictably.

This plan's slice: the runtime of a Select device. A Select subentry (created from stored data here, from the UI flow in plan 02-05) subscribes to its state topic, maps the payload to an option, runs only that option's actions, and is published to Home Assistant as a select entity. Run modes (02-02), test buttons (02-03), the circuit breaker (02-04) and the option editor flow (02-05) build on it.

<objective>
Generalize the Switch-only runtime into a device model that describes both kinds, run a Select device end to end, publish it as a select entity with a hostile-string-safe mapping, and make unknown payloads and removed values behave per D-02, D-08 and D-09.

Purpose: the whole phase rests on one pure `DeviceSpec` per subentry (kind, accepted payload map, triggers keyed by a stable `trigger_key`). Doing the generalization first, behind a tracer that keeps all Phase 1 tests green, means run modes, buttons, breaker and flow only add to a proven path.

Identity model (assumption-delta answer): `device_id` (the subentry UUID, unchanged) stays the only device identity, entity unique_id and topic segment. Inside a device every trigger (Switch ON and OFF, each Select option) is identified by `trigger_key = sha256(lowercased StateValue)[:12]`. It is derived, never stored, and StateValue is immutable (D-03), so the key is stable across renames and adds nothing to the future central-config document.

Output: `model.py`, generalized `state.py`, `runner.py`, `manager.py` and `discovery.py`, factories for Select and extended Switch subentries in `tests/conftest.py`, and the tests named in the tasks. Implements D-02, D-05, D-06, D-07, D-08, D-09, D-10.
</objective>

## Assumptions carried from RESEARCH.md (visible, not silent)

- **A11** A stored baseline that is not a StateValue of the device (for example after an option was removed) is sanitized to no baseline. Risk if wrong: different edge behavior after an option is removed and re-added; the next live message then acts as a first message (D-14 of Phase 1).
- **Open question 1 default** Renaming or removing the currently selected option leaves the HA select entity showing `unknown` until the next valid payload; the tracker and baseline behave as D-02 says, HA's entity cannot. No republish of `last_acted` is added. The behavior is pinned by a test here and documented for users in plan 02-05.

|----------|-------------|
| Broker to state subscription | Payload text and retain flag come from any party with write access to the state topic |
| Subentry data to discovery templates | Option names and StateValues are user-authored text that is embedded in templates evaluated by core MQTT |
| Store on disk to Manager | Persisted baselines and stored subentry data are read back at start |
