## Phase Goal

**As a** Home Assistant user, **I want to** create Select devices whose options each run their own actions, **so that** multi-state MQTT devices drive my setup predictably.

This plan's slice: the user interface. Everything the previous plans made possible through stored data (Select devices, run modes, breaker limits) becomes configurable in the Home Assistant dialog, in English and German.

<objective>
Build the Select subentry flow as a menu loop over an in-memory draft (settings, add, edit, remove with confirmation, done), add the run mode and breaker fields to the Switch and Select flows, validate everything through pure model functions, translate all strings, and document the behavior.

Purpose: DEV-03 and DEV-04 are user-facing requirements, and DEV-06 and STA-06 must be configurable per device (D-14). The menu loop is the only piece of this phase without an in-repo analog, and a menu cannot show validation errors, so the design keeps invalid states unreachable (Done hidden until two options exist, Remove hidden at two options) and validates in the form steps.

Output: `SelectSubentryFlow` and a shared base in `config_flow.py`, `validate_option` and `validate_breaker` in `model.py`, the translations, README updates and the tests named in the tasks. Implements D-01, D-02, D-03, D-04, D-05, D-10, D-14.
</objective>

## Assumptions and defaults carried from RESEARCH.md (visible, not silent)

- **A1** Count and length caps are needed; the values are constants: at most `MAX_OPTIONS` = 50 options and `MAX_TEXT_LENGTH` = 64 characters for StateValue and StateFriendlyName. The menu hides Add at the cap.
- **A6** StateValue and StateFriendlyName must be printable (`str.isprintable()`), which also rejects lone surrogates. Risk: legitimate exotic names are rejected; the rule lives in one function and is easy to relax. The model loader (plan 02-01) accepts anything UTF-8 encodable, so this is UI hygiene only.
- **A7** Breaker limits are 1..100 runs and 1..3600 seconds (`BREAKER_MAX_RUNS_LIMIT`, `BREAKER_WINDOW_LIMIT`).
- **Open question 1 default** Renaming or removing the currently selected option leaves the HA select entity at `unknown` until the next valid payload arrives; no republish of the baseline. The option edit step, the remove confirmation and the README say so in both languages.
- **Open question 2 default** A test button press fans out to every instance subscribed to the test topic (single instance in this release); the README names the test topic as a second trigger source for broker ACLs.
- **Open question 3 default** Existing Switch devices receive their two test buttons after the upgrade with no opt-out; the README says so.
- **A12** (from plan 02-04) A save that changes nothing does not release a tripped breaker; the README says "change the device or reload the integration".

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI form input to stored subentry data | User-typed names, values, actions and numbers become persisted configuration and later template and payload text |
| Stored option text to discovery and logs | Names are embedded in retained discovery, entity names, Repairs text and log lines |
| Flow instance to live subentry data | A flow that edits stored data in place would change live configuration without validation or an update listener call |
