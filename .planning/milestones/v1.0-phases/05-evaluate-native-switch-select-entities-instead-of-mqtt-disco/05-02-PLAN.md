## Phase Goal

Switch and select entities owned by the MQTT Actions config entry replace MQTT Discovery as the default way device entities are created; existing installations migrate automatically with entity ids, history and registry customizations intact. This plan builds the registry half of that migration as a pure, separately tested module.

<objective>
Implement `custom_components/mqtt_actions/takeover.py`: the fixed-order registry takeover of legacy core-MQTT entities into this integration's config entry and subentry, with the identity check, the bounded unload wait and the duplicate guard, proven against real core MQTT discovery (D-05, D-07, D-12).

Purpose: this is the one-way core of the migration. Keeping it a pure module without broker access makes every ordering rule and every edge testable on its own before plans 05-05 and 05-06 wire it into the setup and the cutover.

Output: `takeover.py` and its tests in `tests/test_takeover.py`. Nothing calls the module yet; no existing behavior changes.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions)

- **The wait is event-driven polling:** `TAKEOVER_UNLOAD_TIMEOUT` is 10 seconds and `TAKEOVER_RETRY_INTERVAL` 0.25 seconds, both module constants and both overridable per call so tests run in milliseconds. 10 seconds covers the broadcast round trip and mirrors the order of magnitude of core's own discovery cool-down (5 seconds).
- **DEFERRED is all-or-nothing:** if any legacy entity of the device is still loaded after the timeout, no entity and no device is moved. The caller leaves the device on the legacy path for this run and retries at the next setup.
- **The module does not publish:** the owner's migrate payload goes out before the call and its retained clear after it, both in the caller (plan 05-05). This keeps the broker order, which is a fixed rule of the phase, in one place.
- **Domains are limited to switch, select and button**, the three the legacy discovery payload creates.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker-supplied device id to the registry lookup | Mirror device ids come from foreign documents; a hostile id could steer the takeover at an unrelated entity |
| Takeover steps to the user's registry | A wrong step order silently destroys customizations, registry ids and device-based automations |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-5-01 | Tampering | A document whose device id equals the unique id of an unrelated MQTT entity makes a unique-id-only takeover steal it | high | mitigate | The device is found by the MQTT identifier `(mqtt, mqtt_actions_<id>)`; each entry must match platform, config entry, device, domain and unique-id shape (`is_legacy_entity`); `test_a_foreign_mqtt_entity_with_the_same_unique_id_is_left_alone` |
| T-5-08 | Tampering | Moving the device before the entities, or moving while an entity is loaded, deletes registry entries and loses customizations | high | mitigate | Fixed order entities, device, merge; nothing moves while any legacy entity is in `entity_sources` (DEFERRED, registry untouched); pinned by the plan 05-01 core tests and `test_take_over_defers_and_moves_nothing_while_an_entity_stays_loaded` |
| T-5-09 | Tampering | A duplicate registry key is created silently because core does not guard it | medium | mitigate | `async_get_entity_id` check before every move; the legacy duplicate is deleted instead; `test_an_existing_native_entry_is_never_duplicated` |
| T-5-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs nothing |
</threat_model>
