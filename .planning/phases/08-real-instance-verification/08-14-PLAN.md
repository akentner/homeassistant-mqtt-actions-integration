## Phase Goal

The re-run of UAT-04 is recorded in the ledger the way the first run was, and the traceability of UAT-01 to UAT-04 is current (ROADMAP Phase 8, success criteria 4 and 5).

<objective>
Record the outcome of plan 08-13 in `08-UAT.md`, and bring REQUIREMENTS.md, ROADMAP.md and `08-VALIDATION.md` in line.

Purpose: a pass is only as honest as the state it was observed on. A pass on a pruned registry must say so everywhere it is stated; a pass on the original tombstoned state with a guard build needs no qualifier. A FAIL is raised again with its new evidence. The ledger is written once, here, before any verifier runs (plan 08-15).

Output: block 4 (and, for a guard build, blocks 2, 3 and 9 as re-run) recorded, a resolved or failed Gaps entry, current Requirement verdicts, REQUIREMENTS.md and ROADMAP.md updated.
</objective>

Run `~/ha-test/bin/check-uat04-iso.sh disposition` first: a missing or invalid disposition (exit 2) FAILS this plan. The plan applies for all four dispositions and for both outcomes of the re-run; the wording differs by disposition (qualifier) and by outcome (pass or issue).

## Decisions this plan implements (visible, not silent)

- **D-05:** one ledger, one row per check; a re-run is recorded by hand like the first run (block, table row, evidence folder, `check-recorded.sh ID`).
- **D-07:** nothing is overridden; a FAIL stays an issue unless the owner records an override in their own name, which this plan never supplies.
- **D-08 (failure rule, which stands):** a failed check is a gap and is never turned into a pass.
- **D-03:** the checks that are not re-run after a guard build are listed with the reason and with the owner's recorded confirmation (UAT04-GAP-DISPOSITION).
- **Planner decisions (documented, not owner choices):** (1) the qualifier "passes only on a pruned registry state" is carried by the block note, the Requirement verdicts row, the Gaps resolution line and REQUIREMENTS.md, because a reader of any one of them must not read the pass stronger than the evidence; (2) the D-05 results table keeps the plain token because `check-recorded.sh` compares it with the block result exactly; (3) plan 08-15 reads the first token of the Requirement verdicts cell (an amendment of `check-final.sh` made there); (4) the first failing run stays in `uat-04` and is referenced from the block note, never overwritten.
