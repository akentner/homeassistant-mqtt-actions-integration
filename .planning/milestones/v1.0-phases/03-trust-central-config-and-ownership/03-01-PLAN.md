## Phase Goal

**As a** user with several HA instances, **I want** devices created on one instance to appear on the others once I approve them, **so that** every instance runs the actions locally.

This plan's slice: the published contract. An owner turns each of its devices into one retained, versioned, hash-stamped document that any other instance can read strictly and safely, and the repository gains the two-instance test harness every later plan builds on.

<objective>
Define and publish the central config document (D-12, D-13): pure `document.py` (build, canonical hash, strict parse, denylist walker), the config topic helpers, the owner publish path with persisted `rev` (D-15), and the Wave 0 seams (`IncomingMessage.topic`, `Manager(gateway=, store_key=)`, `tests/fake_broker.py`).

Purpose: SYN-01, SYN-04 and the validation half of TRU-03. Everything else in the phase reads or reacts to this contract, so it is fixed once, in one pure module, with a golden fixture that fails loudly when the wire format drifts.

Output: `document.py`, extended `topics.py`, `const.py`, `discovery.py`, `actions.py`, `mqtt_gateway.py`, `manager.py`, `tests/fake_broker.py` and the tests named in the tasks. Implements D-03, D-04, D-06, D-12, D-13, D-14 and the publish half of D-15.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Self-derived edge cases (no SPEC.md exists, the spec-less probe was not run):** the prohibitions above and the edge cases in the behavior lists were authored from RESEARCH and CONTEXT by the planner.
- **Wire details left to discretion by CONTEXT:** the key spelling (subentry data keys reused verbatim, plus `schema_version`, `device_id`, `owner`, `owner_name`, `rev`, `hash`, `kind`, `name`), the canonical-JSON/hash algorithm and the choice of two hashes (`content_hash` for apply-or-no-op, `actions_hash` for approval) are RESEARCH recommendations. They are pinned by a golden fixture test so any change is explicit.
- **No checkpoint for the one-way rating:** D-12 already records the user's choice and its one-way rating, so no `checkpoint:decision` re-asks it.
- **A2 tunables:** `MAX_DOCUMENT_BYTES = 256 KiB`. `MAX_ACTION_DEPTH = 32` counts container levels (list and dict nesting), not action steps; RESEARCH's "about 16" counted steps, and one nested `choose` costs about four container levels, so 32 keeps real automations valid while bounding hostile nesting.
- **A1 denylist policy (Open Question 2 default):** whole domains `shell_command`, `python_script`, `rest_command`, `command_line`, `hassio`, `backup`; exact `homeassistant.restart`, `homeassistant.stop`, `homeassistant.reload_all`, `homeassistant.reload_core_config`, `homeassistant.reload_config_entry`, `homeassistant.set_location`, `homeassistant.save_persistent_states`, `mqtt.publish`, `mqtt.dump`, `recorder.purge`, `recorder.purge_entities`. `notify`, `script` and `automation.trigger` stay allowed. This is a fixed constant (D-03) and a policy that needs the user's confirmation at review.
- **A5:** `run_on_startup` is part of `actions_hash`; run mode and breaker limits are not.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker to document parser | Any broker client with write access can put arbitrary bytes on a config topic |
| Owner to broker | Published documents contain the full action data in clear text |
| Document text to logs and Repairs text | Names and owner names are attacker-controlled and reach logs and markdown |

## STRIDE Threat Register

Threat IDs are unique within the phase; `T-03-SC` is the reserved exception.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `parse_document` hash handling | high | mitigate | The wire `hash` field is ignored; both hashes are recomputed from the received content (`test_parse_never_trusts_the_wire_hash`), so a forged hash can neither skip a change nor reuse an approval |
| T-03-02 | Denial of service | oversized or deeply nested documents | high | mitigate | `MAX_DOCUMENT_BYTES` checked in bytes before parsing, orjson-based parser, `MAX_ACTION_DEPTH` container cap, option count caps, every rejection typed and content-free |
| T-03-03 | Elevation of privilege | denied services inside a received action tree | high | mitigate | Pure walker (`analyze_actions`) reports denied and templated names with strip and lower normalization for plans 03-04 and 03-06 to enforce; the denylist is a fixed constant the user cannot edit (D-03) |
| T-03-04 | Information disclosure | action data readable by every broker subscriber | medium | accept | Documents must contain the actions to be mirrored; the README and ACL document (plan 03-07) tell users not to put secrets into actions and to restrict read access with the broker ACL |
| T-03-05 | Tampering | log and markdown injection through names and owner names | medium | mitigate | Printable and length rules at parse time, no payload or action content in any rejection message, `escape_markdown` for every name that reaches an issue or flow text |
| T-03-SC | Tampering | package installs | low | accept | This plan installs nothing; `manifest.json` requirements stay empty and the tests use packages already pinned through PHACC |
</threat_model>
