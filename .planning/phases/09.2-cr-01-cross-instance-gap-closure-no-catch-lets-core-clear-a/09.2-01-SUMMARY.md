# Phase 9.2 Plan 01: No catch lets the shared legacy topic go empty under a peer's kept row (Summary)

**One pure gate, `takeover.shared_topic_verdict`, now decides every catch action that can empty the shared core-prefix legacy topic. It takes the role, the content, the local keep, and what online peers announce in the new `kept_legacy` heartbeat field. Followers never remove integration-disabled twins on LEGACY content.**

## Accomplishments

- `takeover.py`:
  - Added `PeerKeep` (clear/unheard/unknown/kept), `TopicVerdict(remove_disabled, may_clear, rearm)` and the pure `shared_topic_verdict`.
  - Moved the keep test into `_is_kept`. `remove_replay_twins` and the new `keeps_enabled_legacy_row` both use it.
  - `remove_replay_twins` has a new keyword `may_empty_topic: bool = False`. On LEGACY content it removes an integration-disabled row only when this is True. On EMPTY content the row is always removed.
  - The D-08 filter line and the catch log text are byte-identical.
- `presence.py`:
  - Added `KEPT_LEGACY_KEY = "kept_legacy"`, `MAX_HEARTBEAT_KEPT_DEVICES = 16` and `Heartbeat.kept_legacy`.
  - `_kept_legacy` parses the field leniently: a bad field reads as None and the heartbeat stays valid.
  - Added `Roster.peer_keep_state(device_id, announced_online)` and `PresenceManager.peer_keep_state(device_id)`.
- `manager.py`:
  - Added `_topic_verdict`, plus `_ids_that_may_empty_the_topic`, which fails safe per id.
  - `_async_replay_catch` reads the MQTT entry, content and verdicts, then removes, with no await in between (WR-01).
  - After the flush, the explicit clear re-reads content and peer state and needs `may_clear` (D-10). It also needs that no local legacy device is left (D-08).
  - New count-only INFO line for owned LEGACY devices kept because of a peer.
  - The takeover-path call is unchanged: no content and no may-empty id, so D-05 holds there.

- **Files modified:** `custom_components/mqtt_actions/manager.py`
