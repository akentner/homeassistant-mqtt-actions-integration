## Summary

Scope: `git diff 7baec98..HEAD` for the 13 listed files. Fix commit: 681c587. I read core MQTT 2026.9.4 (`client.py`, `entity.py`, `discovery.py` in `.venv`) to check the settle signal and the clear-on-remove behaviour.

The new tests pass: 122 passed and 2 xfailed across `test_discovery_content`, `test_native_replay`, `test_takeover` and `test_export_guard_receiver`. Most of the design holds up:

- The classifier only accepts exact shapes. The shapes have not changed since v0.1.0.
- On every uncertain path, an unseen topic stays UNKNOWN.
- The verdict is read and the registry step runs in the same synchronous block.

**One defect is new and proven.** The D-02 path lets the catch remove a row that the integration disabled while the topic still holds the legacy payload. That removal fires core MQTT's clear-on-remove hook. Core then publishes an empty retained discovery, and that payload deletes every loaded legacy row of the device. This includes customized rows that the catch deliberately kept, on this instance and on every other one. So the D-08 guard in `_async_replay_catch`, which is meant to protect a kept row, is bypassed.

I reproduced this with a throwaway test in the scratchpad. It was not added to the repo. The test used the repo's own helpers, with `_loop_back_discovery` active:

- **Setup:** the integration had disabled the switch, and the user had renamed the test button.
- **Result:** after the catch, core published `None` retained on the device topic, and the renamed button was gone from the registry.
- **Control run:** the same scenario with the switch customized instead. Nothing was removed while disabled, nothing was cleared, and the renamed button survived.

There are also two robustness gaps. Each one can make the UAT-02 fix silently do nothing, but in the safe direction (rows are kept, never wiped):

- A qos mismatch can stop the settle signal from ever firing.
- The catch runs only once, so it can fire before the settle has finished.

Known residual, not reported again: `async_remove_mirror` does not call `sync.forget`.

## Critical Issues

### CR-01: Removing an integration-disabled twin on LEGACY content makes core delete the legacy rows that were kept on purpose (D-08 bypass)

**File:** `custom_components/mqtt_actions/takeover.py:244-250` (caller `custom_components/mqtt_actions/manager.py:905-925`)

**Issue:** When `content` is LEGACY, `remove_replay_twins` removes a row with `disabled_by is INTEGRATION`. Because the retained legacy payload is still on the topic, core discovered that row while it was disabled in this run. Core therefore holds the `async_clear_discovery_topic_if_entity_removed` hook (`homeassistant/components/mqtt/entity.py:771-778`).

Removing the row fires that hook. Core publishes an empty retained payload on the device topic. Every core MQTT instance on the broker then handles the empty device payload by calling `_async_remove_state_and_registry_entry` (`entity.py:1042-1056`) for each loaded component of the device. That deletes the registry entries of rows that `remove_replay_twins` kept on purpose:

- customized rows (`_is_customized`, WR-03)
- rows that carry the identity
- rows the user disabled stay, but every enabled kept row is deleted

On the owner, `_async_replay_catch` explicitly skips its own clear when a legacy row is kept (`takeover.legacy_device(...) is None` at `manager.py:920`, with the D-08 docstring "the empty payload would delete a loaded row that was kept on purpose"). Core has already sent that same empty payload, so the guard does nothing.

Concrete trigger: a replay recreates the device, the guard disables the switch, and the user renames a test button (or one row is otherwise kept and still enabled). At the next HA start the catch removes the switch, and the renamed button and its `entity_id`, which automations may use, are deleted. Reproduced as described in the Summary.

The existing tests miss this:

- `test_remove_replay_twins_keeps_a_customized_row_with_legacy_content` (`tests/test_takeover.py`) does not loop back core's publish. Its kept row is disabled, so it is not loaded.
- `test_the_owner_keeps_a_customized_duplicate_and_its_device_and_clears_nothing` (`tests/test_native_replay.py`) customizes the switch, so no integration-disabled row is ever removed.

**Fix:** Do not remove an integration-disabled row on LEGACY content while any other legacy row of the device stays. Decide the keeps first, then remove.

```python
candidates = list(_legacy_entries(hass, device, device_id, mqtt_entry_id))
kept_any = False
plan: list[tuple[er.RegistryEntry, bool]] = []  # (entry, disable_first)
for legacy in candidates:
    twin_id = entity_registry.async_get_entity_id(legacy.domain, DOMAIN, legacy.unique_id)
    twin = entity_registry.entities.get(twin_id) if twin_id else None
    if (
        twin is None
        or twin.config_entry_id != entry_id
        or _is_customized(legacy)
        or _carries_the_identity(legacy, twin)
    ):
        kept_any = True
        continue
    if legacy.disabled_by is None:
        plan.append((legacy, True))
    elif legacy.disabled_by is er.RegistryEntryDisabler.INTEGRATION and content in REMOVABLE_DISABLED_CONTENT:
        plan.append((legacy, False))
    else:
        kept_any = True
if kept_any and content is DiscoveryContent.LEGACY:
    # Core holds a clear-on-remove hook for a row it discovered disabled; its clear would delete the kept rows (D-08)
    plan = [(legacy, first) for legacy, first in plan if first]
for legacy, disable_first in plan:
    if disable_first:
        entity_registry.async_update_entity(legacy.entity_id, disabled_by=er.RegistryEntryDisabler.INTEGRATION)
    entity_registry.async_remove(legacy.entity_id)
```

Also add a regression test that uses `_loop_back_discovery`. In it, a renamed, enabled test button sits next to an integration-disabled switch that core rediscovered while disabled. Assert that the button survives the catch.

## Warnings

### WR-01: The settle watch only matches qos 1, so a core discovery qos of 2 means the settle never fires and the fix stops working

**File:** `custom_components/mqtt_actions/sync.py:210-217`, `custom_components/mqtt_actions/mqtt_gateway.py:63-79`

**Issue:** Core sends `MQTT_PROCESSED_SUBSCRIPTIONS` with `(topic, max_qos)`, where `max_qos` is the highest qos of all subscribers to that filter string (`client.py:953-957`). Core MQTT discovery subscribes to the same string, `{prefix}/device/+/config`, at the user's **discovery qos** option (MQTT options flow, `config_flow.py:4506`; `discovery.py:605`).

If the user sets discovery qos to 2, the signal reads `(topic, 2)`, and `_sync_mqtt_subscribe` never matches the `(topic, 1)` watch. As a result:

- `_discovery_settled_at` stays `None` for good.
- No unseen topic is ever EMPTY, so the null-tombstone case of UAT-02 (`test_a_disabled_leftover_is_removed_at_a_start_with_an_empty_topic`) never heals on that installation.
- The "next start checks again" INFO line repeats at every start.

The same happens if any other integration subscribes to that filter at qos 2. The literal `1` also silently copies the gateway default of `async_subscribe`.

**Fix:** Our subscription is qos 1, so the filter's max qos is always 1 or 2. Watch both and treat either as the settle:

```python
topic = discovery_wildcard(self._discovery_prefix)
for qos in (1, 2):
    self._unsubscribers.append(manager.gateway.async_on_subscribed(topic, qos, self._on_discovery_settled))
```

Alternatively, pass an explicit qos constant to both the subscribe and the watch, and add a test that runs with core's discovery qos set to 2.

### WR-02: The catch runs once and can fire before the settle has finished, so the fix may never apply

**File:** `custom_components/mqtt_actions/manager.py:868-885`, `custom_components/mqtt_actions/manager.py:906-908`

**Issue:** `_arm_replay_catch` runs once per start, `REPLAY_QUIET_SECONDS` (5 s) after `async_start` returns. An unseen topic only becomes EMPTY after two waits:

- the SUBACK of the discovery wildcard, and
- `DISCOVERY_SETTLE_GRACE_SECONDS` (2 s) after it.

Core subscribes wildcard filters one at a time and waits for each SUBACK (`client.py:1101-1122`). At HA boot, our filter sits in the same pending batch as roughly 60 discovery wildcards from core, plus those of every other MQTT integration. Each costs one broker round trip, and over Tailscale that is tens of milliseconds. With a 0.5 s initial cooldown on top, the settle plus grace can easily end after the catch.

The catch then reads UNKNOWN, keeps the twin and logs "the next start checks again". Nothing re-arms it, and the next start has the same timing, so on a slow or remote broker the leftover may never be removed. This is safe, because nothing is wiped, but the phase goal fails silently.

**Fix:** When the settle is unset or still inside its grace, have the catch re-arm itself for the remaining time instead of deciding on UNKNOWN. Cap the retries, for example at 3. One option is to expose `sync.discovery_settles_in() -> float | None` and, in `_async_replay_catch`:

```python
if (wait := self.sync.discovery_settles_in()) and self._replay_catch_retries < MAX_RETRIES:
    self._replay_catch_retries += 1
    self._cancel_replay_catch = async_call_later(self._hass, wait, self._on_replay_catch_due)
    return
```

## Info

### IN-01: Owned ids skip the scope rule, so they can read as EMPTY after their retained message was dropped

**File:** `custom_components/mqtt_actions/sync.py:400-419`, `custom_components/mqtt_actions/sync.py:792-800`

**Issue:** For mirrors, `discovery_content` only infers EMPTY if the id was held when the subscription was made (`_discovery_scope`). For owned ids it uses `subentry_id_of` at call time.

`_holds` drops discovery messages for ids that are not held when the message arrives. So consider an owned subentry that appeared after the subscription, for example by adopting a mirror that was created after the subscription. After the grace, that id reads EMPTY even though its retained message was dropped. `forget()`, called by `_release_device` and delete, also pops a verdict while the subentry may still exist.

Today the only consumer is the start-up catch, roughly 5 s after the subscription, so the window is tiny.

**Fix:** At subscription time, also put the owned ids into the scope: `frozenset(manager.mirrors) | current_owned_ids`. Then infer EMPTY only for ids in `_discovery_scope`.

### IN-02: The fixtures patch with `raising=False`, which hides a renamed constant or method

**File:** `tests/conftest.py:87-111`

**Issue:** `discovery_never_settles` (autouse) and `discovery_settled` patch `DISCOVERY_SETTLE_GRACE_SECONDS` and `MqttGateway.async_on_subscribed` with `raising=False`. If either is renamed, the fixture quietly creates a new attribute. Every test then runs against the real 2 s grace and the real core signal, and EMPTY verdicts start to depend on timing.

**Fix:** Drop `raising=False`. Both attributes exist now.

### IN-03: The gateway tests wait a fixed number of event-loop turns

**File:** `tests/test_discovery_content.py:375-391`

**Issue:** `_subscribe_and_let_the_debouncer_run` spins `asyncio.sleep(0)` up to 2000 times and then exactly 50 times. Whether that is enough depends on how many loop turns core's debouncer, the SUBACK future and the dispatcher take. A change in PHACC or HA can make `test_the_gateway_calls_back_once_the_subscription_is_done` flaky.

The negative tests (`..._never_calls_back_for_another_qos`, `..._after_the_watch_was_stopped`) pass even if the 50 turns are too few, so they can pass vacuously.

**Fix:** Wait for the `MQTT_PROCESSED_SUBSCRIPTIONS` dispatcher signal itself, with an `asyncio.Event` and a timeout. In the negative tests, assert that the signal fired before checking that `calls == []`.

### IN-04: The "Kept the MQTT entities" INFO line counts devices that would be kept anyway, and it repeats at every start

**File:** `custom_components/mqtt_actions/manager.py:930-944`

**Issue:** The count includes every native device whose content is UNKNOWN and whose legacy MQTT device still exists. That also covers devices that only hold customized or user-disabled rows, which stay whatever the content. Combined with WR-01 and WR-02, the line can repeat at every start with no action the user can take.

**Fix:** Count only devices that still have an `INTEGRATION`-disabled legacy row with a native twin, which is what the content check actually blocks. Alternatively, log once per device per run at DEBUG after the first INFO.

### IN-05: troubleshooting.md promises a clear the owner does not always perform

**File:** `docs/troubleshooting.md:114-115`

**Issue:** "the instance that owns the device clears them at its next start" is only true in some cases. The owner does not clear in these cases:

- the payload has the exact current legacy shape, but the owner keeps a legacy row (D-08);
- the payload has any other shape (UNKNOWN);
- the content was not settled in time (WR-02) or never settles (WR-01).

**Fix:** Qualify the sentence. Suggested wording: "...clears them at its next start, unless it still keeps a renamed or otherwise customized MQTT entity of that device".
