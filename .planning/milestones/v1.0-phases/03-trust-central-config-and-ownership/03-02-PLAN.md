## Phase Goal

**As a** user with several HA instances, **I want** devices created on one instance to appear on the others once I approve them, **so that** every instance runs the actions locally.

This plan's slice: the owner's side of ownership. The owner cleans up completely when a device is deleted, defends its published truth against foreign writes, and heals the discovery that a follower's entity deletion tore down.

<objective>
Extend the delete path with the config tombstone and a pop-first removal order (D-16), introduce `sync.py` with the owner side of `SyncManager` (config and discovery watchers, echo history, trailing throttle, ownership issues: D-15, D-17, D-18) and wire it into `Manager`.

Purpose: SYN-03 (owner enforcement and conflict reporting), SYN-06 (broker side of delete) and DSC-03 (discovery healing). The follower side reuses the same wildcard subscription in plan 03-04.

Output: `sync.py`, changes in `manager.py` and `const.py`, en/de issue texts, and `tests/test_sync_owner.py`. Implements D-15, D-16, D-17 and D-18.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Self-derived edge cases (no SPEC.md exists, the spec-less probe was not run):** the prohibitions above and the edge cases in the behavior lists were authored by the planner from RESEARCH and CONTEXT.
- **A2 tunables:** `REPUBLISH_THROTTLE_SECONDS = 60.0` (D-18 start value, also used for config heals), echo history of `PUBLISHED_HASH_HISTORY = 8` hashes per device, repeated-removal hint at `DISCOVERY_REMOVAL_HINT_COUNT = 3` removals within `DISCOVERY_REMOVAL_HINT_WINDOW_SECONDS = 600`.
- **Republish without waiting for the retained replay:** the owner publishes at start without a settle window (SYN-04 says it republishes on every reconnect). A foreign write that predates the start is therefore only caught when the replay reaches the owner after the device exists; live foreign writes are always caught. The README (plan 03-07) states this limit.
- **Issue lifetime:** `doc_overwritten_`, `ownership_claim_` and `discovery_removed_` issues are not persistent and not fixable; they are deleted when the device is deleted, when the hub is removed and at the next restart. The claim and overwrite issues are created only when absent, so a repeating attacker does not reset a user's dismissal.
- **Follower entity customizations (A8, Pitfall 14):** healing republishes the discovery; core recreates the entities fresh, so areas, names and labels the user set on the mirrored entities are lost everywhere. This is the price of D-18 and is documented in plan 03-07.
