## Fixed Issues

### CR-01: Removing an integration-disabled twin on LEGACY content makes core delete the legacy rows that were kept on purpose (D-08 bypass)

**Files modified:** `custom_components/mqtt_actions/takeover.py`, `tests/test_native_replay.py`, `docs/troubleshooting.md`
**Commits:** 342d476 (RED), f3fc554 (GREEN), 1b0392f (docs)
**Status:** fixed: requires human verification
**Applied fix:** `remove_replay_twins` now decides the keeps first and removes after. With LEGACY content, it does not
remove an integration-disabled row while a kept legacy row of the device is still **enabled**. Enabled rows that
are not kept are still disabled first and then removed, which publishes nothing.

This differs from the reviewer's sketch, which blocked on any kept row:
- The sketch breaks the existing test `test_remove_replay_twins_keeps_a_customized_row_with_legacy_content`. In that
  test the kept row is disabled, and the test expects the two disabled buttons to go. The test must stay unedited.
- A scratch probe with `_loop_back_discovery` active showed that core's clear leaves a disabled kept row alone. The
  danger is only to enabled, loaded rows.

The integration regression test
`test_the_catch_keeps_an_enabled_customized_button_next_to_a_disabled_twin_on_legacy_content` loops core's publishes
back. It asserts that the renamed button survives, that the disabled switch and the MQTT device stay, and that nothing
is cleared on the topic. It failed on the pre-fix code with "the customized, kept test button was deleted".

`docs/troubleshooting.md`: "the next start removes them" and "clears them at its next start" now carry the
customized-entity exception, because the behavior changed.

### WR-01: The settle watch only matches qos 1, so a core discovery qos of 2 means the settle never fires

**Files modified:** `custom_components/mqtt_actions/mqtt_gateway.py`, `custom_components/mqtt_actions/sync.py`, `tests/test_discovery_content.py`
**Commits:** 08a9167 (RED), f5aca85 (GREEN)
**Status:** fixed: requires human verification
**Applied fix:**
- `MqttGateway.async_on_subscribed(topic, qos, ...)` now watches core's signal for every qos from `qos` up to 2
  (`MAX_QOS`) and returns one stop callback for all of them.
- Core signals the filter's max qos, so our qos-1 subscription now settles even when core discovery raised the filter
  to qos 2.
- The sync keeps a single watch call. It now passes an explicit `DISCOVERY_SUBSCRIBE_QOS = 1` to both the subscribe
  and the watch, instead of relying on the gateway default.

This differs from the reviewer's sketch, which had the sync register two watches. That would have broken the existing
assertion `settle.watches == [(discovery_wildcard(PREFIX), 1)]`, so the change lives in the gateway instead. The
existing gateway test `test_the_gateway_never_calls_back_for_another_qos` (a qos-2 watch on a qos-1 filter) still
holds.

When core already holds the subscription, `on_done` may be called once per watched qos. `_on_discovery_settled` is
idempotent, so this is harmless.

The new test `test_the_gateway_calls_back_when_another_subscriber_raised_the_qos_of_the_filter` subscribes the filter
at qos 2 and checks that a qos-1 watch fires.

### WR-02: The catch runs once and can fire before the settle has finished, so the fix may never apply

**Files modified:** `custom_components/mqtt_actions/manager.py`, `custom_components/mqtt_actions/sync.py`, `custom_components/mqtt_actions/takeover.py`, `tests/test_native_replay.py`
**Commits:** 923677a (RED), 3158bbf (test setup), 5243f27 (GREEN)
**Status:** fixed: requires human verification
**Applied fix:** A new `SyncManager.discovery_settles_in()` returns how long until an unseen topic can read as EMPTY:
- before the settle: the grace;
- inside the grace: the time that is left;
- `None` once the grace has passed, or when the grace is not finite.

At the end of `_async_replay_catch`, when devices with UNKNOWN content still keep their legacy device, the catch arms
itself again after `max(wait, REPLAY_RETRY_MIN_SECONDS=1.0)`:
- It does so at most `REPLAY_CATCH_RETRIES=5` times per start. `_arm_replay_catch` resets the counter.
- While it re-arms, it logs at DEBUG and skips the INFO "next start checks again" line. The INFO line is logged on the
  final pass only.
- The stop path already cancels `_cancel_replay_catch`.

The test `test_a_catch_that_runs_before_the_settle_checks_again_once_the_grace_has_passed` captures the settle watch.
It runs the first catch before the settle (the twin stays), then settles, advances the manager clock past the grace
and fires time. It asserts that the twin and the legacy device are gone and that nothing was cleared.

Commit 3158bbf added `reset_mock()` after the restart. It drops the publishes from the initial takeover, as the
sibling test `test_a_disabled_leftover_is_removed_at_a_start_with_an_empty_topic` does. With it, the test was
re-checked to fail on the pre-fix code for the intended reason (`['switch.lamp_2'] == []`).
