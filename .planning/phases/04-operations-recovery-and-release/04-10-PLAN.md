## Phase Goal

**As a** user running several HA instances, **I want** to re-trigger actions, see who is connected and recover devices, **so that** I can operate the setup with confidence.

This plan's slice: the headline operation. One service call re-runs a device's actions on every instance that approved it and tells the caller who executed it.

<objective>
Add the re-trigger protocol and its service: the non-retained request topic, the per-requester acknowledgement topic, the receiver rules that make it replay-safe and rate-limited, the caller's collector with a 5 second window, and the ACL lines that a real Mosquitto enforces (D-01 to D-04).

Purpose: OPS-01 and OPS-02. The re-trigger is a second remote execution path next to the state topic, so it reuses the existing approval, mode and breaker gates instead of creating its own and is never retained.

Output: `retrigger.py`, topic helpers, constants, `Manager.retrigger`, the `retrigger` service, translations, the ACL document and tests in all three tiers. Implements D-01, D-02, D-03 and D-04.
</objective>

## Assumptions and defaults (visible, not silent; none are locked decisions, confirm at review)

- **Wire contract (Claude's discretion, names are new and costly to change later):** request topic `<base>/v1/devices/<device uuid>/retrigger`, QoS 1, retain False, payload keys `request_id` (uuid4 text), `requester` (instance id), `state` (the exact StateValue) and `sent_at` (UTC epoch seconds). Acknowledgement topic `<base>/v1/instances/<requester id>/acks`, QoS 1, retain False, payload keys `request_id`, `device_id`, `instance_id`, `instance_name`, `status` and an optional `reason`. `no_answer` is synthesized by the caller and never sent. New topics stay under `v1`.
- **`executed` means accepted and started** (assumption A2), not finished; a failing run still shows up as the usual action-failed Repairs issue.
- **The caller decides the StateValue** and sends the concrete value (assumption A3): the caller's last acted state, or the optional `state` of the call when it matches a StateValue of the device (compared like a state payload, canonical form sent). Receivers whose baseline differs run the caller's trigger anyway.
- **Gate order on the receiver:** retained, size and strict parse, freshness, duplicate, receiver rate limit (other instances' requests only), then device known, state valid for the device, mode (`disabled`, then `observing`), breaker (`paused`), runnability (`not_approved` for a pending or blocked mirror, `error` with reason `no_actions` or `not_runnable` otherwise), then `enqueue(..., test=True)` and `executed`. The re-trigger uses `test=True` like the test button (D-01), so scripts see the run variable `test`.
- **Constants in `const.py` (D-04):** `RETRIGGER_ACK_WINDOW_SECONDS` 5.0, `RETRIGGER_DEVICE_INTERVAL_SECONDS` 5.0, `RETRIGGER_SEEN_LIMIT` 128 (assumption A13), `RETRIGGER_MAX_AGE_SECONDS` 60.0 (assumption A4, a clock-skew tolerance as well), `SERVICE_RETRIGGER`; the status words `ACK_EXECUTED`, `ACK_NOT_APPROVED`, `ACK_PAUSED`, `ACK_OBSERVING`, `ACK_DISABLED`, `ACK_ERROR`, `ACK_NO_ANSWER` and the reason words `unknown_device`, `bad_state`, `no_actions`, `not_runnable`, `offline`. The window is read from the module global at call time so tests can shorten it.
- **Expected acknowledgers:** this instance plus every peer the roster says is online. Roster-known offline instances are listed as `no_answer` with the reason `offline` without waiting. Instances that answer but were not expected are listed too.
- **Own requests:** the caller remembers its request ids (bounded) so its own echo skips the receiver rate limit but not the duplicate check (research pitfall 3); the caller executes through the same receiver path as everyone else.
- **Payload and response naming:** the service response uses the key `uuid` for the device (not `device_id`), so documentation examples of responses never need the registry field name; the wire payloads keep `device_id` like the config document.
- **Task 3 is declarative:** it touches eight files but each edit is a service definition, text or a document line.
- **No SPEC.md exists; the spec-less probe was skipped.** The prohibitions above were authored by the planner from RESEARCH Pattern 1 and CONTEXT D-01 to D-04.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker to receiver | Any client with write access can publish a re-trigger request for any device |
| Broker to caller | Any client with write access can publish an acknowledgement on a requester's topic |
| Service caller | Only an administrator may start a re-trigger |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-42 | Elevation of privilege | the re-trigger as a second remote execution path | high | mitigate | Receivers run only what the approval gate already allows (`can_run`), obey the mode and the breaker, answer not_approved for pending or blocked mirrors, and the ACL grants the topic to Home Assistant users only; the request carries only a StateValue that must match the device, never actions (`test_unapproved_mirror_answers_not_approved_and_runs_nothing`) |
| T-04-43 | Denial of service | replay or flood of requests | medium | mitigate | Retained messages ignored, a 128-entry request id memory, a 60 second freshness window, one accepted request per device per 5 seconds on the receiver and on the caller (`test_duplicate_request_ids_run_once`, `test_receiver_rate_limit_per_device`) |
| T-04-44 | Spoofing | forged acknowledgement | medium | accept | Acknowledgements only decide what the caller is shown, never execution; they follow the same trust boundary as config ownership (cooperative inside the Home Assistant user group) and the ACL limits writes to Home Assistant users; stated in the ACL limits |
| T-04-45 | Tampering | a QoS 1 request queued during an outage runs actions late | medium | mitigate | The send time must be within 60 seconds of the receiver's clock (`test_stale_and_future_requests_are_dropped`) |

| T-04-47 | Denial of service | pending collectors or acknowledgements growing without bound | low | mitigate | One pending record per call removed in a `finally`, at most one acknowledgement per instance per request and a cap per request |
| T-04-48 | Tampering | broker-supplied instance names in the response or in logs | low | mitigate | Names validated like heartbeat names; logs use quoted, capped text; the response is data, not markdown |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs nothing |
