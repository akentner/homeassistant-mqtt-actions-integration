# Phase 09.2: CR-01 cross-instance gap closure - Context

**Gathered:** 2026-10-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the cross-instance CR-01 gap that the bench observation on FIX dc6513c proved (09.1-VERIFICATION truth #7,
`09.1-evidence/fix2/cr01-observation/outcome.txt`: `contradicts`): while a legacy Discovery message is retained, a
customized, enabled MQTT entity of the device that any instance keeps on purpose survives on **every** instance. No
instance's replay catch, takeover-path twin removal or explicit clear lets the shared legacy topic go empty under another
instance's kept row (directly or through core MQTT's clear-on-remove hook).

Then: new FIX commit, CI and Validate green on it, full bench re-run on exactly that SHA (preflight, heal start, UAT-02
from integration and null tombstones, UAT-04, CR-01 gate), and a records plan that re-points 09-04 and 09-05 to the new
FIX and completes the release notes. The tag itself stays with Phase 9 (09-04/09-05), pushed by the owner.

Root cause (from `takeover.py:216-262`, `manager.py:889-930`, 1133-1160): any empty retained payload on the legacy
device topic deletes the loaded legacy rows on every instance. `keeps_an_enabled_row` and the owner's
`legacy_device(...) is None` check only see local rows. On ha-b the WR-04 move had already turned the customized row
native, so its catch removed the integration-disabled switch twin on LEGACY content, core on ha-b cleared the topic, and
core on ha-a deleted the kept button.

### Cross-instance mechanism
- **D-01:** Peers announce kept legacy rows in the existing presence heartbeat (`presence.py`). Each instance adds a new
  field: the list of device ids for which it holds a kept, **enabled, loaded** legacy (platform `mqtt`) row (the rows
  `remove_replay_twins` keeps: no native twin under this entry, customized, or carrying the identity). Device ids only,
  never names, entity ids or registry content; capped and strictly validated like the other heartbeat fields
  (T-04-09 to T-04-12); no field value in any log line (T-04-14). The ids already appear in broker topics, so nothing new
  leaks. The value must be correct in the first heartbeat after start (the registry already holds the customized row
  before the replay arrives). — **Reversibility:** costly — the heartbeat field becomes a wire contract between versions;
  removing or renaming it later makes newer peers read older ones as UNKNOWN.
- **D-02:** The gate: the shared legacy topic may go empty for device X only when (a) this instance keeps no enabled legacy
  row of X (existing local rule) **and** (b) every **online** peer (presence roster) has sent a heartbeat since this
  start that carries the new field and does not list X. Offline peers do not block: they have nothing loaded, so core's
  empty payload deletes nothing there.
- **D-03:** A peer that is online but not yet heard since start, or that sends no field (older version, e.g. v1.0.0),
  counts as UNKNOWN: keep, no removal, no clear (fail-safe in the spirit of 09.1 D-03). In a mixed-version fleet the
  disabled twins stay until every online instance runs 1.0.1. README/troubleshooting and the release notes say so.
- **D-04:** Waiting for peer heartbeats uses the existing catch re-arm (`REPLAY_CATCH_RETRIES`,
  `takeover.py:46`): a device blocked only because a peer is not heard yet is treated like UNKNOWN content and the catch
  arms itself again within the existing bound; after that it keeps, and the next start tries again. No separate peer
  timeout constant.

### Who lets the topic go empty
- **D-05:** **Only the owner** of a device ever lets its shared legacy topic go empty: by removing an integration-disabled
  twin that core discovered in this run (core's clear-on-remove hook) or by an explicit retained clear. A follower
  (mirror) never removes an integration-disabled twin on LEGACY content. This extends T-5-02 ("a follower publishes
  nothing") to core's hook. It applies at **both** call sites of `_remove_replay_twins`: the start-up takeover path
  (`manager.py:1152`) and the later replay catch (`manager.py:913`). Enabled replay twins (disable-then-remove, which
  publishes nothing) are unaffected.
- **D-06:** A follower removes its integration-disabled twins once the content of that device is EMPTY. When the content
  of a device with a waiting twin changes from LEGACY to EMPTY (the owner cleared), the follower's catch re-arms in the
  same run, bounded like the existing retries, so UAT-02 meets E1 to E3 on both instances after one start without any
  change to expectations or procedure.
- **D-07:** If the owner is offline, the legacy topic stays retained and the followers' twins stay disabled. That is
  harmless and documented.

### Owner clear (09.1 D-06)
- **D-08:** The owner's explicit clear in the catch (`manager.py:918-930`) falls under the same gate (D-02/D-03), on top of
  its existing conditions (LEGACY content, owned, not transferred away, no local legacy device left).
- **D-09:** As a second layer, the owner publishes the migrate payload (`discovery.py:312` `async_publish_migrate`, as the
  takeover path does at `manager.py:1135-1142`) before the clear, **if research confirms** that core MQTT 2026.9.4 then
  keeps the registry rows of other instances when the empty payload follows. If research cannot confirm it, the gate alone
  applies and no migrate is added.
- **D-10:** Re-check right before the publish: after the flush and immediately before the clear (and before the removal
  that triggers core's hook), the owner re-reads both the content and the peer signal, like the existing "read again after
  the flush" for EXPORT. The remaining window (a user customizes a legacy row live between the re-check and the clear) is
  a documented known limit.

### Moved `_2` row (WR-04)
- **D-11:** No product change. A takeover that moves a replayed, customized row (with its `_2` entity id) to native and
  removes the original native row is correct per WR-04: the row the user customized keeps its entity id, which
  automations may use. `docs/troubleshooting.md` explains the behavior. On the bench, the planned registry restore after
  the CR-01 gate stays the hygiene fallback (recorded as such, never as a result), as in `09.1-11`.

### Proof: tests
- **D-12:** Red test first (09.1 D-05): one `hass` with the fake broker. The empty retained payload core publishes is
  looped back with `async_fire_mqtt_message` (the gap the 09.1 review named), and a simulated peer heartbeat reports the
  kept row. Red before the fix (the kept row is deleted or the clear goes out), green after. No two-`hass` harness.
- **D-13:** Unit tests of the gate matrix: role (owner, follower) x peer state (lists X, silent on X, older version
  without field, online but not heard, offline) x content (LEGACY, EMPTY, EXPORT, UNKNOWN), for the twin removal and the
  explicit clear. Plus: the follower re-arm on LEGACY to EMPTY (D-06), the re-check before publish (D-10), and the
  heartbeat field's validation and cap. Existing CR-01, null-tombstone and integration-tombstone tests stay green unchanged.

### Proof: bench
- **D-14:** Full re-run on exactly the new FIX: preflight, heal start (D-09 of 09.1), UAT-02 (a) integration and (b) null
  tombstones, UAT-04, then the CR-01 gate. CI and Validate green on that SHA first (`workflow_dispatch` counts, `headSha`
  must equal FIX, Phase 9 D-04 amendment).
- **D-15:** The CR-01 check becomes a **pass/fail release gate**, no longer an observation. Expectations are fixed in the
  plan before the run, in the format of `outcome.txt`; the verdict must be `holds` on ha-a and ha-b. It gets its own block
  in `09-UAT.md`. If it does not hold: no re-pointing, no tag, back to the owner.
- **D-16:** Three variants, each with its own fixed expectations:
  1. **Bench case repeated:** mirror ha-b moved the customized row native (WR-04), owner ha-a keeps a customized enabled
     legacy row. Expected: the kept row on ha-a survives, ha-b removes nothing on LEGACY, the topic stays retained.
  2. **Reverse case:** only follower ha-b keeps a customized enabled legacy row, the owner ha-a keeps nothing. Expected:
     the owner does not clear and removes no disabled twin, the row on ha-b survives.
  3. **Positive control:** nobody keeps anything. Expected: the owner removes its twins and clears, the followers remove
     theirs on EMPTY in the same run, no legacy row or device is left on either instance.
