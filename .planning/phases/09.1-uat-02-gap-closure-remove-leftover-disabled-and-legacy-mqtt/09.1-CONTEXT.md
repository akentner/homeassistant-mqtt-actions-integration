# Phase 9.1: UAT-02 gap closure: remove leftover disabled and legacy mqtt rows on replay - Context

**Gathered:** 2026-10-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the UAT-02 gap from `09-UAT.md` (Gaps, test 3). The starting state is that the regression tombstones carry
`disabled_by: integration`. After a retained legacy Discovery replay at start, the replay brings the rows back as disabled
`platform: mqtt` rows (`switch.lampe_test_2`, `select.bar_select_2`). Those rows and the legacy devices
`mqtt_actions_<id>` stay on ha-a and ha-b, and E1 to E3 fail in both rounds.

The phase delivers:
1. a failing test that reproduces the gap;
2. the product fix in the start-up replay catch;
3. the bench comparison fix in `check-uat02.sh clean`;
4. CI green on the fix SHA;
5. a bench double pass (UAT-02 from both tombstone states, UAT-04 per D-06) on exactly that SHA;
6. a ledger update and release notes.

Tagging and the release check stay in the existing plans 09-04 and 09-05, re-pointed to the fix SHA.

**Root-cause hypothesis (research must confirm):** `takeover.remove_replay_twins` (`custom_components/mqtt_actions/takeover.py:202`)
skips every disabled legacy row on purpose. This is the CR-01 rule: when a row that core MQTT discovered while it was disabled
leaves the registry, core publishes an empty retained discovery. Integration tombstones make the replay restore the rows as
disabled, so the catch never removes them. PROJECT.md:91 records "CR-01 leaves disabled rows behind (accepted)", which
conflicts with UAT-02 E1 to E3 (unchanged per Phase 9 D-09). Phase 8 passed only because its run started from null tombstones.
A second lead: the duplicate guard can disable an enabled duplicate before the 5-second quiet-period catch runs, and that also
makes the row unremovable.

</domain>

<decisions>
## Implementation Decisions

### Fix strategy vs. CR-01
- **D-01:** CR-01 stays a hard invariant. The product never clears another instance's retained export topic, including
  indirectly through core MQTT's clear-on-removal hook.
- **D-02:** The start-up replay catch may now remove a **disabled** legacy replay twin, but only when the retained discovery on
  that row's topic is a **legacy payload** (multi-component with test buttons, as opposed to the single-component export from
  `discovery.build_export`, `discovery.py:140`) or the topic is empty. Core clearing a stale legacy topic is acceptable and even
  wanted. With an export payload on the topic, the row stays and CR-01 holds.
- **D-03:** If the catch cannot determine the topic content reliably (payload not readable, not delivered yet, or of an unknown
  shape), the row stays. This is a fail-safe in favor of CR-01, and the next start tries again. The log line carries a count
  only, never broker content.
- **D-04:** Only rows with `disabled_by: integration` are candidates. Rows with `disabled_by: user` always stay, because that is
  a user decision. The existing customization rule (`_is_customized`, WR-03) and the twin and identity rules of
  `remove_replay_twins` stay unchanged.
- **D-05:** Test first. A test that starts from integration tombstones reproduces E1 to E3 (red) before the fix and goes green
  after it. The existing null-tombstone tests stay green unchanged.

### Legacy devices and retained topics
- **D-06:** After the catch removes the rows, the product explicitly clears the retained legacy discovery topic with an empty
  retained publish. It does so only when a legacy payload is on that topic (the same check as D-02), and it uses the same pattern
  as the takeover path's retained clear (`manager.py` around line 1032). It does not rely on core's hook. The publish rule of the
  takeover path applies: only the instance allowed to publish for the device clears (T-5-02, "a follower publishes nothing").
  Research confirms the exact owner/follower split.
- **D-07:** Scope is the start-up replay only. WR03-LIVE-REPLAY (a live replay creates `_2` entities that go only at the next
  start) stays a documented known limit in the release notes (Phase 9 D-11).
- **D-08:** A legacy device that still has rows after the catch (customized, `disabled_by: user`, foreign) stays, as it does
  today. It goes only when nothing is left on it (`takeover.py`, end of `remove_replay_twins`). E3 covers the bench case, which
  has no such rows.

### Bench start state and re-run
- **D-09:** The bench recovers through product behavior, not hand edits or a backup restore. Deploy the fix build and do one
  start; the new catch must clean up the current bench state (2 disabled live mqtt rows plus 2 legacy devices per instance).
  That start is recorded as evidence of the real case. Baseline and reseed come only after it.
- **D-10:** UAT-02 runs twice on the fix SHA, both times with the unchanged expectations E1 to E4 (Phase 9 D-09):
  (a) from **integration** tombstones, the failing case;
  (b) from **null** tombstones, the Phase 8 reference.
  Both must pass.
- **D-11:** Fix the bench comparison in `check-uat02.sh clean` (`do_clean`) by filtering the UAT marker rows on **both** sides of
  the baseline comparison. The change touches the comparison path only, never an expectation (allowed under Phase 9 D-09). It is
  its own commit, with proof that the `run` path stays byte-identical. The copy under `~/ha-test/bin/` and the evidence snapshot
  under `09.1-evidence/` must match.
- **D-12:** UAT-04 stays as in Phase 9 D-06: reseed to null tombstones after UAT-02, a `prepare.txt` state line in the same
  format, and unchanged expectations X1 to X10. ha-c stays stopped (Phase 9 D-07). Preflight and backups follow Phase 9 D-08,
  pinned to the fix SHA.

### Release mechanics
- **D-13:** The version stays **1.0.1**. It was never tagged or released, so there is no 1.0.2 and no separate bump commit. The
  fix commit on `main` (manifest still `1.0.1`) becomes the tag SHA. Phase 9 D-02 now reads: tag SHA == bench SHA == fix SHA. The
  `.planning/` commits between `7baec98` and the fix are part of the tagged tree, which is acceptable. — **Reversibility:**
  one-way — once the owner pushes `v1.0.1` and HACS offers it, moving the tag breaks installs that resolved it.
- **D-14:** `main` stays frozen per Phase 9 D-01. Only the 9.1 product fix, its test and `.planning/` commits land on it before
  the tag. No IN-04 or MIR-01 change, no Phase 10 work, and no `release/` branch.
- **D-15:** 9.1 ends with the bench passing. The order is: failing test, then the fix, then the bench-script fix, then the owner
  pushes `main`, then CI and Validate are green on the fix SHA (Phase 9 D-04 amendment: `workflow_dispatch` counts, and `headSha`
  must equal the fix SHA), then UAT-02 (both starts) and UAT-04 run, then the ledger and the release notes are written. After
  that, 09-04 and 09-05 run unchanged in substance and are re-pointed to the fix SHA instead of `7baec98`. The owner pushes the
  tag.
- **D-16:** Raw evidence goes under `.planning/phases/09.1-.../09.1-evidence/` (`preflight/`, `heal-start/`,
  `uat-02-integration/`, `uat-02-null/`, `uat-04/`, `release/`). `09-UAT.md` gets new rows that carry the fix SHA. The FAIL and
  BLOCKED rows for `7baec98` stay as history. 09-04 keeps reading `09-UAT.md`. Release notes follow Phase 9 D-10 and D-11, and
  they also name the fixed case: the replay from disabled tombstones now cleans up.

### Claude's Discretion
- Tombstone handling: research determines whether a replay is still possible once the legacy topic is cleared (D-06). The
  deleted-entity record is purged only if that is needed and a stable API exists. The default is not to touch
  `deleted_entities`.
- How the catch reads the retained payload (its own short-lived subscribe vs. core MQTT discovery state). Prefer a public API.
  The D-03 fail-safe applies.
- How the guard and the catch interact: whether rows the guard disabled during this run count as candidates. They must fall
  under D-02 to D-04.
- Plan split, wave order, and the names of helper scripts and evidence files.

## Existing Code Insights

### Reusable Assets
- `takeover.remove_replay_twins` (`takeover.py:202`): the catch's registry logic. The fix extends its disabled-row branch (`takeover.py:233`) under D-02 to D-04.
- `takeover.disable_duplicates` (`takeover.py:250`): the guard, unchanged in rule. Its docstring and the one of `_arm_duplicate_guard` (`manager.py:899`) state CR-01 and must be updated to the refined rule.
- `takeover.legacy_device`, `_legacy_entries`, `is_legacy_entity`, `_is_customized`, `_carries_the_identity`: identity and safety checks to reuse as they are.
- `manager._arm_replay_catch` / `_on_replay_catch_due` / `_async_replay_catch` (`manager.py:860` to `886`): the start-up quiet-period catch (5 s, `takeover.REPLAY_QUIET_SECONDS`). After a removal it flushes the registries.
- The takeover path in `manager.py` (around line 1030): migrate publish, registry move, catch, flush, then the retained clear. This is the pattern for D-06, and it holds the owner-only publish rule.
- `discovery.build_export` (`discovery.py:140`) vs. the legacy payload builder: the shape difference that D-02 relies on. `DiscoveryPublisher.async_clear_export` (`discovery.py:198`) shows the empty-retained publish.

### Established Patterns
- Registry logic stays synchronous in one step (disable, then remove), so core cannot discover a row in between (WR-01).
- Log lines carry counts only, never ids, names or payloads from the broker.
- A failure in the catch or the guard must never stop the manager (`except Exception` with a warning plus a debug type name).
- Pure tests use PHACC `mqtt_mock` / `async_fire_mqtt_message` for retained replays. Registry flushes go through the private API (`registry._store`), which Phase 10 FIX-01 will guard.

### Integration Points
- `manager.py` start-up sequence (around line 815): arming the catch after subscribe.
- The retained discovery topic of a legacy device, which `topics.discovery_topic` derives under the configured discovery prefix.
- The bench: `check-uat02.sh` (`run` and `clean`), `reseed-tombstones.sh`, and the evidence checkers `check-evidence-clean.sh` and `check-stale-anchor.sh`.
