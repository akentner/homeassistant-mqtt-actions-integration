## Decisions this plan implements (visible, not silent)

- **D-01:** ha-a and `mosq` only; production untouched.
- **D-03:** each task starts from `check-preflight.sh --quick`; the breaker check restarts ha-a, which re-uses the same mounted files, and the end gate asserts the SHA again.
- **D-04:** the loop, the publishes, the issue reads, the restart and the reload are scripted; the browser MCP captures the flows and cards; the owner judges rendering. If the browser MCP cannot edit the loop actions (the one step that must go through the action editor), a `checkpoint:human-action` hands the owner the uuid and the YAML.
- **D-07, D-08:** both items are in scope; a rejection or a FAIL is `result: issue` with a Gaps entry and the phase continues.
- **Planner decisions (documented):** (1) the loop device is created by `import_devices` with inert actions to learn its uuid, then its actions are set to the loop through the reconfigure flow, because the uuid is only known after creation; (2) the loop actions publish with `retain` false, so the retained state value stays at the last external value; (3) P2-2's recorded result is `pass` only when the scripted verdict is PASS and the owner accepts the card rendering; an owner rejection is recorded as `result: issue` with an `owner_rejected:` line (the recorder accepts that combination); (4) the loop device is not approved on ha-b.

## Fixture facts (verified 2026-10-04; re-read before relying)

- Breaker defaults: `DEFAULT_BREAKER_MAX_RUNS = 5` runs per `DEFAULT_BREAKER_WINDOW = 10` seconds; the next change trips and does not run; a trip pauses the device (baseline only), stops running and queued runs, logs one warning and raises the Repairs issue `circuit_breaker_{device id}` (`const.py`, STA-06).
- The tripped state persists as a per-device config hash in the Store, so a restart keeps the pause; a reload of the integration entry or a real config change releases it; an unchanged save releases nothing (STATE, 02 decisions D-15 and D-17).
- Owned actions are unrestricted, so `mqtt.publish` works on an owned device (it is denied only for actions received from the broker, `DENIED_SERVICES`).
- Expected message count of the loop on the state topic: one external publish plus five action publishes, then the trip; the script asserts a bounded range and records the observed number, because a runaway loop would show hundreds.
- `UAT Loop` is mirrored on ha-b as an approval request; it must stay unapproved.
- External publisher: `uat_bridge` (state topics only). Hub entry reload: `POST /api/config_entries/entry/{entry id}/reload` through the guard (research A5; fallback is the Reload action in the frontend).
