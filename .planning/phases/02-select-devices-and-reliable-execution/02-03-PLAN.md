## Phase Goal

**As a** Home Assistant user, **I want to** create Select devices whose options each run their own actions, **so that** multi-state MQTT devices drive my setup predictably.

This plan's slice: the test button. A user can run any trigger's actions of a device at any time to check them, without flipping the real state.

<objective>
Add a Discovery `button` entity per trigger, a non-retained test topic, and a manager path that runs the pressed trigger's actions locally with the run variable `test`, while leaving state, baseline, startup window and publishes untouched.

Purpose: DEV-07. A user who edits actions needs a way to try them without creating a state change that other systems (and the baseline) would see. A discovery button always publishes to the broker, so the integration subscribes to a dedicated test topic and executes the press itself; the button entity carries no logic.

Output: `test_topic` in `topics.py`, button components and tombstones in `discovery.py`, the test subscription and lifecycle in `manager.py`, the `test` run variable in `runner.py`, and `tests/test_test_buttons.py`. Implements D-13.
</objective>

## Assumptions and defaults carried from RESEARCH.md (visible, not silent)

- **A2** The test button stays usable while a device is paused by the circuit breaker (plan 02-04): the test path never consults the breaker. Risk if wrong: none for correctness, a user could not debug a tripped loop; trivial to flip.
- **A4** Test buttons use `entity_category: "config"`, which keeps them out of auto-generated dashboards and lists them under Configuration.
- **A9 / open question 2 default** A press fans out to every instance subscribed to the test topic, not only the instance whose user pressed it. Accepted for Phase 2 (a single instance); Phase 3 revisits it together with the trust gate, and the broker ACL documentation (TRU-04) must cover the `/test` topic as a second action trigger source.
- **Open question 3 default** Existing Phase 1 Switch devices get their two test buttons on the next discovery publish after the upgrade, with no opt-out; release notes and the README (plan 02-05) mention it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Broker to test topic subscription | Anyone with write access to the test topic can ask a device to run an action |
| Retained broker messages | A retained message on a subscribed topic is replayed on every (re)subscribe |
| Discovery payload to core | Component keys and unique ids become entity registry entries |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-08 | Elevation of privilege | broker user publishes to the test topic to run actions | medium | mitigate | Only payloads that equal a StateValue of the device run anything; the topic sits under `<base>/v1/devices/`, covered by the existing ACL guidance; the README (plan 02-05) names the test topic as a second trigger source and the Phase 3 trust gate and ACL documentation (TRU-04) extend it |
| T-02-09 | Tampering | a retained message on the test topic replays actions at every restart or reconnect | high | mitigate | `_on_test_message` returns immediately for `msg.retain`; the discovery button itself publishes with `retain` False; covered by `test_retained_test_message_is_ignored` |
| T-02-10 | Repudiation | log forging through unknown test payloads | low | mitigate | Unknown payloads reuse `_log_ignored` (truncated repr, one line, empty payload only at debug) |
| T-02-11 | Tampering | a button entity survives after its option was removed while MQTT was unavailable | low | accept | Tombstones are kept in memory while the process lives; a removal during an MQTT outage leaves an orphaned registry entry the user can delete; no action can run from it because the subscription resolves triggers from the spec |
| T-02-12 | Denial of service | a press fans out to every instance subscribed to the test topic | low | accept | Single instance in Phase 2 (assumption A9); revisited in Phase 3 with the trust gate; the action itself is the user's own |
| T-02-SC | Tampering | package installs | low | accept | This plan installs nothing; no dependency is added |
</threat_model>
